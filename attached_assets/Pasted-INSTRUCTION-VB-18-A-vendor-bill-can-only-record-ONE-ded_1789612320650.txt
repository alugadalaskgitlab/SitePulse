INSTRUCTION VB-18: A vendor bill can only record ONE deduction/advance line at the whole-bill level — when the diesel-advance auto-suggestion fills it, there is no way to also record a separate cash/advance deduction to the same vendor on the same bill

Do not touch the per-equipment-group "Other Debit / Recovery / Advance Adjustment / Other Credit" three-field system used elsewhere in this same file (~line 2714) — that one already works correctly and is not in scope; if anything, use it as a design reference. BACKGROUND (confirmed by direct code review — do not re-derive)
1. client/src/pages/VendorBills.tsx has a single bill-level adjustment: `adjustmentLabel` (string) and `adjustmentAmount` (number), declared once (~line 624-625), rendered as ONE label + ONE reason/reference input + ONE signed amount input (~line 3478-3504), stored as ONE pair of flat columns on the bill: `adjustment_label` / `adjustment_amount` (shared/schema.ts ~line 2248-2249, real/text, default 0).
2. When a diesel-advance recovery is detected for the vendor (`contractorAdvanceSuggestion`), it auto-fills this SAME single field: `setAdjustmentLabel(reason); setAdjustmentAmount(-contractorAdvanceSuggestion.amount)` (~line 918-919). The label even changes to "Other Debit / Recovery — Contractor Diesel Advance" specifically to describe this auto-filled use (~line 3479).
3. Because there is only one label/amount pair for the whole bill, once the diesel-advance suggestion has filled it, there is no remaining field for any OTHER deduction — a cash advance paid directly to the vendor, a damages recovery, or any other agreed deduction unrelated to diesel. Typing over the field would simply replace the diesel-advance entry, not add a second one. This is confirmed as the exact case the person hit: a JCB Hourly Hire bill had a correctly auto-calculated 10 L diesel-advance deduction already occupying this field, with no way to also enter a separate advance amount owed by the same vendor.
4. `netTotal` (~line 1581) already sums the single `adjustmentAmount` correctly into the bill total; the PDF/print output (~line 2207-2208, 2225) and the bill list/history view (~line 4063-4064) also each read this single value. All of these read points will need to account for multiple entries once the fix is in.

FIX — SUPPORT MULTIPLE INDEPENDENT DEDUCTION/CREDIT LINES ON THE SAME BILL
1. Add a new nullable column to the bill's schema to hold an array of additional adjustment entries — each with its own label/reason (text) and signed amount (number), e.g. `additionalAdjustments: jsonb("additional_adjustments")` defaulting to an empty array. Keep the existing `adjustmentLabel`/`adjustmentAmount` columns exactly as they are today (still used for the diesel-advance auto-suggestion, for backward compatibility with existing saved bills) — do not remove or repurpose them.
2. In the UI (~line 3478-3505), keep the existing single adjustment row exactly as it is (still auto-filled by the diesel-advance suggestion when applicable). Below it, render the list of `additionalAdjustments` entries the same way — each with its own label/reason input and signed-amount input — plus a "+ Add deduction / credit" button that appends a new blank entry, and a remove control on each entry.
3. Update `netTotal` (~line 1581) to sum the existing single `adjustmentAmount` PLUS every entry in `additionalAdjustments`.
4. Update every other place that reads the bill's adjustment for display or export — the PDF/print row-builder (~line 2207-2208, 2225), and the bill list/history rendering (~line 4063-4064) — so each additional entry appears as its own labeled line (not just a single combined number), consistent with how the primary adjustment line is already shown.
5. Update the save payload (~line 1868-1869) to also send `additionalAdjustments`, and the corresponding server-side bill create/update handling to persist and return it.
6. When an existing bill is loaded for editing (~line 1096-1113), hydrate `additionalAdjustments` from the saved record the same way `adjustmentLabel`/`adjustmentAmount` are already hydrated.
