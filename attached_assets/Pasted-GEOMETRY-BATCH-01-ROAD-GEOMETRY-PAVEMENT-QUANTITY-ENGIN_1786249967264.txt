GEOMETRY BATCH 01 — ROAD GEOMETRY + PAVEMENT QUANTITY ENGINE FOUNDATION

Batch 03 is closed.

We are now starting the optional Enterprise Road Geometry / Engineering Quantity feature.

This first geometry batch must remain deliberately small.

OBJECTIVE

Create a simple project-level Road Geometry setup and a reusable geometry quantity engine for linear pavement items.

For this batch:

- geometry is OPTIONAL;
- Contract BOQ quantities remain untouched;
- calculated quantities are for preview/comparison only;
- do NOT feed geometry quantities into Auto Sequence, Gantt, Execution Arrangement, BOM, DPR, No-Scope quantity deductions or RA bills yet.

The purpose is to establish and verify the engineering calculation foundation first.

1. HARD UOM INVARIANT

This is mandatory throughout the design.

EVERY calculated quantity exposed by the geometry/quantity engine must be returned and displayed in the ACTUAL UoM of that BOQ item.

Never infer output UoM from work type.

Examples:

- BOQ DBM unit = Cum → calculated DBM must be shown in Cum.
- BOQ BC unit = Cum → calculated BC must be shown in Cum.
- BOQ Tack Coat unit = Sqm → calculated Tack must be shown in Sqm.
- BOQ WMM unit = Cum → calculated WMM must be shown in Cum.
- If another project's BOQ genuinely uses MT for an item → only then may the final result be MT.
- Rmt / Nos / other units must similarly respect the actual BOQ item unit.

Internal calculations may use length, area, volume, density, etc., but before a calculated quantity leaves the engine it must be normalized to:

{
  quantity,
  unit: actual BOQ item UoM,
  calculationBasis / explanation
}

Do not hardcode "bituminous = MT" or similar assumptions.

First inspect and report:

- Project schema and current project setup/settings UI.
- BOQ item fields:
  • unit/UoM
  • category/work classification

  • any current plannedWidthM / plannedThicknessMm fields.
- `shared/quantityResolver.ts`.
- Existing quantity calculations in programme/Gantt that already use width/thickness.
- Existing work classification such as pavement / earthwork-estimate / mt-proportional.
- Existing unit-normalization helpers and tests.

IMPORTANT:

Identify the existing canonical BOQ/UoM normalization helper(s) by exact file/function name before writing any new unit-normalization code.

Inspect relevant existing tests such as:
- `tests/uomConvert.test.ts`
- `tests/boqNormalise.test.ts`
or their current equivalents.

Reuse the existing canonical normalization path.

If any new UoM logic is genuinely required, justify why the existing helper cannot handle it.

Do NOT create a second parallel normalization implementation.

Also confirm explicitly whether existing work classification distinguishes individual pavement layers:

- Subgrade
- GSB
- WMM
- DBM
- BC
- Prime
- Tack

or whether it only has coarse groups such as:
- pavement
- earthwork-estimate
- mt-proportional.

If existing classification is too coarse, design and report the proposed item→geometry-layer mapping mechanism before relying on it.

Possible approaches may include:
- existing persisted work category/layer field;
- deterministic description/short-name mapping;
- explicit manual mapping where necessary.

Do NOT assume individual pavement-layer classification already exists.

This feature is intended for the Enterprise version/module.

However, do not implement broad commercial licensing/plan logic in this batch unless an existing feature-gate mechanism already exists and this can plug into it trivially.

At project level provide an explicit optional state conceptually like:

Enable Road Geometry & Quantities

Default for existing projects must be OFF / unset so existing projects behave exactly as before.

Create a compact project-level section/page/card:

ROAD GEOMETRY & QUANTITIES

The UI must be simple enough for a PM/site engineer and avoid unnecessary technical fields.

For Geometry Batch 01 capture only the typical/proposed pavement section needed for pavement quantities.

Suggested basic inputs:

- Soft shoulder RHS — optional

- GSB

- enabled / applicable
- thickness

Do not expose unnecessary engineering parameters.

5. LAYER WIDTHS

SitePulse must know the applicable width for each layer.

Do NOT blindly assume every layer has exactly the carriageway width.

For Batch 01:

- derive a sensible proposed default layer width from the entered road section;
- allow a compact override only where needed.

For example, a proposed rule might be:

- bituminous layers = carriageway + applicable paved shoulders
- granular layers = defined pavement/formation width
- Subgrade = its intended formation/subgrade width

BUT THIS IS AN ENGINEERING BUSINESS RULE, NOT JUST A CODING DETAIL.

Before treating any default rule as final:

- report the proposed default width rule for every supported layer;
- identify the assumptions behind it;
- make the rule easy to override;
- do not represent the rule as engineeringly authoritative merely because it is implemented consistently.

We will review/sign off the default rules after seeing the report and preview.

A simple model is sufficient:

Layer | Default Width | Thickness | Override Width (optional)

The UI may hide width overrides behind:

Advanced / Adjust layer widths

Do not create a complicated cross-section designer.

IMPORTANT:

Show a clear state such as:

"Confirm project corridor first to calculate geometry quantities."

For Batch 01, calculate against the FULL confirmed contractual/project corridor geometry only.

Do NOT deduct:
- No-Scope

from geometry quantity in this batch.

Scope masking comes later.

The purpose now is:

"What quantity does this typical road geometry produce for the full confirmed project corridor?"

7. PAVEMENT QUANTITY CALCULATIONS

Build a reusable geometry quantity engine/service in shared code.

Do not calculate quantities inside the React component.

At minimum support:

A. AREA-BASED ITEMS

Where the BOQ UoM and mapped work type require area:

Quantity = applicable width × length

Typical examples:
- Prime Coat
- Tack Coat
- other Sqm linear treatments

B. VOLUME-BASED PAVEMENT ITEMS

For layer quantities:

Quantity = applicable width × thickness × length

with thickness converted correctly from mm to metres internally.

Typical examples:
- Subgrade
- GSB
- WMM
- DBM
- BC

If BOQ UoM is Cum, return Cum directly.

C. MASS-BASED BOQ ITEMS

Only if the actual BOQ item UoM requires mass:

geometry volume may be converted using an explicit density/conversion basis.

Do not add a complicated density UI in this batch unless needed by actual test data.

If a mass conversion cannot be safely calculated because no density is configured:

return a clear "conversion input required" state rather than inventing a density.

Again:
work type must NEVER determine the final output UoM.
BOQ UoM determines the final output UoM.

8. BOQ ITEM → GEOMETRY LAYER MAPPING

Do not automatically apply geometry math to every BOQ item.

Identify only suitable LINEAR pavement items.

Existing `allocationRuleForItem` or equivalent coarse classification may NOT be sufficient to distinguish individual layers.

Before implementation, report whether the current code can reliably distinguish:

- Subgrade
- GSB
- WMM
- Prime
- Tack
- DBM
- BC

If not, implement the smallest clean mapping mechanism necessary for Geometry Batch 01.

The mapping must distinguish between:

- Geometry calculable
- Needs mapping/configuration
- Unsupported/non-linear for this geometry phase

Do not rely on fragile description regex alone if an existing persisted classification can be reused.

If deterministic description/short-name matching is required as a fallback:
- keep it centralized;
- test it;
- surface uncertain/unmapped items instead of guessing.

Do not attempt to calculate:
- structures
- culverts
- LS items
- Nos.
- miscellaneous/non-linear items

merely because they appear in the BOQ.

Do not modify BOQ mappings globally in this batch unless strictly required for this feature.

10. CALCULATION TRANSPARENCY

For each calculated result, retain enough metadata so the user/system can know how it was derived.

Conceptually return:

- quantity
- unit
- basis: "geometry"
- length used
- width used
- thickness used where applicable
- geometry layer type
- any unit conversion used
- density/conversionBasis only if applicable

The UI can show a compact "How calculated" detail/tooltip rather than cluttering the screen.

Example:

BC Geometry Qty: 1,425.00 Cum
Based on:
3,800 m × 9.375 m × 0.040 m

Do not show unnecessary calculation detail by default.

11. UNIT NORMALIZATION

This must use the EXISTING canonical BOQ/UoM normalization path identified during investigation.

Do not introduce independent aliases or a new normalization table unless the existing canonical module genuinely cannot support the required unit.

Internally normalize compatible aliases where already supported, e.g.:

Cum / cum / m3 / m³
Sqm / sqm / m2 / m²
Rmt / rm / m
MT / tonne / ton where already supported

BUT:

- preserve the BOQ's original/display UoM for user-facing output;
- use normalized unit only internally for calculation compatibility;
- final output unit must be the BOQ item's UoM.

Do not recreate the previous "1 cum / 1 hec" class of normalization bugs.

In the report state:
- exact shared helper/module reused;
- whether any new alias was added;
- why any addition was necessary.

12. ARCHITECTURE

Prefer a shared service/module conceptually like:

shared/roadGeometry.ts
or
shared/geometryQuantityEngine.ts

Use naming consistent with the codebase.

It should NOT depend on React/UI.

Its inputs should be physical geometry + BOQ item metadata.

Its output should be deterministic and testable.

Keep this engine separate from `quantityResolver.ts` for this batch if that reduces risk.

Do NOT yet change the resolver's production calculation basis.

Later, Geometry can plug into the resolver as an alternate calculation basis.

13. DATA MODEL / SCHEMA

A small schema addition IS acceptable in this batch because geometry inputs are persistent physical project facts.

The new project-level geometry data must live in its OWN geometry/profile table or similarly isolated structure.

Do NOT:

- add these project-level typical-section fields to `work_program_bars`;
- repurpose `plannedWidthM`;
- repurpose `plannedThicknessMm`;
- use per-bar planning fields as project design geometry storage.

These are two distinct concepts:

A. Project-level typical/design geometry
B. Per-stretch/per-bar planning or actual width/thickness

Keep them structurally separate.

Prefer:

one project-level road geometry/profile record

with only the necessary Batch-01 inputs.

If layer data is cleaner as child rows, keep the model simple and extensible.

Do not add:
- calculated geometry quantity columns to BOQ items
- eligibleQty storage
- noScopeQty storage
- programmeQty storage

Calculated quantities must remain derived.

Before running any migration:
- inspect generated SQL;
- confirm it is additive only;
- no DROP TABLE / DROP COLUMN;
- no unrelated schema drift.

Report the migration before/after structure.
