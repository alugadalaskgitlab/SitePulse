--------------------------------------------------
OBJECTIVE
--------------------------------------------------
Fix the ambiguity between:
1. normal measurable BOQ work;
2. actual site work that happened but should NOT earn BOQ/RA progress credit;
3. genuinely no site work.

Also improve the current overlap-warning workflow so that:
- the exact conflicting DPR entries are visible;
- the user can open/edit the exact activity row;
- corrections can be made without losing chainage/location context;
- returning from DPR Edit brings the user back to the same Progress Report state;
- overlap status is recalculated after correction.

Do NOT redesign BOQ quantities, RA formulas, Work Programme sequencing,
Execution Arrangement, material receipts, equipment, or notifications.

Expected schema change:
Investigate existing progress_entries fields first.
A minimal additive field may be required for incidental/non-BOQ state.
STOP and report before migration if so.

--------------------------------------------------
1. CORE BUSINESS RULE
--------------------------------------------------
Every DPR progress/activity row must conceptually be one of:

A. BOQ WORK
Physical work was executed and is eligible to credit the linked BOQ item.
Examples: Clearing & Grubbing, Excavation, Embankment, GSB, WMM, DBM, BC.
Existing behavior.

B. INCIDENTAL / NON-BOQ WORK
Physical site work genuinely happened and must remain in the site record,
including where it happened, but it must NOT add BOQ progress / RA credit.
Examples:
- clearing vegetation that regrew after rains;
- cleaning already-cleared stretch;
- rectification/rework not payable as additional BOQ quantity;
- minor preparatory work outside measurable BOQ credit;
- other genuine work the Engineer wants recorded without claiming progress.

C. NO SITE WORK
No physical execution took place.
Examples: rain, site inaccessible, machinery breakdown, client stoppage,
no labour, shutdown.

These three concepts must never be conflated.

--------------------------------------------------
2. UI — INCIDENTAL / NON-BOQ WORK
--------------------------------------------------
Keep normal BOQ work as the DEFAULT. Do NOT introduce three large radio
cards or clutter every row. Add one compact optional control on
progress/activity rows:

    [ ] Incidental / Non-BOQ Work

Default: OFF.

When OFF: existing BOQ behavior remains exactly as today.

When ON: the row still represents ACTUAL SITE WORK. Therefore KEEP:
- BOQ/activity name or activity description;
- Side; From chainage; To chainage;
- Length; Width; Thickness where meaningful; Layer/Lift where relevant;
- Personnel; Equipment/context where existing;
- Photos; Remarks/description.

But: BOQ CREDIT = ZERO. The row must NOT contribute to current BOQ
executed quantity, cumulative BOQ progress, balance quantity, percentage
complete, or RA payable quantity. Do not delete its physical measurements.

--------------------------------------------------
3. INCIDENTAL LABEL / DISPLAY
--------------------------------------------------
When incidental is ON, show a clear compact tag:

    Incidental Work · No BOQ Credit

Example submitted DPR:
    Clearing vegetation after rains
    RHS · Ch. 2+900–3+050
    Incidental Work · No BOQ Credit

This must remain visible in Site Report / submitted DPR, DPR Edit, and
DPR History/revision where applicable. Do not hide the activity just
because it has zero BOQ credit.

--------------------------------------------------
4. INCIDENTAL DESCRIPTION
--------------------------------------------------
When Incidental / Non-BOQ Work is ON: require a short description/reason.
Examples: "Vegetation regrowth after rains", "Cleaning before WMM laying",
"Rework after edge damage".

Do not use the existing "No Site Work reason" field for this. The user
must be able to understand later WHAT work was actually done.

--------------------------------------------------
5. NO SITE WORK — CORRECT SEMANTICS
--------------------------------------------------
No Site Work must mean: NO PHYSICAL SITE EXECUTION.

When No Site Work is ON:
- do not treat the row as progress;
- no BOQ credit; no incidental-work credit;
- Side/From/To/Length/Width/Thickness/Layer are not required;
- require a reason/remarks.
Examples: Rain, Client stoppage, No machinery, Access blocked.

Do NOT use No Site Work for "Clearing vegetation after rains" if clearing
actually happened. If physical work happened, use BOQ Work or Incidental
Work.

--------------------------------------------------
6. MUTUAL EXCLUSIVITY
--------------------------------------------------
A row cannot be both No Site Work = true and Incidental Work = true at
the same time. If the user turns on Incidental Work, ensure No Site Work
is OFF; if the user turns on No Site Work, ensure Incidental Work is OFF.

Do not silently destroy entered physical measurements when toggling
between states during editing. If values become temporarily hidden,
preserve them in row state until save or explicit clear.

--------------------------------------------------
7. EXISTING SUBMITTED BOQ ROW → INCIDENTAL
--------------------------------------------------
If an already-saved/submitted BOQ progress row currently contributes BOQ
credit, and the user edits it and changes it to Incidental / Non-BOQ
Work, show an explicit confirmation:

    This activity currently contributes <X UOM> to BOQ progress.
    Marking it Incidental will remove that quantity from BOQ/RA progress
    while keeping the physical work record and chainage.
    [Cancel]  [Mark Incidental]

Do not silently remove BOQ credit. After confirmation, save normally
through the existing DPR edit/revision workflow.

--------------------------------------------------
8. INCIDENTAL → BOQ WORK
--------------------------------------------------
If an incidental row is later corrected back to normal BOQ work, run all
normal BOQ validation again: BOQ item, chainage, quantity, conversion,
overlap, layer/lift, readiness. Do not simply start crediting it without
validation.

--------------------------------------------------
9. CREDIT / REPORT CALCULATION
--------------------------------------------------
Investigate the canonical BOQ-credit calculation in
`shared/progressReport.ts`, `entryBoqCredit(...)`, and the cumulative
loops. Do NOT create separate report arithmetic. The canonical credit
function should return ZERO for an incidental row. Physical `quantity`
may remain stored for operational/reference purposes.

Example — incidental clearing: Length 150 m, Width 1.5 m, physical
calculated qty 225 sqm. Stored physical qty may remain 225. But BOQ
credited qty = 0. This preserves both what physically happened and what
is contractually claimable.

--------------------------------------------------
10. RA REPORT
--------------------------------------------------
Incidental work must NOT increase Previous Qty, Current Qty, Cumulative
Qty, RA payable quantity, or % Complete. But RA / supporting drill-down
may show it separately, for transparency:

    Incidental / Non-BOQ Work
    Clearing vegetation after rains
    RHS 2+900–3+050
    No BOQ Credit

Do not mix that quantity into the payable total.

--------------------------------------------------
11. PROGRESS REPORT (revised)
--------------------------------------------------
Default BOQ progress totals remain based only on credited BOQ work.
Incidental work may appear in activity/detail/drill-down as:

    Incidental Work · No BOQ Credit

Do not show it as unfinished BOQ quantity or contract progress.

(NEW) On the chainage coverage bar itself, an incidental-work stretch
must render with its OWN distinct marker — not the green used for
credited progress, and not the orange used for "needs review." Reusing
either would make the bar misrepresent what actually happened at that
chainage. A third, clearly-different treatment (e.g. a hatched/striped
segment with its own legend entry, "Incidental — no BOQ credit") is
sufficient; do not add a fourth state beyond what's needed to keep this
distinguishable from the other two.

--------------------------------------------------
12. OVERLAP ENGINE — INCIDENTAL BEHAVIOR
--------------------------------------------------
The chainage overlap engine should distinguish:
A. BOQ vs BOQ → existing overlap rules apply.
B. BOQ vs Incidental → do NOT create a BOQ-credit duplicate warning
   merely because the chainages overlap.
C. Incidental vs Incidental → no BOQ overlap warning required.

However, keep the records visible in physical/site-history detail.
Layer/Lift behavior from 06P remains unchanged: same BOQ + same chainage
+ different explicit layer = valid separate work. Do not weaken genuine
BOQ duplicate detection.

--------------------------------------------------
13. EXISTING OVERLAP REPORT — SHOW EXACT CONFLICT
--------------------------------------------------
The current Progress Report can flag "3 possible overlaps" but clicking
it does not make the correction clear. Replace/improve this with an
Overlap Review detail. For every overlap pair show: Activity/BOQ Item,
DPR No., DPR Date, Side, From chainage, To chainage, Layer/Lift where
applicable, Credited Qty, and the existing overlap override reason if any.

Example:
    DPR-249 · 30-May · Clearing & Grubbing · RHS · 2+600–3+100 · Qty 0.125 Ha
    overlaps
    DPR-266 · 08-Aug · Clearing & Grubbing · RHS · 2+900–3+050 · Qty 0.023 Ha

Make the physical overlap segment visible: "Overlap: RHS · 2+900–3+050".

--------------------------------------------------
14. OVERLAP REVIEW ACTIONS (revised)
--------------------------------------------------
For each conflicting entry provide: View DPR, Edit Activity.

"Edit Activity" must deep-link to the EXACT activity row (see §15). Do
not open the user at the top of a long DPR and make them hunt for it.

Also support the existing valid-overlap mechanism: "Both are valid".

(NEW) The reason for "Both are valid" must be captured from a short,
fixed pick-list, not free text — this feeds an audit trail and must stay
queryable/consistent:
    - Different layer/lift
    - Vegetation regrowth / repeat clearing
    - Re-measurement after approved correction
    - Genuine separately payable repeated operation
    - Other (free text — used only when none of the above genuinely fit)
This REPLACES free-form `chainageOverrideReason` entry for this specific
flow; the field itself does not change, only how it is captured here.

(NEW) When "Both are valid" is confirmed, the SECOND (chronologically
later) entry must default to Incidental / Non-BOQ Work, not to full BOQ
credit — unless the user takes one additional, deliberate action ("Credit
this as separately payable BOQ work") to keep it as full BOQ credit. The
safe default must never be "both are fully paid" without an explicit,
separate confirmation, since that is exactly the double-payment risk this
batch exists to close.

Do not automatically accept overlap merely because a reason exists.
Preserve current Final Submit readiness semantics.

--------------------------------------------------
15. DEEP-LINK TO EXACT DPR ROW
--------------------------------------------------
Implement a stable navigation target for a specific progress entry.
Prefer an existing progress-entry id if already available. Conceptually:

    /site/report/:dprId/edit?progressEntryId=<id>&returnTo=<encoded-report-state>

or equivalent existing routing convention. When Edit DPR opens: scroll
the exact activity row into view, visually highlight it briefly, and
optionally show "Opened from Progress Report overlap review". Do not
introduce a second edit page.

--------------------------------------------------
16. RETURN TO REPORT
--------------------------------------------------
When a user enters DPR/Edit from Progress Report / Overlap Review, show
"← Back to Progress Report". After Save / Cancel / Back, return to the
SAME report context. Preserve where practical: project/site, from date,
to date, selected BOQ item, measurement/chainage view, sorting, expanded
overlap item, and relevant scroll/section anchor. Do not send the user
back to generic Report Hub unless that is where they came from.

--------------------------------------------------
17. AFTER CORRECTION — RECOMPUTE
--------------------------------------------------
After a DPR correction saves successfully, invalidate/refetch the
relevant Progress Report / overlap data. If a duplicate row was
corrected, deleted/cancelled, changed to incidental, or given a valid
different layer, the overlap warning count must update. Do not leave a
stale "3 possible overlaps" until logout/reload — confirmed on video that
today it does exactly that.
