=====================================================================
PART A — "View" must mean page access, and nothing else may grant it
=====================================================================
Today `sectionVisible` (client/src/lib/auth-context.tsx:156-160) returns true if ANY of view, create, edit, delete, view_reports, export or approve is set. So a page opens when only Create is ticked, while the screen greys those cells and says "Not used for this section". This single function is why the audit reports 361 HIDDEN cells.

A1. FIRST, AND BEFORE CHANGING ANYTHING: compute and report the lockout list. For every user and every section, list the cases where the user would LOSE page access under the new rule — that is, `view` is false but at least one of create/edit/delete/view_reports/export/approve is true. Report the count and the full list. Do this for the development database, and state clearly that production is not covered.

A2. For every pair on that list, SET `view = true` for that user and section. This is additive only: no other bit changes, nothing is revoked, and nobody loses access they have today. Record every row you changed in an audit entry. If the list is empty, say so.

A3. THEN change `sectionVisible` to read `view` alone. Notify never grants entry.

A4. The `gated(...)` and `gatedEither(...)` route wrappers in client/src/App.tsx keep working as they do — they decide WHICH sections open a page. This part only changes WHICH BIT within a section counts.

A5. Hub rows are the deliberate exception and stay as they are: the Hub tables show one "Access" column, and that is honest. Do not turn hub rows into seven columns.

=====================================================================
PART B — The grey/active map must come from the code, not from a hand-kept list
=====================================================================
`SECTION_ACTIONS` in client/src/pages/UserManagement.tsx (~line 85) is hand-maintained and decides which cells render tickable. Nothing keeps it in step with what the code enforces, which is how it drifted.

B1. Generate it instead, from the same analysis `scripts/permission-audit.ts` already performs. The map that drives the screen and the map the audit produces must be the same artefact, checked in, regenerated by running the script.
B2. Add a test that fails when the checked-in map and a fresh run of the audit disagree. That is what stops this drifting again.
B3. A cell renders tickable if and only if the code reads that (section, action). Everything else renders grey.

=====================================================================
PART C — Labels and tooltips must describe the real effect
=====================================================================
From the audit's B5 section. Fix the words, not the behaviour:

C1. "Reports" actually controls EXPORT in ReportExportGate (client/src/components/ReportExportGate.tsx:8 reads `view_reports`). Either rename the column for those sections or correct the tooltip — say which you chose and why.
C2. "Edit" also authorises DELETE and CANCEL (server/auth-routes.ts:1076-1077, `assertDeleteOrCancel` delegating to `assertEdit`). The tooltip must say so.
C3. "Approve" gates different real actions by section — issue, reject, close, verify. The tooltip for each section must name the actual action, from the route evidence in the audit.
C4. IRN approval reads the CREATE bit (client/src/pages/irn/IrnDetailPage.tsx:81). Say so in the tooltip.
C5. Every tickable cell gets a tooltip in plain words: what the person can do if it is ticked. No cell is left with no tooltip.
C6. PAIRED CHECKS: the audit lists ~35 multi-section OR gates (`gatedEither`, `assertEditEither`, `assertCreateEither`). Where two or more cells OR together, the tooltip on each must name the others — "this page also opens if <other section> is granted" — so the screen stops hiding the connection.

PART F — Six templates grant Create without Edit
=====================================================================
`buildTemplateMatrix(viewCreate, approveSections, editSections)` grants edit only for sections passed in the third argument, which most templates never use. A site engineer can file a DPR and cannot correct his own typo.

F1. For every template, grant `edit` on every section where it grants `create`. A person who may enter a record may correct it.
F2. Do NOT change delete, approve, export or notify on any template.
F3. Templates apply to NEW grants only. Do not re-apply any template to an existing user — nobody's current permissions change because of this part.
