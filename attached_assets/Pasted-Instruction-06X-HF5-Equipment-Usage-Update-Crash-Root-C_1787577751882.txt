The real root cause has now been found and independently reproduced outside

ROOT CAUSE (verified, reproducible in isolation)

client/src/pages/PlantEquipmentUsage.tsx, in the "Send to Site" branch of
handleSubmit() (around line 544), sets:

  openedAt: new Date().toISOString(),

This travels to the server as JSON, so by the time it reaches
server/routes.ts and server/storage.ts, req.body.openedAt is a plain
STRING (e.g. "2026-08-24T10:41:10.670Z") — JSON has no Date type, this is
unavoidable and correct on the client side.

The problem is server-side: server/storage.ts's _updateEquipmentUsageTxn
(~line 4587) and _createEquipmentUsageTxn (~line 4387) both do:

  await tx.update(equipmentUsage).set({ ...usage, ... })   // update
  await tx.insert(equipmentUsage).values({ ...usage, ... }) // create

usage.openedAt (a string) is passed straight through to Drizzle untouched.
shared/schema.ts defines:

  openedAt: timestamp("opened_at"),

This is Drizzle's default DATE-mode timestamp column, whose driver-value
encoder is (verified directly in node_modules/drizzle-orm/pg-core/columns/
timestamp.ts):

  mapToDriverValue = (value: Date): string => value.toISOString();

It assumes `value` is already a Date object and calls `.toISOString()` on
it. A string has no such method, so this throws:

  TypeError: value.toISOString is not a function

This is a genuine unhandled exception — not a ZodError, not an
insufficient-stock error, and its message contains neither "closing" nor
"reading" — so it falls straight through to the generic 500 in the PUT
route's catch block (server/routes.ts ~line 3957) and the equivalent POST
catch block (~line 3928). This matches the reported symptom exactly.

This is NOT specific to the diesel-source change 06X-HF4 targeted. It
fires any time openedAt (or any other client-supplied date/timestamp
value) reaches a Drizzle date-mode timestamp column as a string. Today,
openedAt is the only such field sent by the client, and it is only sent
when Send to Site is turned on — which is exactly the action in every one
of Sunil's reproductions.

VERIFICATION ALREADY DONE (do not repeat — use as given)

Ran this directly against your actual shared/schema.ts column definition,
with the exact string shape the client actually sends:

  const col = equipmentUsage.openedAt;
  const parsed = JSON.parse(JSON.stringify({ openedAt: new Date().toISOString() })).openedAt;
  col.mapToDriverValue(parsed);
  // → TypeError: value.toISOString is not a function
  //   at PgTimestamp.mapToDriverValue (drizzle-orm/pg-core/columns/timestamp.ts)

REQUIRED FIX

In server/storage.ts, normalise any client-supplied date/timestamp fields
to real Date objects before they reach Drizzle's .set()/.values() calls.
Minimum scope — fix both _updateEquipmentUsageTxn and
_createEquipmentUsageTxn:

    ...usage,
    ...(usage.openedAt !== undefined && {
      openedAt: usage.openedAt ? new Date(usage.openedAt as any) : null,
    }),
    ...(usage.closedAt !== undefined && {
      closedAt: usage.closedAt ? new Date(usage.closedAt as any) : null,
    }),
  };

  // then spread ...normalisedUsage instead of ...usage in both the
  // .set({ ...normalisedUsage, ... }) and .values({ ...normalisedUsage, ... })
  // calls.

Search the whole file for every place equipmentUsage rows are written
(insert or update) and confirm none of them spread a raw client `usage`
object containing openedAt/closedAt without this normalisation — do not
fix only the one call site and miss a duplicate.

Also check whether any OTHER route in server/routes.ts ever sends
openedAt/closedAt (or any other timestamp-mode column) as part of a
request body reaching a Drizzle write — grep for "timestamp(" in
shared/schema.ts to get the full list of date-mode timestamp columns
(openedAt, closedAt, unlockedAt, createdAt, and any others), then grep
each column's write paths for the same unguarded-string risk. Report what
you find even if you conclude no other path is affected — do not assume.

DO NOT invent a broader refactor (no generic "deep-normalise all Date
fields" utility, no ORM-wide interceptor) — fix exactly the columns and
call sites identified above. Keep this narrow.

PART 3 — Overlap Review Classification Has No Authority Check (Permission Gap)

BACKGROUND

While blocked by Part 2's bug, a Foreman-level user (Dinesh Singh) used the
Overlap Review flow to mark two rows on his own DPR (EMBANKMENT - EXCAVATED
EARTH and CLEARING AND GRUBBING, DPR: Takkadpally-Sirur, 08 Aug 2026) as
"Incidental / Non-BOQ", which let the DPR save by exempting those rows from
the overlap-reason requirement — but this ALSO removes BOQ credit for that
work entirely (confirmed: "Done" stays 0 against the planned quantity even
with qty entered). This is a real, unwanted side effect for genuine billable
work, and Sunil has confirmed a Foreman should never have had the authority
to make this classification call in the first place — it should require the
same kind of review authority as approving an override reason, not ordinary
DPR-editing rights.

CONFIRMED IN CODE

PATCH /api/progress-entries/:id/overlap-resolution (server/routes.ts ~line
1701) — which handles ALL THREE Overlap Review actions (marking a row
Incidental, providing a chainageOverrideReason, and layer correction) — is
gated only by:

  if (!assertEdit(req, res, "site_dprs")) return;

This is the exact SAME permission check used for ordinary DPR field entry
(readings, quantities, personnel, etc.) — there is no separate, distinct
authority check for Overlap Review classification specifically. Any user
with edit rights on their own DPR can reclassify a row as Incidental
(losing BOQ credit) or supply an override reason, with no higher-authority
review step, even though this is meant to be a review/approval action
distinct from routine field data entry.

shared/permissions.ts already implements a granular, per-section,
individually-grantable permission model (see the "site_dprs" section and
surrounding structure) — reuse this existing pattern, do not invent a
parallel role/hierarchy system. There is no "Foreman" role construct in
the permission system today — role titles like "FOREMAN" are free-text
labels only, not access-control tiers — so the fix must be a new,
separately-grantable permission, not a hardcoded title check.

REQUIRED FIX

1. Add a new, distinct permission (e.g. "site_dprs_overlap_review" or
   similar, matching the existing naming convention in
   shared/permissions.ts) that specifically gates the Overlap Review
   actions (isIncidental, chainageOverrideReason, layerNo) on PATCH
   /api/progress-entries/:id/overlap-resolution. Ordinary DPR field entry
   (readings, quantities, etc.) must be unaffected — this permission gates
   ONLY the overlap-resolution endpoint's three actions.
2. This new permission must default to OFF for all existing users — it
   must be explicitly granted per-user by an Admin, the same way other
   granular permissions in this app already work. Do not auto-grant it to
   any existing role/title.
3. On the client, hide or disable the "Give reason" / "Mark Incidental"
   controls in ChainageOverlapGuard.tsx (and wherever else Overlap Review
   actions are exposed) for a user who lacks this permission, and show a
   clear message (e.g. "Overlap review requires engineer/manager
   approval — ask your site engineer to review this row") rather than a
   raw permission-denied error.
4. Confirm the User Management / permissions screen lets Sunil grant this
   permission per-user, consistent with how other section permissions are
   already managed there.
