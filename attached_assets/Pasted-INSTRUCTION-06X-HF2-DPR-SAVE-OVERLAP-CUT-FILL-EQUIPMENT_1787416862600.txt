1. DPR ACTIVITY FILTER — SCARIFYING / HISTORICAL DPRS MISSING
============================================================

REPRODUCED CONCERN

Existing DPRs contain work such as Scarifying Existing BT, but the Site DPR
Activity filter does not reliably show/find them.

CURRENT CODE ISSUE TO CONFIRM

SiteDashboard currently builds uniqueActivities from raw:

  dpr.progress[].activity

and filters by exact text equality:

  p.activity === filters.activity

This is fragile because the same BOQ activity may exist historically with:
- different case;
- old free-text name;
- full imported BOQ description;
- newer short BOQ display name.

FIX

For BOQ-linked progress rows:

- activity filtering must use boqItemId as the canonical identity;
- filter options should show the canonical current short BOQ item name;
- all DPRs with that same boqItemId must match regardless of stored activity
  text.

For legacy progress rows with boqItemId = null:

- retain a normalized text fallback;
- compare trimmed/case-insensitive normalized activity text;
- do not lose old free-text DPRs.

Do NOT rewrite historical activity descriptions merely to make filtering work.

Verify specifically the known Scarifying Existing BT DPRs:
- identify the DPR ids/dates;
- identify whether they have boqItemId;
- prove they appear when the Scarifying activity filter is selected.

Also verify Site/date/Engineer filters do not accidentally suppress them.

GUIDED DPR NOTE

Do not confuse the Site Dashboard Activity filter with Guided DPR
"Today's likely activities".

Today's likely activities remains programme/date based:
- programme bars covering selected date;
- minus already reported bar ids.

But "+ Add Activity" must always allow selection from the project's BOQ items,
including Scarifying, even if it is not planned for that date.

2. ONE CANONICAL CHAINAGE OVERLAP RULE EVERYWHERE
============================================================

Use ONE shared overlap semantic for:

- new DPR final submit;
- draft -> final submit;
- submitted DPR edit/version;
- Guided DPR advisory;
- Detailed DPR advisory;
- Progress Report badge;
- Progress Report Overlap Review.

Rules:

- same BOQ item;
- actual intersecting chainage only;
- endpoint touching is NOT overlap;
- side aware:
    LHS vs RHS = no overlap;
    Both Sides / Full Width may overlap applicable sides;
    unknown remains conservative;
- layer/lift aware:
    if BOTH entries have explicit non-null layerNo and differ = no overlap;
    null retains legacy conservative behavior;
- No Site Work excluded;
- Incidental / Non-BOQ excluded.

Do not maintain a second slightly different implementation in progressReport.ts.

Prefer a shared pair comparator/helper so DPR and Reports cannot drift again.

============================================================
3. EXISTING DPR EDIT MUST NOT BE BLOCKED BY UNCHANGED HISTORY
============================================================

Current production symptom:

User opens an existing submitted DPR to correct equipment/remarks/etc.,
then Save/Submit is blocked by an old possible overlap in an unchanged
progress activity.

Required behavior:

When editing an existing submitted DPR:

- compare persisted progress rows against the edited payload;
- if BOQ item, From, To, Side, Layer/Lift, Incidental status and overlap/credit
  classification did NOT change, do NOT create a new mandatory overlap blocker
  merely because equipment/labour/remarks/photos changed;

- new progress rows must receive normal overlap validation;
- changed overlap-relevant fields must receive normal overlap validation.

Do NOT weaken validation of new/changed progress claims.

If a real blocking activity remains:
- identify exact activity;
- side;
- from/to;
- layer;
- other DPR/entry;
- overlap segment;
- scroll/highlight the exact row.
