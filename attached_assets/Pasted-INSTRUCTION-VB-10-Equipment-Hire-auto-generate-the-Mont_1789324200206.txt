BACKGROUND / DESIGN DECISIONS CONFIRMED BEFORE BUILDING

After VB-09 lands, creating any vendor bill — Equipment Hire included — works the same simple way: pick vendor + period, the app pulls what was actually logged, you review it, done. This batch adds exactly one thing on top of that, for monthly-basis equipment only, and it is fully automatic — no button, no manual calendar-marking step, no separate flow to choose between.

The rule: Equipment Master's hireBillingBasis is the single source of truth for how a machine is billed. If it says "monthly", the machine's entire hire is billed as monthly for the bill period — there is no mid-period splitting between monthly and daily/hourly in this batch (explicitly descoped — if a machine's basis genuinely changes mid-hire, that's handled by editing Equipment Master's hire terms for future bills, not by the bill itself detecting a split). If a vendor has one monthly machine and one daily/hourly machine, the bill produces one auto-generated Monthly Hire line for the first and ordinary itemized lines for the second, in the same bill, automatically — because each machine's own Master record determines which path it takes, with no manual sorting by the person creating the bill.

The data this pulls from, already confirmed to exist:
- client/src/pages/SiteEntry.tsx and PlantEquipmentUsage.tsx already tag every equipment log entry with an entryType (time_meter/hourly/daily/trip_based/monthly) and already capture breakdowns per entry via BreakdownStoppageEditor (feeding the maintenance log, eventType "breakdown"). This is real, logged activity — use it as the activity calendar, do not have the bill re-ask the user to mark days.
- shared/hireBilling.ts already has the monthly proration math (monthlyGross, monthlyDailyRate, using hireMonthlyDivisorType/hireMonthlyDivisor from Equipment Master) and the breakdown-deduction logic (breakdownHoursPerDay, hireBreakdownDeductionEnabled) — reuse this engine as-is, do not rewrite the math. The earlier "hire groups" UI that called this engine is what VB-09 removes; the engine itself stays in the codebase untouched, per VB-09's Fix 2a.
- DIESEL-01 makes opening/closing tank balance mandatory for plant_stock diesel and keeps diesel-issued loggable (as a recoverable advance) under contractor scope. This batch is what actually uses that data.

An unresolved day, for a monthly machine, still counts as billable by default. Monthly hire means "the machine was available to you," not "the machine was used that specific day" — so days inside the machine's active hire dates within the bill period are billable unless there's a positive record saying otherwise (a logged breakdown). A missing DPR entry on a monthly machine must NOT silently reduce the bill, unlike daily/hourly billing where an unlogged day naturally isn't billed.

FIX 1 — AUTO-DETECT AND SPLIT BY BILLING BASIS WHEN A VENDOR IS SELECTED
a. When vendorName + periodFrom + periodTo are set on an Equipment Hire (or All Types) bill, for each of that vendor's hired equipment (ownership === "hired", vendorName matches): read hireBillingBasis from Equipment Master.
b. If hireBillingBasis === "monthly": route this machine into Fix 2 below (auto-generate one Monthly Hire line). Do not surface it in the itemized pull as individual daily/hourly rows.
c. If hireBillingBasis is daily/hourly/trip: this machine's usage flows through the itemized pull exactly as VB-09 restores it — no change from that batch's behavior.
d. This must work per-machine, independent of what other machines from the same vendor are doing — a vendor with 3 machines (1 monthly, 2 hourly) produces 1 auto-generated line + itemized rows for the other 2, all in the same bill, automatically.

FIX 2 — AUTO-GENERATE THE MONTHLY HIRE LINE
For each monthly-basis machine identified in Fix 1:
a. Determine the billable date range: the overlap between the machine's active hire dates (hireStartDate/hireEndDate) and the bill's periodFrom/periodTo.
b. Build the activity calendar for that range from equipmentLogs entries (any entryType) plus the maintenance log's breakdown entries for this equipment in that range — this is a read-only summary showing which days were logged as active and which had a breakdown, for transparency and audit, not something the user builds by hand.
c. Every day in the billable range counts as billable by default. Only days with a linked breakdown event reduce the bill, and only for the portion beyond whatever grace period / breakdownHoursPerDay rule is already configured (hireBreakdownDeductionEnabled must be on for this machine, same as today's gating).
d. Compute Gross using the existing monthlyGross function (full rate for a complete period, prorated via hireMonthlyDivisorType/hireMonthlyDivisor for a partial one). Compute the breakdown deduction using the existing monthlyDailyRate-based logic. Do not reimplement this math — call the existing shared/hireBilling.ts functions.
e. Render the result as one line item in the same bill (category "equipment", same table every other item sits in), with the underlying calendar available to expand/inspect (so the person preparing the bill can see and, if genuinely necessary, override an individual day's breakdown status before finalizing — this is a correction mechanism for exceptions, not the primary way of entering data).

FIX 3 — DIESEL RECONCILIATION FOR HLC-SUPPLIED MONTHLY MACHINES
a. Only when this machine's hireDieselResponsibility === "hlc": compute Expected = consumptionNorm (in the machine's own unit, L/hr or L/km per meterType, same figure Equipment Performance already shows) × total hours/km actually logged across the billable range (from equipmentLogs entries, any entryType — this reflects real usage regardless of billing basis).
b. Compute Actual using the DIESEL-01 data: opening tank balance at the start of the billable range + diesel issued (dieselSource === "plant_stock") during the range − closing tank balance at the end of the range. Use this proper reconciliation, not a plain sum of diesel-issued entries, now that DIESEL-01 makes tank balance mandatory for plant_stock entries.
c. Surface Expected vs Actual and the resulting suggested recovery using the same Accept/Edit/No-Recovery mechanism already built for diesel recovery elsewhere in this file — reuse it, do not build a second one.
d. When hireDieselResponsibility === "vendor" (contractor scope): no Expected/Actual reconciliation block (there's nothing for HLC to reconcile against its own stock). Instead, per Fix 4.

FIX 4 — SURFACE CONTRACTOR-SCOPE DIESEL ADVANCES AS A RECOVERABLE DEBIT
a. For ANY hired equipment belonging to the selected vendor in the bill period — monthly or daily/hourly/trip, this is not limited to monthly machines — check for equipmentLogs entries where dieselSource === "contractor" and diesel > 0 (these are the advances DIESEL-01 makes possible to log). If any exist in the bill period, surface them as a suggested "Other Debit / Recovery" adjustment on this vendor's bill (using the existing adjustments.otherDebit field already in the hire calculation structure), with a clear reason string identifying it as a diesel advance (e.g. dates and quantities), pre-filled but editable/removable by the person preparing the bill — never silently applied without them seeing it.
b. This must appear regardless of whether the equipment it was logged against is billed monthly (Fix 2) or itemized (VB-09's flow) — the advance recovery is about the vendor's bill as a whole, not tied to one billing basis.

- Do not let a missing DPR entry on a monthly machine reduce the bill — only a logged breakdown should.
- Do not rebuild the monthly proration or diesel-recovery math — reuse shared/hireBilling.ts and the existing recovery-decision UI as-is.
