BACKGROUND (confirmed by direct code review — do not re-derive)
Three separate, confirmed issues, found while reviewing why an owner's own scope decisions were not being respected by the schedule, and why BOQ item names display badly.

1. THE REACH ITEM-APPLICABILITY BUG (the important one)
On the Work Programme "Scope Reconciliation" screen, a "Working Reach" record (e.g. "REACH 1") has an "Applies to: Only selected items" checklist where the user ticks/unticks which BOQ items apply within that reach. The owner unchecked "Forming Embankment with material" (and the culvert/structure items) for Reach 1, since that work genuinely does not occur there. This selection IS saved to the reach record (`project_scope_segments`, `itemIds`/`applicability`).
However, the central scope resolver, `segmentAppliesToItem()` in `shared/projectScope.ts` (~line 178), has this:
```
if (seg.segmentType === "working_reach") return true; // reaches define WHERE work happens for everyone
```
A `working_reach` segment is treated as applying to every item unconditionally — its own `itemIds`/`applicability` selection is never consulted. Meanwhile, the SAME eligibility/redistribution machinery (`resolveEligibleScope`/`coverageForStretch` in `shared/projectScope.ts`, wired into `generateSequencedProgramme` via the `scopeCoverage` callback, `server/routes.ts` ~line 18483) already works correctly for `no_scope`, `temporary_block`, and `withdrawn` segment types — it correctly clips bars and (per that existing logic) computes quantity distribution only over the eligible stretch. So the mechanism to do this right already exists and is proven; a `working_reach`'s own item checklist is simply never routed through it.
Net effect: the owner's explicit "this item doesn't apply here" answer is silently ignored, and embankment (and other unchecked items) still gets spread proportionally into Reach 1 as if the whole corridor were uniform.

2. THE BOQ IMPORT LINE-FRAGMENTATION BUG
Separately, many BOQ item descriptions in the current import are showing as multiple broken fragments instead of one item — e.g. a single real item is showing as five separate checklist rows: "earthen shoulder", ", spreading and", "applying primer", "applying tack", "50" (plus some entirely blank rows), instead of one full, correctly-worded item. Root cause, confirmed in `client/src/components/BoqImportWizard.tsx`, `parsedItems` (~lines 206-305): the importer reads the Excel sheet strictly one physical row at a time and treats every row that has no item code as a new "sub-item" of whatever came before it. Real BOQ sheets commonly wrap one long clause across several physical Excel rows (via manual line breaks/merged cells) with only the last line carrying the unit/quantity — the importer has no logic to merge those continuation rows back into a single description, so each wrapped line becomes its own bogus, fragment-only BOQ item. This is why some fragments are blank, why some are lowercase mid-sentence pieces, and why identical continuation text can appear duplicated under two different parent items.

3. RAW, UNCLEANED DISPLAY NAMES
Even for correctly-imported single-row items, screens display the raw imported description verbatim — e.g. a long sentence starting in lowercase — rather than a clean, readable name. WP-02 already built deterministic identity-matching/classification against the SNL/SDB libraries for auto-mapping; that same intelligence is not currently used to also produce a better display name.

Be explicit, not a blind copy of exclusion-segment handling:

   - `applicability = "categories"` → the reach applies ONLY to the listed `categoryIds`.

PART 2 — FIX THE BOQ IMPORT LINE-FRAGMENTATION BUG
Reconstruct LOGICAL BOQ items before creating `parsedItems` — a physical Excel row is not automatically a new BOQ item.
1. Use genuine item-boundary evidence to start a new logical item: a new item/serial/code value, a recognized Bill/Section marker, or another existing importer rule that conclusively starts a new BOQ item. Rows without a new-item boundary continue the description of the CURRENT logical item and must be appended to it, not turned into a new item.
2. IMPORTANT — this corrects an internal contradiction in an earlier draft of this instruction: the presence of a UOM and/or quantity on a row must NOT by itself start a new item. A continuation row is very often exactly the row that carries the UOM/quantity completing the current logical item (e.g. the clause's description spans two blank-code rows, and the third row has no new item code but does carry "CUM | 500" — that row still completes and belongs to the SAME item as the two rows before it, not a new one). Boundary detection must be based solely on genuine new-item evidence (point 1), never on whether a row happens to carry a unit/qty.
3. Never merge across a genuine next-item, Bill, Section, or other recognized source boundary.
4. Preserve source Bill/Section, source Item No., original first-row position and ordering for the reconstructed logical item.
5. Skip rows that are only whitespace/empty after trimming entirely — never create a blank-labeled item.
6. This is a fix to the importer for FUTURE imports. Do not attempt to auto-repair already-imported, already-fragmented ALLADURG items in this batch — the owner is separately planning to rebuild that import file from the original tender document and re-run it through the (now fixed) importer. Confirm this scope boundary explicitly in your report.

PART 3 — CANONICAL, CLEAN BOQ DISPLAY NAMES
1. Keep the full original imported description intact and always accessible (e.g. in an item detail view/tooltip) — this remains the contractual record. Never lose or alter it.
2. Add a separate, derived "display name" shown on normal list/programme/DPR screens wherever the item name currently renders. A canonical display label may be used ONLY when it comes from a deterministic/exact WP-02 identity match, or a mapping the user has manually confirmed — call it a "canonical concise display label where a reliable canonical label exists," not a guaranteed short name (the canonical source's own label is not always short). Do NOT promote an ordinary fuzzy-match suggestion into the displayed item name merely because its confidence score is above some threshold — an unconfirmed fuzzy match must never be shown as if it were the authoritative item name, since that risks turning a messy-but-correct description into a clean-looking WRONG one.
3. Where no exact/deterministic or manually-confirmed canonical label exists, fall back to a cleaned version of the raw description rather than the raw text verbatim: capitalize only the first letter of the first meaningful word, and leave the rest of the sentence's casing as imported. Do NOT apply Title-Case-Every-Word — that would corrupt technical abbreviations. Preserve known technical abbreviations exactly as written wherever they appear in the sentence, not just at the start (e.g. RCC, PCC, NP4, DBM, BC, WMM, GSB, M15, and similar grade/class codes already recognized elsewhere in the app's classification/matching logic) — do not lowercase or re-case them.
4. This display-name change is presentation-only — it must not alter the stored `description` field, any matching/classification logic, quantities, or BOQ Bill/item ordering.
