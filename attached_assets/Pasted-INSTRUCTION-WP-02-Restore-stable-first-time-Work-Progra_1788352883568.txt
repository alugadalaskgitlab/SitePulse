PART 1 — RESTORE FREE MANUAL EDITING FOR FIRST-TIME PROGRAMME PLANNING
Problem: Every edit to a programme bar's start date, end date, or duration currently triggers the mandatory "Schedule Revision" workflow (requiring a typed reason and going through a revision-preview/apply flow), even on a brand-new project that has never been baselined and has zero actual progress recorded. This did not happen a few days ago — bars could be dragged/edited directly. This is a real regression introduced when the revision-protection feature was added, and it is separate from anything in WP-01.

Required fix:
1. Add a check before requiring Schedule Revision: if the project (or the specific programme) has not yet had a baseline explicitly published/frozen, AND the bar being edited has no recorded actual progress (no execution/outcome events), allow the start date, end date, duration, and manual/auto mode fields to be edited directly — no revision required, no reason required.
2. Once a baseline has been explicitly published for that programme, restore the current behavior: any further edit to those fields requires the Schedule Revision flow with a reason, exactly as it does today.
3. There is currently no "baseline published" concept in the schema. Add the smallest possible additive field to represent it (e.g., a nullable timestamp/flag on the programme or project record indicating whether a baseline has been published, defaulting to "not published" for all existing projects). Do not remove or repurpose any existing field. If this requires a schema change, stop and show me the exact change before writing any migration, per our usual schema-safety rule.
4. Do not build the full Draft/Baseline/Revision lifecycle UI here (that is a separate, larger piece we are deliberately holding for later). This part is only: unlock free editing pre-baseline, keep revision protection post-baseline.

Test: On the Takkadpally project (or any project that has never had a baseline published), confirm you can now drag/edit a bar's dates and duration directly without hitting the Revision workflow, exactly like the older behavior. On any project that already went through baseline publishing (if one exists), confirm Revision is still required. Show me both results.

PART 2 — MAKE AUTOMATIC MAPPING THE DEFAULT, NOT THE EXCEPTION
This is the most important part of this instruction. Right now the Mapping Review screen is showing far too many items as uncertain, including very ordinary, standard road and culvert items that any experienced engineer would recognize instantly (WMM, DBM, BC, tack coat, prime coat, embankment, subgrade, PCC, Hume pipe culverts, kilometre stones, sign boards, thermoplastic road marking, crash barriers, rumble strips, reflective studs, etc.). These are not unusual or ambiguous items — they are standard MoRTH/IRC-specification items that appear in virtually every road tender BOQ in the country. The app should recognize them with confidence and map them automatically, without asking the user.

Required approach:
1. First, investigate and report back: how many distinct SNL/SDB standard-item libraries or sources currently exist in the app (for example: the MoRTH SDB library seeded in the last batch, and any other standard-item source tables or seed files you find in the codebase)? List them by name/table and item count before changing anything. If there is currently only one library, say so plainly — do not invent additional libraries that do not exist in the code.
2. For whichever standard-item library/libraries exist, build a small set of deterministic, identity-based matching rules for the common, unambiguous item families listed above (and any other equally standard, equally unambiguous families you find in the codebase's existing keyword/classification lists). "Deterministic" means: when a BOQ item's description, chapter/spec reference, and unit clearly identify it as one specific standard item (for example, a 1000mm NP4 RCC Hume pipe item with a pipe-laying description and RM unit), the app assigns that exact standard-item mapping directly, with high confidence, and does NOT send it to Mapping Review.
3. Reserve the fuzzy/scored matching (the existing 0.70/0.50 threshold logic) only for items that do not match any deterministic rule — i.e., genuinely unusual, poorly worded, or composite items. Mapping Review should end up showing only that leftover minority, not common items.
4. Apply the same "recognize the obvious, only flag the unusual" principle to equipment and labour/resource mapping (BOM/recipe mapping) wherever the same style of auto-suggestion exists in the app today — investigate and report what you find there before changing it, following the same deterministic-first approach.
5. Target stated by the client: roughly 85-90% or more of normal BOQ items in a standard road/culvert/furniture/safety BOQ should map automatically with zero user action. Mapping Review should contain only genuine exceptions — not become a second full mapping exercise for the user.
6. Do not loosen the existing fuzzy-matching confidence thresholds to force more items through as "mapped." That would hide real ambiguity instead of resolving it, and it is exactly the kind of shortcut we do not want. The improvement must come from recognizing obvious items directly, not from lowering the bar for uncertain ones.

Test: Re-run the existing ALLADURG mapping review (already documented in the last batch's report) and the Pampad-style test BOQ we discussed, and show me, before and after this change, how many items were auto-mapped vs. sent to review, with a couple of concrete examples (e.g., the 1000mm NP4 pipe item, the kilometre-stone item, the WMM/DBM/BC items).
