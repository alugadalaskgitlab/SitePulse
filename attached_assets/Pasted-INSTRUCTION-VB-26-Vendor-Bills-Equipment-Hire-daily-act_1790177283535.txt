2. `consumptionIncomplete` (`shared/equipmentPerformance.ts:550`) is `dieselConsumed == null`, and `dieselConsumed` is only computed when BOTH the opening and closing boundary readings for that day have `dieselBasis === "tank_measured"` (`equipmentPerformance.ts:513-520`), which in turn requires the entry's `dieselBalanceConfirmed` checkbox ("Physical Tank Balance Confirmed", `client/src/components/DprEquipmentCompact.tsx:294`) to be explicitly ticked — a manual confirmation, separate from whether Opening/Closing Tank numbers were actually entered. Confirmed live: a day with real 0L→8.5L tank readings still showed "Tank Readings N/A" because this checkbox wasn't ticked, even though the raw numbers display correctly elsewhere in the same row (`openingTank`/`closingTank` are populated unconditionally, `equipmentPerformance.ts:692-693`).
3. CONFIRMED BUG: `expectedDiesel` (`shared/equipmentUsage.ts:219`, computed purely from `consumptionNorm × runtime` — needs NO tank data at all) is nonetheless gated by the SAME `consumptionIncomplete` flag (`EquipmentHireBillOutput.tsx:168`, and again in the period-total summary at `:228`: `expectedDiesel: fuelIsContractorScope || item?.consumptionIncomplete ? null : item?.expectedDiesel`). 4. The "Actual Consumption | Master Norm" cell (`EquipmentHireBillOutput.tsx:146,155-157`) crams both the day's actual consumption RATE and the master's norm into one combined text cell, also fully suppressed by `consumptionIncomplete` — confirmed this is what the person found confusing ("what is actual consumed master norm").

The "Difference" column (`EquipmentHireBillOutput.tsx:146`, cell at `:90-91`/`169`, using `row.difference = dieselConsumed - expectedDiesel` from `equipmentPerformance.ts:547`, also surfaced as a "Total Variance" period total at `:262`/`:389-390` and in `DraftEquipmentHireCalendar.tsx:41`) — the person wants this removed entirely.
6. Status/Remarks (`EquipmentHireBillOutput.tsx:134-135`, rendered at `:171`) currently generates a generic `"Worked"`/`"No Work"` status and `"Activity recorded"`/`"No activity recorded"` remarks text. The actual task/work description IS already captured in the data model — each `EquipmentPerformanceEvent` has a `task` field (`equipmentPerformance.ts:150`, populated at `:681` from the DPR log/usage row), and the daily row retains the raw events at `events: orderedRows` (`equipmentPerformance.ts:576`) — it's simply never read into this display.
7. `meterType`-driven L/Hr vs L/Km unit selection (`shared/equipmentUsage.ts:211`, `equipmentPerformance.ts:549`) is already correctly implemented and working — confirmed NOT broken, no change needed there.

This fix applies uniformly across all equipment shown in this calendar.

FIX 1 — DECOUPLE EXPECTED DIESEL FROM THE TANK-CONFIRMATION GATE
a. In `EquipmentHireBillOutput.tsx` (~line 168) and the period-total builder (~line 228), stop gating `expectedDiesel` on `item.consumptionIncomplete`. Expected should render whenever `consumptionNorm × runtime` can be computed (i.e., the equipment has a norm set in its master and the day has runtime data) — completely independent of whether tank readings were confirmed that day.
b. Diesel CONSUMED (the actual, tank-based figure) should CONTINUE to correctly show "Tank Readings N/A" (or clearer wording, see Fix 3) when `dieselBalanceConfirmed` is false — this part of the gating is legitimate (an unconfirmed physical reading shouldn't be presented as a trusted actual figure) and must NOT be removed, only decoupled from Expected.
c. Confirm this fix applies correctly to both the per-day row and the period summary total for Expected.

FIX 2 — REMOVE THE DIFFERENCE/VARIANCE COLUMN
a. Remove the "Difference" column header and its per-day cell value from `EquipmentHireBillOutput.tsx` (~lines 146, 169).
b. Remove the corresponding "Total Variance" period-total line (~lines 262, 389-390 and `DraftEquipmentHireCalendar.tsx:41`).
c. Confirm no other part of the bill (e.g. HSD recovery suggestion logic used elsewhere in Vendor Bills) depends on this specific displayed value being present in this table — if the underlying `difference`/variance calculation is used elsewhere for a real purpose (e.g. feeding the recovery-suggestion feature), keep the underlying calculation intact and only remove it from THIS display.

FIX 3 — SPLIT "ACTUAL | MASTER NORM" INTO CLEAN SEPARATE COLUMNS
a. Replace the combined "Actual Consumption | Master Norm" cell with two separate, clearly labeled columns: "Diesel Consumed" (already exists as its own column per the screenshot, keep as-is, gated correctly per Fix 1b) and a new "Norm" column showing the equipment master's `consumptionNorm` value with its correct unit (L/Hr for hour-meter equipment, L/Km for odometer equipment — reuse the already-correct `meterType`-driven unit logic from `equipmentUsage.ts`/`equipmentPerformance.ts`, do not reimplement).
b. The Norm column should show the master's value regardless of tank confirmation status (it's a static master value, not a computed actual) — always visible when the equipment has a norm set.
c. If a consumption RATE (actual L/Hr or L/Km for that specific day, distinct from the master norm) is still considered useful to show, it may remain as part of the Diesel Consumed column's own gating (Fix 1b) rather than mixed into the Norm column — your judgment on the cleanest layout, but Norm and Actual/Consumed must be visually and logically separate columns, not combined text.

FIX 4 — SHOW THE ACTUAL LINKED ACTIVITY/TASK, NOT A GENERIC STATUS LABEL
a. In `buildBillingDailyRows()` (`EquipmentHireBillOutput.tsx` ~lines 134-135), replace the generic `remarks` value ("Activity recorded"/"No activity recorded") with the actual task/activity description(s) from that day's DPR entries — read from `performance.events[].task` (confirmed already populated, `equipmentPerformance.ts:150,681`). If multiple distinct tasks were logged for the equipment on the same day, join them clearly (e.g. comma-separated distinct values) rather than picking just one arbitrarily.
b. Keep the "Worked"/"No Work" status concept if it remains useful as a quick visual indicator (e.g. a small badge), but the REMARKS text specifically must now show the real activity, not a placeholder phrase.
c. When no activity/task was logged for a no-activity day, it's fine to keep "No activity recorded" or similar — this fix is about days that DO have a real linked activity showing it properly, not about inventing text for genuinely blank days.
