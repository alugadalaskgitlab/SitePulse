PART 1 — DUPLICATE BILLABLE ROW: SITE DPR LOG + ITS AUTO-MIRRORED PLANT USAGE ROW BOTH COUNTED

BACKGROUND (confirmed by direct code review — do not re-derive)
server/storage.ts, getVendorBillHireActivities (~line 16204 onward): this function queries `dprRows` from equipmentLogs (source: "dpr_log", joined to dprs) AND separately queries `usageRows` from the equipmentUsage table (source: "plant_usage"), for the SAME equipment IDs and period. It then maps BOTH into the final combined activity list with no deduplication between them.

The dprRows query already selects `plantUsageId: equipmentLogs.plantUsageId` (~line 16231) — this column links a DPR equipment log row to the Plant-side equipmentUsage row that was auto-created/mirrored from it (confirmed elsewhere in this file, e.g. ~line 6669, `tx.update(equipmentLogs).set({ plantUsageId: usage.id })`). This means when a machine is logged once in a Site DPR, the app can auto-create a corresponding Plant Operations usage record for the same event — a legitimate feature for plant visibility — but `plantUsageId` is fetched and never used to exclude that mirrored row from the vendor-bill activity list. The result: one real usage event produces TWO billable rows — one tagged "(SITE)" from dpr_log, one tagged "(PLANT)" from plant_usage — with identical date, hours, and diesel, confirmed directly in a real vendor bill (JCB VISWANATH BODAPALLY, 31-AUG-2026, 5.4 HRS, 10L diesel, appearing as both row 3 "(SITE)" and row 4 "(PLANT)").

FIX 1 — DEDUPE THE MIRRORED ROW
a. In getVendorBillHireActivities, after fetching both dprRows and usageRows, exclude from usageRows any row whose `id` matches a `plantUsageId` already present among dprRows for the same equipment. In other words: if a dpr_log row says "my mirror is plant_usage row #123", plant_usage row #123 must NOT also be included as its own separate activity — the dpr_log row is authoritative for that event, the plant_usage row is just its mirror.
b. Apply this filter before both rows are mapped into the returned array (the `...dprRows.map(...)` and `...usageRows.map(...)` spreads, ~line 16289 and ~line 16313).
c. Do not change how or when a DPR log gets mirrored into equipmentUsage in the first place (that Plant-visibility feature is out of scope) — this fix only affects which rows are counted as billable activity for a vendor bill.
d. Verify the fix does not accidentally exclude a genuinely independent plant_usage row that has no dpr_log counterpart (i.e. real Plant-only usage with plantUsageId null/not referenced by any DPR log) — those must still appear normally.

PART 2 — CHANGE ALREADY-BILLED HANDLING FROM "SKIP BEFORE PULL" TO "PULL EVERYTHING, THEN LET THE PREPARER EXCLUDE"

BACKGROUND
VB-14 (already built) made Pull All / each group's Pull button skip already-billed items by default, with an "INCLUDE ALREADY-BILLED ITEMS (NEXT PULL ONLY)" checkbox to opt into pulling them, and a toast like "4 item(s) pulled — 7 already billed elsewhere were skipped." Live use showed this isn't the preferred flow: the person preparing the bill wants to see ALL billable activity for the vendor/period first — including already-billed/paid rows, clearly flagged — review it, and only then choose to strip out the already-billed ones before saving. Choosing what to exclude AFTER seeing everything is more useful than being asked to decide before anything is even visible.

FIX 2 — REVERSE THE DEFAULT: PULL EVERYTHING, EXCLUDE AFTERWARD
a. Remove VB-14's skip-before-pull default. Pull All and each group's individual Pull button should once again bring in ALL matching items for the group/vendor/period, exactly as VB-11/VB-13 did — already-billed items included, each still showing its existing "BILLED (billNo - STATUS)" badge (this badge and the underlying check-duplicates call are correct and must stay).
b. Remove or repurpose the "INCLUDE ALREADY-BILLED ITEMS (NEXT PULL ONLY)" checkbox and the "N already billed elsewhere were skipped" toast — they no longer apply once pulling always includes everything.
c. Add a new, clearly-labeled action available AFTER items are pulled — e.g. "Exclude Already-Billed Rows" — that removes every line item currently flagged BILLED from the bill's line items in one click, leaving only unbilled rows. This must be a deliberate, visible action the preparer takes when ready, not automatic.
d. This action should be safely repeatable: if more items are pulled afterward (e.g. from another group) that are also already billed, the same "Exclude Already-Billed Rows" action should catch those too when used again, or the badge/exclude option should otherwise remain available for as long as any BILLED rows are present in the bill.
e. Manually re-adding a specific already-billed item afterward (e.g. via Add Item, or by not excluding it) must remain possible — this batch does not need to block that, since the flag is informational, not a hard lock; the point is giving the preparer control after seeing the full picture, not before.
