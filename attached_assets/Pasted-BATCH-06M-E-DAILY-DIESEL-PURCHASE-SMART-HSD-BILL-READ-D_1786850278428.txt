BATCH 06M-E — DAILY DIESEL PURCHASE
SMART HSD BILL READ + DUPLICATE CHECK
+ OPTIONAL MERCHANT QR
+ DEFERRED PAYMENT RECORDING

This is a focused enhancement to the existing Daily Diesel Requirement
purchase process.

OBJECTIVE

Improve the existing Diesel Purchase form so that:

1. Purchaser can upload/take a fuel bill photo.
2. SitePulse reads the bill and extracts relevant purchase details.
3. Extracted values can populate the purchase form after user confirmation.
4. SitePulse checks for possible duplicate use of the same bill.
5. Purchaser can optionally upload the fuel station's Merchant QR.
6. Purchaser can either:
   - record payment immediately, or
   - leave payment as Pending for Company/Admin to pay later.
7. PM/Admin/permitted user can later use a small Record Payment action.

Do NOT redesign Diesel stock, Material Receipt, 06M-B/C/D, Vendor Bills,
notifications or PI.

Expected schema change:
Investigate current Diesel payment fields first.
Prefer existing fields where sufficient.
If minimum extra payment fields are required, STOP and report before schema.

4. PRODUCT VALIDATION
--------------------------------------------------

The parser should identify whether the bill appears to be for:

Diesel / HSD

Examples:
- Diesel
- HSD
- High Speed Diesel

If the detected product clearly appears to be Petrol or another product:

do not auto-apply the values.

Show a warning:

"This bill appears to be for Petrol, not Diesel."

Allow PM/Admin/permitted user to inspect/correct if the parser is uncertain.

Do not silently accept an obviously non-Diesel bill.

--------------------------------------------------
9. QTY × RATE VALIDATION
--------------------------------------------------

When Qty, Rate and Amount are available:

calculate:

Qty × Rate

and compare against detected Amount.

Allow small rounding tolerance.

Example:

40.00 × 104.61 = 4,184.40

Show:

✓ Bill amount matches Qty × Rate

If mismatch:

show:

"Bill total does not exactly match Qty × Rate."

Do not automatically reject because tax/rounding/other charges may exist.

Treat as review warning.

--------------------------------------------------
10. REQUIREMENT COMPARISON
--------------------------------------------------

Compare detected/purchased Qty with the Daily Diesel Requirement Qty.

Do NOT require equality.

Example:

600 L

Detected bill:
620 L

Show:

Purchased quantity is 20 L above requirement.

Informational only.

Do not block purchase.

--------------------------------------------------
11. MULTIPLE BILLS AGAINST ONE REQUIREMENT
--------------------------------------------------

Do not assume one Daily Diesel Requirement can have only one fuel bill.

If current purchase model already supports only one Bill No/purchase record,
investigate before changing it.

The desired behavior is:

a requirement may be fulfilled through one or more purchase bills.

Example:

Required:
600 L

Bill 1:
400 L

Bill 2:
200 L

Total Purchased:
600 L

If the current Diesel Requirement persistence does NOT support multiple
purchase transactions cleanly:

STOP and report rather than forcing multiple bill data into one set of fields.

Do not redesign this silently.

--------------------------------------------------
12. DUPLICATE BILL CHECK
--------------------------------------------------

Before allowing confirmed bill details to be saved, check whether the bill
appears already used.

Strong duplicate identity should use:

- Supplier / Fuel Station
- Bill / Receipt Number
- Bill Date

and reinforce with:

- Quantity
- Amount

Do not depend only on Bill Number because receipt sequences may repeat across
different stations.

14. FUZZY DUPLICATE
