BATCH 06B — DPR CHAINAGE DUPLICATE / OVERLAP GUARD
WITH SAFE READ-ONLY PRIOR-DPR PREVIEW

This is a focused DPR-entry integrity batch.

Purpose:

Prevent accidental duplicate/overlapping chainage progress from being silently submitted, while still allowing legitimate repeated work such as:

- WMM/GSB multiple layers
- embankment lifts
- rework
- correction
- remeasurement
- intentionally repeated operations

The rule is:

WARN + REQUIRE REASON where overlap is real,
NOT a blanket hard prohibition.

Draft Save remains lenient.
Final Submit must recheck server-side.

IMPORTANT LIVE-FORM NAVIGATION RULE:

If an overlap warning references an earlier submitted DPR, the Engineer must be able to inspect that DPR READ-ONLY without losing or disrupting the current in-progress DPR form.

Preferred behavior:
open the referenced DPR in a read-only modal/drawer/overlay over the current entry form.

Closing the preview must return immediately to the untouched current DPR.

Do NOT casually navigate away from an unsaved live DPR form.

Do NOT modify Progress Report calculations, BOQ quantities, Geometry, Tomorrow's Programme, programme-bar quantities, Project Scope, Auto Sequence, Gantt, Execution Arrangement, or schema.

--------------------------------------------------
2. EXTRACT ONE NEUTRAL SHARED CHAINAGE-OVERLAP HELPER
--------------------------------------------------

Do not let DPR entry import overlap semantics from a report-specific module.

Move/extract the relevant generic functions from:

shared/progressReport.ts

into a neutral shared module, for example:

shared/chainageOverlap.ts

This helper should contain only generic road-chainage logic such as:

- side normalization
- side compatibility / may-overlap
- chainage range normalization
- interval overlap
- overlap segment calculation

Then:

- Progress Report imports from the neutral helper
- Guided DPR uses the same helper
- Detailed DPR uses the same helper
- server submit validation uses the same helper

Do not duplicate overlap math in four places.

Existing Progress Report behavior must remain unchanged.

--------------------------------------------------
3. SCOPE — CHAINAGE-BASED ROAD PROGRESS ONLY
--------------------------------------------------

Apply this guard only where the progress entry genuinely has meaningful road chainage.

Examples:
- pavement
- earthwork
- shoulders
- road linear/area/volume activities

Do NOT try to invent overlap comparison for:

- structures without chainage
- manual location strings
- non-linear items
- unrelated plant/material/labour records

If no usable From/To chainage exists, this overlap guard does not apply.

--------------------------------------------------
4. TWO TYPES OF OVERLAP MUST BE CHECKED
--------------------------------------------------

A. SAME DPR / SAME EDITING SESSION

If the Engineer adds two progress rows in the same DPR for:

- same BOQ item
- compatible side
- overlapping chainage

warn immediately.

Example:

Row 1:
WMM RHS 2+000–2+200

Row 2:
WMM RHS 2+150–2+300

Second row must surface:

"Possible overlap with another row in this DPR:
RHS Ch. 2+150–2+200"

Do not silently allow it without acknowledgement/reason.

B. PRIOR SUBMITTED DPRs

When entering/editing a chainage row, check prior valid submitted DPR progress for:

- same BOQ item
- compatible side
- overlapping chainage

Use the same canonical submitted/superseded/review filters already used by Progress Report / BOQ actual aggregation.

Do not treat drafts as authoritative prior executed work.

--------------------------------------------------
5. OVERLAP IS ADVISORY UNTIL ACKNOWLEDGED, NOT AUTOMATIC DUPLICATE
--------------------------------------------------

Never label the condition:

"Duplicate"

unless some future business rule proves that.

Use:

"Possible overlap"

Example:

⚠ Possible overlap with previously recorded progress

DPR-123
08-Aug-2026
RHS Ch. 2+150–2+180
35.000 Cum

Possible reasons may include:
- another layer
- another lift
- rework
- correction
- repeated operation

The system must not:

- auto-delete
- auto-reduce quantity
- auto-merge
- alter cumulative
- reject legitimate repeated work merely because chainage overlaps

--------------------------------------------------
6. EXACT DUPLICATE VS PARTIAL OVERLAP
--------------------------------------------------

Differentiate visually:

A. Exact same item + side + same From/To

Show stronger warning:

"Progress has already been recorded for this exact chainage."

B. Partial overlap

Show:

"Part of this chainage overlaps previously recorded progress."

Also show exact overlapping segment.

Example:

Entered:
2+100–2+300

Existing:
2+250–2+400

Overlap:
2+250–2+300

Both remain allowable with a proper reason.

--------------------------------------------------
7. REUSE EXISTING REASON-CAPTURE UX
--------------------------------------------------

Do not create a second independent overlap-reason field if the existing model can support it.

Guided/Detailed already carry:

`chainageOverrideReason`

and an existing "Give reason" style flow for outside-programme-bar chainage.

Reuse/extend that existing field/UX where semantically safe.

Examples:

"Second WMM layer"
"Embankment lift 3"
"Rework after rain damage"
"Correction to earlier measurement"

If the same field can represent both:
- outside-bar override
- overlap acknowledgement

make it visually clear which warning(s) the reason satisfies.

Do not overwrite an already-entered reason.

If one field cannot safely represent both semantics, STOP and report before adding schema.

--------------------------------------------------
8. DRAFT SAVE REMAINS LENIENT
--------------------------------------------------

Draft Save must NOT be blocked by overlap.

The Engineer may save:

- partial chainage
- overlapping row
- unresolved warning
- no overlap reason yet

and return later.

Draft must preserve:

- row
- entered chainage
- entered reason
- all other DPR data

Final Submit is where acknowledgement becomes mandatory.

--------------------------------------------------
9. FINAL SUBMIT RULE
--------------------------------------------------

For a chainage-based progress row with a real overlap:

Final Submit requires an explicit reason/acknowledgement.

If no reason:

mandatory readiness issue:

"Possible chainage overlap requires a reason before submission."

If reason exists:

submission allowed.

This applies to:

- same-DPR overlaps
- prior submitted-DPR overlaps

Do not make overlap itself a permanent hard block.

--------------------------------------------------
10. SERVER-SIDE RECHECK
--------------------------------------------------

Do not rely on client warnings.

On Final Submit, server must re-evaluate overlaps using current database state.

Reasons:

- another Engineer may submit overlapping progress after the draft was opened;
- client state can be bypassed;
- same-DPR payload can itself contain overlapping rows.

Server should return the overlap readiness issue using the existing Batch 04 readiness response shape where possible.

Draft endpoint remains lenient.

--------------------------------------------------
11. GUIDED + DETAILED MUST BOTH USE SAME RULE
--------------------------------------------------

Implement symmetrically in:

- Guided DPR
- Detailed DPR / SiteEntry
- SiteEdit draft completion
- server Final Submit

Detailed mode remains supported post-Batch-05 and must not bypass this guard.

Do not fix Guided only.

--------------------------------------------------
12. PRIOR DPR REFERENCE MUST BE READ-ONLY
--------------------------------------------------

When an overlap warning references an earlier submitted DPR:

show the DPR number/date as an inspectable reference.

The prior DPR must be READ-ONLY.

The Engineer must not enter edit mode for the previous DPR from the overlap warning.

Do not expose:
- Edit
- Cancel
- Delete
- any mutation action

inside this overlap-inspection experience.

The purpose is only:

"Show me what was recorded earlier so I can decide whether today's overlap is legitimate."

--------------------------------------------------
13. PREFERRED UX — READ-ONLY DPR PREVIEW WITHOUT LEAVING CURRENT FORM
--------------------------------------------------

Preferred implementation:

Click:

"DPR-123"

→ open a modal / drawer / overlay containing the relevant submitted DPR information.

The live Guided/Detailed DPR entry form underneath must remain mounted.

Closing the preview returns immediately to the exact same entry state.

At minimum show:

- DPR date
- site
- Engineer
- activity progress
- relevant chainage rows
- quantity/UoM
- equipment/log sections only if existing reusable report renderer makes this straightforward
- remarks

Ideally reuse the existing SiteReport rendering or shared report sections.

Do NOT create a second unrelated read-only DPR presentation if existing components can be safely extracted/reused.

The preview should have:

[Close]

and optionally:

[Open full report]

only if full navigation is useful and safe.

No editing actions.

--------------------------------------------------
14. FOCUS THE PREVIEW ON THE RELEVANT OVERLAP
--------------------------------------------------

Where practical, when opening the previous DPR from an overlap warning:

highlight or scroll to the referenced progress entry.

Example:

Current:
WMM RHS 2+150–2+300

Previous DPR contains:
WMM RHS 2+100–2+180

Preview should make that prior row easy to identify.

Do not require the Engineer to search a long DPR manually if the matching row ID/reference is already available.

This is usability only.

Do not build a complex new report engine.

--------------------------------------------------
15. FALLBACK IF EMBEDDED/MODAL DPR PREVIEW IS NOT SAFELY FEASIBLE
--------------------------------------------------

If the existing DPR report cannot reasonably be reused in an embedded read-only preview without substantial refactoring:

do NOT force a rushed second renderer.

Fallback:

navigate to:

`/site/report/:id`

using the existing Batch 06A validated `returnTo` mechanism.

But this fallback is permitted ONLY if the following is proven:

A. the current in-progress Guided/Detailed DPR is safely preserved before navigation;

B. returning restores the SAME draft;

C. unsaved:
- activity rows
- chainages
- width/thickness
- quantities
- chainageOverrideReason
- equipment opening/closing values
- labour/material rows
- other edited state

survive the round trip;

D. no second DPR is created;

E. stale local-autosave recovery does not replace the active server draft.

Use existing autosave/server-draft mechanisms.

Do not invent another navigation persistence store.
