Instruction 030 — Execution Arrangements fix, Field Home short-name fix, Tomorrow's Plan arrangement awareness

Part A — Execution Arrangements (Work Programme / Earthwork Control)

Root cause (verified in code): arrangements are stored per BOQ item (earthwork-arrangements-item query, keyed by boqItemId), but the Gantt's per-reach "Execution Arrangement Required" badge is driven by a separate per-bar allocation table (earthwork_arrangement_programme_allocations, keyed by programmeBarId) — see BarArrangementPanel.tsx lines ~77-101. Creating an arrangement via Earthwork Control (EarthworkArrangementDialog.tsx) only writes the item-level record; it never creates the bar-level allocation rows, so the badge stays stuck even after a valid arrangement — including a non-outsourced one — exists. shared/executionState.ts already treats hlc_in_house / reused_excavated as a valid resolved state equal to outsourcing, so "no outsourcing needed" is already modeled; it just never reaches the bar because of this gap.

Close the item→bar allocation gap. On arrangement approval (any arrangementType, including hlc_in_house / reused_excavated), auto-create/update earthwork_arrangement_programme_allocations rows for every programme bar whose chainage range overlaps the arrangement's covered range on that BOQ item, up to the arrangement's quantity. If a bar isn't fully covered, leave it flagged and surface the shortfall (reuse the existing checkCutFillBalance pattern). Confirm whether this should also backfill allocations for arrangements approved before this fix ships — otherwise those will still show stuck badges.
Fix the Apply button in BarArrangementPanel.tsx (~lines 324-345). disabled={!overrideValue || overrideMutation.isPending} combined with the default <option value="">Keep auto-detected…</option> (empty value) leaves Apply permanently disabled with no explanation when that option is selected. Either treat "Keep auto-detected" as a valid explicit confirmation that enables Apply, or hide/disable the button with visible helper text explaining why no action is needed.
Declutter the Gantt badge. In WorkProgramme.tsx (~1053-1120) each row currently has three redundant affordances: the full-text ExecutionStateBadge, a hover-only icon button, and an "Arrangements" item already in the "..." menu. Remove the full-text badge; make the icon button always visible (not hover-only), with a colored ring when arrangement is required and a tooltip on hover. Keep the "..." menu entry. Add an aggregate count at the item/category header (e.g., "6 reaches need arrangement") so at-a-glance visibility isn't lost.
Move arrangement creation out of Procurement. WorkDemand.tsx (the Procurement tab) currently imports EarthworkArrangementCell directly and gates procurement actions on classification. Move create/edit into the existing dedicated route /work-program/:id/execution-arrangements (ExecutionArrangements.tsx), which is currently read-only with no "Create" button. Have WorkDemand, Earthwork Control, and the Gantt all link out to it instead of embedding the classification UI inline.

Part B — Field Home "Today's Site Goal" short-name mislabeling

Root cause (verified): extractShortName() in client/src/pages/FieldHome.tsx (~lines 29-64) checks description keywords in a fixed order. The broad check if (d.includes("EMBANKMENT") && (d.includes("BORROW") || d.includes("IMPORT"))) return "Embankment — Borrow Earth"; fires before the more specific if (d.includes("SUBGRADE")) return "Subgrade Preparation";. Subgrade item descriptions often naturally reference embankment/borrow context, so they get mislabeled as Embankment even though the planned quantity is Subgrade.

Fix: reorder the checks so SUBGRADE is tested before the EMBANKMENT + BORROW/IMPORT and EMBANKMENT + CUT checks (move the existing if (d.includes("SUBGRADE")) return "Subgrade Preparation"; line to run first, ahead of all three EMBANKMENT conditions). Leave every other keyword check and its order unchanged. Add a quick regression check confirming a real Subgrade BOQ description containing "borrow" or "embankment" now returns "Subgrade Preparation," not "Embankment — Borrow Earth."

Part C — Tomorrow's Plan has no awareness of Execution Arrangement status

Verified in code: Tomorrow's Plan (SiteRequirementNew.tsx → POST /api/site-requirements) lets a site engineer pick a BOQ item, chainage from/to, and planned qty, then list materials/equipment/labour needed for the next day. Checked the full create/list/status pipeline in server/routes.ts and server/storage.ts (createSiteRequirement, listSiteRequirements, etc.) — there is no reference anywhere to earthwork_arrangements, programmeBarId, or arrangement/execution state. A site engineer can currently submit a plan for an item/chainage that still shows "Execution Arrangement Required," with no warning.

Fix (non-blocking, informational — do not block submission):

In SiteRequirementNew.tsx, when a BOQ item is selected (boqItemId) and it's earthwork/bituminous-eligible (reuse executionArrangementCategoryForItem), look up its current execution state for the entered chainage range (reuse deriveExecutionState from shared/executionState.ts against the item's arrangements/allocations, same data Part A now keeps current) and show it inline next to the BOQ item picker — e.g., a small badge: "HLC In-house," "Outsourcing Approved," or amber "Execution Arrangement Required."
If the state resolves to arrangement_required at submission time, show a non-blocking warning banner ("Execution arrangement for this item/chainage is not yet decided — material sourcing may not be confirmed") but still allow the engineer to submit. PM/Admin reviewing the plan (updateSiteRequirementStatus) should see the same warning so they know to chase the arrangement before relying on the plan.
