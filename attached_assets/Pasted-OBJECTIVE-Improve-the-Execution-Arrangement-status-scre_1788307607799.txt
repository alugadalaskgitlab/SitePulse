OBJECTIVE

Improve the Execution Arrangement status screen so PM/Admin does not normally
type "Actual Quantity" manually.

For earthwork/vendor arrangements, derive execution evidence from:

1. Submitted DPR progress for the same BOQ item / relevant chainage;
2. Material Trips / Receipts linked to the same vendor / BOQ item / arrangement.

Show BOTH original trip quantity in CFT and converted quantity in Cum wherever
relevant.

This should also prepare the same verified quantity trail for future Vendor Bills.

DO NOT redesign DPR, Material Trips, or Vendor Billing in this batch.
DO NOT create duplicate quantity-entry systems.


============================================================
PART 1 — INVESTIGATE CURRENT LINKS FIRST
============================================================

Inspect the current code/data relationships for:

- Execution Arrangements
- Programme Bars / Reaches
- DPR progress entries
- Material Trips
- Material Receipts
- Vendor / Agency
- BOQ item linkage
- earthworkArrangementId
- programmeBarId
- Vendor Bills

Report first:

1. Which DPR records can already be linked reliably to:
   - BOQ item
   - chainage/reach
   - programme bar
   - arrangement

2. Which Material Trip / Receipt records already contain:
   - vendor/agency
   - BOQ item
   - arrangement
   - programme bar
   - quantity
   - UOM

3. Which existing conversion helper should be reused for CFT ↔ Cum.

Do not invent a second conversion formula if one already exists.


============================================================
PART 2 — DPR EXECUTED QUANTITY
============================================================

For every programme bar/reach covered by an arrangement, calculate:

DPR Executed Qty

from valid submitted DPR progress matching:

- same BOQ item;
- same project/site;
- overlapping chainage/reach;
- relevant side/layer/lift where applicable.

Exclude:

- draft DPRs;
- cancelled/deleted DPRs;
- superseded/version-invalid entries;
- unrelated BOQ items.

Use the existing DPR/BOQ quantity and geometry logic wherever possible.

Do NOT simply assign the full DPR quantity to every overlapping programme bar.

If one DPR spans multiple programme bars/reaches, use the existing reach/geometry
logic to allocate the relevant quantity correctly.

If reliable allocation cannot be determined from existing data, show:
"DPR quantity incomplete / requires review"
rather than guessing.


============================================================
PART 3 — VENDOR TRIP QUANTITY
============================================================

For vendor-arranged earthwork, calculate:

Vendor Trip Qty

from Material Trips / Receipts linked to the same:

- vendor/agency;
- BOQ item / intended activity;
- arrangement where available;
- programme bar / reach where available;
- relevant date period.

Prefer exact existing IDs:
- earthworkArrangementId
- programmeBarId
- boqItemId

Do NOT use loose material-name matching where exact linkage exists.

Avoid double counting where a Material Receipt is already the receipt representation
of the same Material Trip.

One physical trip must count once.


============================================================
PART 4 — SHOW BOTH CFT AND CUM
============================================================

The original recorded quantity and UOM remain authoritative.

If a trip/receipt is recorded in CFT and Cum is required for BOQ/arrangement
comparison:

show BOTH:

Example:

Vendor Trips:
63,400 CFT
= 1,795.40 Cum

Use the canonical conversion:

1 Cum = 35.3147 CFT
Cum = CFT / 35.3147

BUT:
Reuse any existing approved conversion helper/configuration if already present.
Do not introduce inconsistent conversion logic.

Never overwrite the original CFT quantity with the converted Cum value.

Store/display:
- Original Qty
- Original UOM
- Converted Qty
- Converted UOM

as appropriate.


============================================================
PART 5 — ARRANGEMENT STATUS SCREEN
============================================================

The current screen shows repeated status forms without clearly identifying which
programme bar they belong to.

For each programme bar/reach, show a clear header:

Reach / Chainage

============================================================
PART 6 — REMOVE NORMAL MANUAL ACTUAL-QTY ENTRY
============================================================

Do NOT require PM/Admin to manually retype Actual Quantity when reliable DPR/trip
evidence exists.

Replace the normal Actual Quantity field with:

DPR Executed Qty
Vendor Trip Qty
Variance

For exceptional cases provide:

"Override / Accepted Qty"

PM/Admin only.

If override is used:
- require reason;
- retain DPR/trip-derived figures;
- record accepted quantity separately;
- audit user/date/time/reason.

Do not overwrite source DPR or trip records.


============================================================
PART 7 — STATUS CHANGE
============================================================

PM/Admin still controls official execution status.

Statuses remain existing values such as:
- Active / Arranged
- Partially Executed
- Executed
- Not Executed
- Cancelled
- Suspended
- Rescheduled
- Early Closed

The status control should use the derived quantities as evidence.

Do NOT automatically change official status merely because a quantity threshold
was reached unless that behavior already exists and is explicitly approved.

Suggested helper only:

If DPR/trip quantity > 0:
"Execution evidence available"

If accepted qty >= allocated qty:
"May be ready to mark Executed"

PM/Admin makes the final status decision.


============================================================
PART 8 — VARIANCE / RECONCILIATION
============================================================

Show:

DPR Executed Qty
Vendor Trip Qty
Difference

Do not silently choose one as "correct".

Interpretation:

DPR Qty = work/progress evidence
Trip Qty = vendor/material movement evidence
Accepted Qty = commercial/verified quantity when required

If variance exists, show it clearly.

Example:

DPR: 1,820.00 Cum
Trips: 1,795.40 Cum
Variance: +24.60 Cum

No blocking workflow is required in this batch.

Keep it informative and simple.


============================================================

- variance

Do not make users enter the same trip/quantity again in Vendor Bills.

workflow.
