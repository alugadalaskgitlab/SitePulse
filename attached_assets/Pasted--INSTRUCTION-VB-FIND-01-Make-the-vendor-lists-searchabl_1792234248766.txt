## Part A — The bill date on the Vendor Bills list

**The fault.** The list is a set of cards, and the meta line at
`client/src/pages/VendorBills.tsx:5495` renders:

```
{bill.billNo} • {getBillTypeLabel(bill.billType)}
{bill.periodFrom && bill.periodTo && ` • ${formatDate(bill.periodFrom)} to ${formatDate(bill.periodTo)}`}
```

So the card shows the **billed period** and never the **bill date**. Worse, a bill with
no recorded period shows no date at all — there is nothing on the card to place it in
time. The bill date is what Tally orders the vendor's ledger by, so it is the one date
that must be visible.

**Required.**

1. Every card shows the bill's own **bill date**, labelled so it cannot be mistaken
   for the period — for example `Bill date 09-Oct-2026`.
2. The billed period continues to show **in addition**, when both ends are recorded,
   labelled as the period.
3. Where `billDate` is missing on an older bill, say so plainly rather than showing
   a blank or substituting another date.
4. Use the existing `formatDate` helper. Do not introduce a second date format.

**Constraints.** Do not change the filters, the sort order, or
`filterFinancialBills`. Do not change which bills appear. This part adds text to a
card and nothing else.

## Part B — Search on the Vendors master list

**The fault.** `client/src/pages/VendorMaster.tsx` has a search box on the **Link
Vendors** tab only (`reviewSearch`, line 53). The **Vendors** tab renders
`const available = vendors.data || [];` — every vendor, unsorted, unfiltered, as cards
in a two-column grid. With the list about to grow, that is a scroll.

**Required.**

1. A text search box over the Vendors tab, matching the same fields the card
   displays: name, business name, GST number and contact phone. Case-insensitive,
   matching anywhere in the value, not only at the start.
2. The list is **sorted by name** so it is predictable with or without a search term.
3. A plain count — how many vendors are shown, and how many there are in total when a
   search is narrowing the list.
4. When a search matches nothing, say so in words. Do not show an empty grid.

**Constraints.** Reuse the shape of the existing `reviewSearch` box on the other tab
so the two behave the same. Do not change what the cards display, and do not change
the Link Vendors tab.

## Part C — Search on the payables page, both tabs

**The fault.** `client/src/pages/VendorPayables.tsx` holds only `dateFrom`, `dateTo`
and `activeTab` (lines 240–243). Neither tab can be searched: the linked tab renders
every vendor row and the unlinked tab every typed name.

**Required.**

1. A text search box on the **linked vendors** tab, over the vendor name, filtering
   the rows shown.
2. A text search box on the **unlinked bills** tab, over the typed vendor name **and**
   the bill number, so a bill can be found either way.
3. Each search is independent — switching tabs does not carry a term across, and does
   not clear the other tab's term.
4. The search term joins `dateFrom`, `dateTo` and `tab` in the URL, so a filtered view
   can be returned to by the back navigation that VB-PAY-02 established.

**Constraints — this is the critical one.**

- **Every total on the page is the total of the rows the filter produced, and says so.**
  A filtered page must not show a headline figure covering rows the user cannot see.
  If that is awkward for any figure, leave that figure as the unfiltered total and
  label it unambiguously — but do not silently mix the two.
- The page stays **read-only**. It creates, updates and deletes nothing.
- Do not change `projectVendorPayables`, `billPaymentPosition`,
  `getBillFinancialTotals` or any other calculation. Filtering happens after the
  figures are computed, never by changing how they are computed.

## Part D — The vendor picker on the bill form

**Not a fault, but three real faults inside it.** The picker at
`VendorBills.tsx:2808–2863` is **already type-to-search** — a text input with a
filtered dropdown, not a scrolling `<Select>`. It does not need replacing. It has
three defects:

1. The dropdown is suppressed by `&& !vendorName`, so once a vendor is chosen the
   list cannot be reopened. To change a selection the user must clear the field by
   hand.
2. There is no keyboard navigation — no up/down through the options, no Enter to
   choose. Only the mouse works.
3. `vendorName` is cleared on every keystroke, so a part-typed edit leaves the form
   with no vendor until something is picked again.

**Required.**

1. The dropdown reopens on focus or on typing **even when a vendor is already
   selected**, so a selection can be changed in place.
2. Up and down arrows move through the options, Enter chooses the highlighted one,
   Escape closes the list leaving the current selection alone. **Enter must not
   submit the form** — `client/src/components/TripMasterCombobox.tsx` already solves
   exactly this and is the pattern to follow.
3. Changing the text does not leave the form in a state where a vendor was selected
   and is now silently empty. Either the previous selection holds until a new one is
   made, or the field reads plainly as unselected.

**Constraints — read this before touching it.**

- **Free-typed vendor names must keep working.** The field deliberately accepts a name
  that is not in Vendor Master; that is why `/api/vendor-aliases` exists. Do **not**
  turn this into a master-only picker, and do not remove the on-blur behaviour that
  accepts typed text. Breaking this would stop bills being raised for new vendors.
- Do not change `/api/vendor-bills/vendor-names` or `getVendorNames()` in
  `server/storage.ts`. The name list, including the free-text names it unions in from
  equipment and receipts, stays exactly as it is.
- Do not change the hire-vendor display handling or `isHistoricalHireEdit`.
