BATCH 06F — ARRANGEMENT-AWARE TOMORROW REQUIREMENT ALLOCATION
+ PRESERVE ARRANGEMENT-ADJUSTED BOM SEMANTICS

This is a focused Tomorrow's Requirements / allocation-context batch.

IMPORTANT BUSINESS RULE

The Site Engineer does NOT select:

- vendor
- Execution Arrangement
- daily supplying agency

while raising Tomorrow's Requirement.

The Engineer continues raising the requirement exactly as today:

- planned work
- material requirement
- equipment requirement
- labour requirement
- immediate requirement

The allocating / approving authority decides HOW the requirement will be
fulfilled.

Execution Arrangement intelligence belongs on the APPROVAL / ALLOCATION
side, not on the Engineer's requirement-entry side.

--------------------------------------------------
2. CONFIRM EXISTING BOM BEHAVIOR — DO NOT REBUILD IT
--------------------------------------------------

The current planning engine already applies active Execution Arrangements
to HLC BOM/resource demand.

Preserve this.

Verified current concepts include:

- Equipment demand reduced when the relevant component is agency/client
  responsibility.

- Diesel demand follows equipment/component responsibility BUT remains in
  HLC demand where HLC is explicitly responsible for fuel.

- Labour demand is reduced only for the execution components that are
  positively non-HLC.

- Material/source demand is reduced where agency/client owns that material
  component.

- "not_decided" responsibility remains in HLC demand provisionally rather
  than being silently excluded.

- arrangement allocations linked to programme bars phase the exclusion to
  that bar/quantity.

DO NOT create a second BOM formula inside Tomorrow's Requirements.

DO NOT alter these existing shared calculation rules.

--------------------------------------------------
3. PURPOSE OF THIS BATCH
--------------------------------------------------

This batch is NOT:

"make Execution Arrangement start affecting BOM."

It already does.

This batch is:

"surface the existing arrangement context to the allocating authority and
record the DAILY fulfilment decision without changing the permanent
Execution Arrangement."

The chain should be:

Standing Execution Arrangement
        ↓
BOM / resource responsibility
        ↓
Engineer raises Tomorrow requirement
        ↓
Allocating authority sees applicable arrangement context
        ↓
Authority chooses tomorrow's actual fulfilment source
        ↓
Next-day receipt / equipment / DPR actual

--------------------------------------------------
4. ENGINEER REQUIREMENT SCREEN — KEEP SIMPLE
--------------------------------------------------

Do NOT add an Execution Arrangement selector to the Site Engineer's
Tomorrow Requirement entry.

Do NOT ask Engineer to choose vendor.

Do NOT ask Engineer to decide:

- outsourced vs HLC
- primary vendor
- alternate vendor

The Engineer simply states what is required.

already exists and needs preservation.

--------------------------------------------------
5. ALLOCATING AUTHORITY — SHOW ARRANGEMENT CONTEXT
--------------------------------------------------

When PM / Manager / Stores / Equipment authority opens a requirement for
allocation, SitePulse should resolve relevant Execution Arrangement context
from the requirement's:

- project/site
- BOQ item / planned work
- programme bar
- reach / chainage
- requirement category

where those stable links exist.

Show this information only to the allocation/review side.

Example:

BORROW EARTH
Required: 350 Cum
For: Embankment — RHS Ch. 2+000–2+200

Applicable Execution Arrangement:
ABC Earthworks
Borrow Earth supply & carting
Ch. 1+500–3+000

Do not make the Engineer enter this.

--------------------------------------------------
6. NO ARRANGEMENT IS NOT AN ERROR
--------------------------------------------------

If NO applicable Execution Arrangement exists:

DO NOT show:

"Arrangement required"
"Missing Arrangement"
"Create Arrangement"

for ordinary requirement allocation.

Treat the responsibility as:

HLC / Main Contractor

The allocating authority may simply mark:

Arranged

with the current normal internal allocation/procurement process.

Execution Arrangement is optional operational/commercial context, not a
mandatory prerequisite for tomorrow's work.

--------------------------------------------------
7. EXACTLY ONE APPLICABLE ARRANGEMENT
--------------------------------------------------

If exactly one active/applicable arrangement exists:

show it prominently as the SUGGESTED fulfilment context.

Example:

Suggested:
ABC Earthworks

Arrangement:
Borrow Earth supply & carting

Do NOT automatically lock the authority to that vendor.

The PM must still be able to choose another valid fulfilment route for
tomorrow.

--------------------------------------------------
8. MULTIPLE APPLICABLE ARRANGEMENTS
--------------------------------------------------

If multiple active arrangements can legitimately fulfil the requirement:

show all compatible choices.

Example:

Applicable vendors:

○ ABC Earthworks
   Arrangement #17
   Ch. 1+500–3+000

○ XYZ Infra
   Arrangement #24
   Embankment / Borrow Earth

The authority chooses tomorrow's actual allocation.

Do NOT guess solely from vendor name.

Use stable arrangement IDs and BOQ/reach/programme compatibility.

--------------------------------------------------
9. DAILY TEMPORARY VENDOR EXCEPTION
--------------------------------------------------

Critical requirement:

A standing Execution Arrangement must NOT be rewritten merely because PM
uses a different vendor for one day.

Example:

Permanent/stretch arrangement:
ABC Earthworks

Tomorrow:
ABC reports a breakdown / no tippers available.

PM agrees:
XYZ Infra will supply tomorrow.

Record:

Tomorrow Fulfilment:
XYZ Infra / relevant Arrangement

Reason:
"Primary vendor unavailable"

This is a DAILY operational allocation.

It does NOT transfer the permanent stretch arrangement from ABC to XYZ.

Do not mutate:

- earthwork_arrangements agencyName
- scopeSegmentIds
- allocatedQty
- programme allocations

merely because of a one-day substitution.

--------------------------------------------------
10. HLC / INTERNAL OPTION
--------------------------------------------------

The allocating authority must always have an option conceptually equivalent
to:

HLC / Internally Arranged

when valid.

Example:

Borrow Earth — 350 Cum

Fulfilment:
HLC / Contractor

Status:
Arranged

This does NOT create an Execution Arrangement.

It simply records the daily operational decision.

13. BOM MUST REMAIN CONSISTENT
--------------------------------------------------

The daily allocation UI must not contradict the BOM.

--------------------------------------------------
14. TEMPORARY DAILY ALLOCATION DOES NOT REWRITE BOM
--------------------------------------------------

A one-day exception does NOT immediately alter the standing project BOM
responsibility model.

Example:

Permanent arrangement says agency supplies Tippers.

PM temporarily gives the job to another approved agency tomorrow.

HLC BOM remains:
Tippers = agency responsibility.

Only the DAILY vendor identity changed.

However:

if PM deliberately chooses:

HLC / Internally Arranged

for a resource that the standing arrangement assigns to the agency, show a
clear informational warning:

"Standing arrangement assigns this component to ABC Earthworks. Tomorrow
has been allocated internally as an exception."

Do NOT silently rewrite the standing BOM.

Do NOT block the allocation.

25. NO OVER-ALLOCATION SIDE EFFECT

a daily exception and reason — do not silently expand its contractual
arrangement quantity.
