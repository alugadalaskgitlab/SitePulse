INSTRUCTION DPR-09: A DPR whose very first save happens before any BOQ item is picked gets permanently locked to "no BOQ project" — even after the user later adds real BOQ-linked activity rows — which hides the BOQ item picker (falls back to free-text Activity) inconsistently across Guided/Detailed/Edit views on reopen

READ THIS FIRST — SCOPE DISCIPLINE
This is a precise, code-confirmed root cause, not a guess — verified by reading client/src/pages/SiteEdit.tsx, GuidedDpr.tsx, SiteEntry.tsx, and shared/dprBoqSelection.ts directly, and reproduced on video (ALLADURG PWD ROAD TO PAMPAD, 16/09/2026). Do not touch DPR-02 through DPR-08 — all confirmed correctly built. Do not reintroduce the manual "BOQ project" dropdown removed in DPR-08 — the fix here is automatic, not a UI control. Do not publish automatically. STOP after this and report back.

BACKGROUND (confirmed by direct code review — do not re-derive)
1. shared/dprBoqSelection.ts's resolveDprBoqProjectId() treats an explicit `null` preferredProjectId as a permanent, deliberate "this DPR has no BOQ project" signal and never re-guesses — this rule exists specifically to protect a genuinely BOQ-less DPR (e.g. "No Site Work" only) from having its project silently reassigned on reload. That part is correct and must not change.
2. The problem is HOW a DPR ends up with that saved `null` in the first place, and what happens afterward. When a brand-new DPR/draft is saved (even just "Save Draft") before the user has picked any BOQ item on any row yet, the server can persist `boqProjectId: null` for that draft, because at that exact moment nothing in the DPR references a BOQ item.
3. client/src/pages/SiteEdit.tsx (~line 719-741) has a recovery effect meant to fix exactly this: if the live editor rows now contain real BOQ item references (`siteEditHasBoqReferences`, computed via `hasDprBoqReferences`) but no project is resolved, it should re-pin to the site's actual project. BUT the effect bails out immediately whenever `hasSavedBoqProject` is true — defined as "the loaded DPR record simply HAS a boqProjectId field at all, including an explicit null" (line ~727-729, comment: "A saved project field is already canonical, including an explicit null."). This means: once a DPR's project field has been saved as null even once, this recovery NEVER runs again for that DPR — regardless of whether the current, live rows in front of the user clearly reference real BOQ items (e.g. "earthen shoulder", Reach 1, visible and correctly linked in the Guided DPR view of the very same draft).
4. Confirmed by video: the same draft (site ALLADURG PWD ROAD TO PAMPAD, 16/09/2026) showed the BOQ item "earthen shoulder" correctly linked with programme context in the Guided DPR flow, but when switched to Detailed/Advanced view (which routes to SiteEdit.tsx in draft mode via `/site/edit/:id?draft`) for the SAME draft, the Activity field fell back to a bare free-text box with no BOQ picker at all — the label even changed from "BOQ Item / Activity" to plain "Activity", which only happens when `siteBoqItems.length === 0`.
5. DPR-08 (the previous batch) correctly removed a manual "BOQ project" dropdown/status panel (DprBoqStatus.tsx) that had been added directly by Replit outside this instruction process. That manual dropdown was, incidentally, the ONLY way a person could work around this null-lock by hand (by re-selecting a project). Removing it without fixing the underlying automatic-recovery gate has left affected drafts with NO way at all — automatic or manual — to ever show their BOQ items again. This is why the person's report says the app got "more erratic" after that deploy: the lock itself is not new, but the one workaround for it is now gone.
6. shared/dprBoqSelection.ts already has a helper, `hasDprBoqReferences()`, purpose-built to detect real BOQ item references in the current DPR data, and a stricter helper `isConfirmedDprNullProjectRecovery()` used server-side for a different, more cautious recovery path (server/routes.ts ~line 2324). The client-side recovery effect in SiteEdit.tsx already computes `siteEditHasBoqReferences` using `hasDprBoqReferences()` (line 721) — it simply never gets a chance to use it because of the `hasSavedBoqProject` bail-out at line 729.
7. GuidedDpr.tsx's equivalent recovery effect (~line 682-705) does NOT have this same `hasSavedBoqProject` bail-out — it only checks `serverBoqProjectPinRef.current !== undefined`, which is why the SAME draft could sometimes recover correctly in the Guided view while never recovering in the Detailed/Edit view. This is the source of the "shows in some views, not others" inconsistency the person is reporting.

FIX — AUTOMATICALLY RE-RESOLVE WHENEVER LIVE DATA HAS REAL BOQ REFERENCES, REGARDLESS OF A SAVED NULL
1. In SiteEdit.tsx's recovery effect (~line 719-741), remove the `|| hasSavedBoqProject` condition from the early-return guard. The effect should re-pin to the resolved `siteBoqProjectId` whenever: BOQ projects have loaded (`boqProjectsLoaded`), a project actually resolves for the site (`siteBoqProjectId != null`), the CURRENT live rows genuinely reference a BOQ item (`siteEditHasBoqReferences === true`), and no preference has been pinned yet in this session (`!boqProjectPreference.resolved`) — regardless of whether the loaded DPR record's own saved `boqProjectId` was null.
2. This must remain narrow: a DPR that genuinely has NO BOQ item anywhere in its current rows (e.g. "No Site Work" only, or Incidental/Non-BOQ only) must keep showing no project and no BOQ picker — `siteEditHasBoqReferences` being false is exactly what correctly blocks recovery in that case, and that must not change.
3. Apply the identical fix to SiteEntry.tsx's equivalent recovery effect (~line 917-936) — check it for the same `hasSavedBoqProject`-style bail-out and remove it under the same condition (live rows have real BOQ references).
4. Audit GuidedDpr.tsx's recovery effect (~line 682-705) too: confirm whether `serverBoqProjectPinRef.current !== undefined` (which is true even for a saved null) is ALSO silently blocking recovery there in some cases (it appears to return early before ever checking `guidedHasBoqReferences`) — if so, apply the same principle: when the live entries have real BOQ references, recovery must win over a stale saved null, consistently across all three screens (Guided, Detailed/new, Edit).
5. Once the project is correctly re-resolved for a DPR whose CURRENT data genuinely has BOQ references, the fix must also ensure this corrected, non-null boqProjectId is what actually gets SAVED on the next Save Draft / Submit — so the DPR is durably un-stuck going forward, not just cosmetically fixed until the next reload. Trace the save payload logic (GuidedDpr.tsx ~line 1251-1256, SiteEdit.tsx's equivalent) to confirm the newly-resolved project, not the stale saved null, is what gets sent.
