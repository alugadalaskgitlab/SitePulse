Instruction DPR-01 — DPR Integrity & Execution Closure Batch

Do not redesign DPR. Do not create duplicate logs or duplicate tables for
anything that already has a home. Reuse and link existing records.

This batch is grounded in a direct code investigation of the current
codebase (not assumptions) — every part below states exactly what was
found before describing what to change. Where the investigation found
the reported problem does NOT exist as described, that is stated plainly
so you do not spend time "fixing" something that already works.

DPR should become the daily truth sheet: work done, resources used,
material moved, equipment performance, stoppages, and what happened to
the planned execution arrangement.


PART 1 — RESUME DRAFT DPR FROM DASHBOARD (CONFIRMED BUG, EXACT FIX)

GROUND TRUTH

client/src/pages/Home.tsx renders the "Unfinished Draft DPR" card and
links its "Open" action to the literal URL `/dpr/${d.id}`. No such route
exists anywhere in client/src/App.tsx — the only DPR routes registered
are `/site/edit/:id`, `/site/report/:id`, `/site/success/:id`,
`/site/guided`, `/site/new`. The app's catch-all route renders NotFound,
which is the exact 404 observed. This is a leftover/incorrect hardcoded
path, not a missing route registration.

The correct pattern already exists and already works correctly elsewhere
in this same codebase: client/src/lib/dprEntryMode.ts exports
`roadDprDraftHref`, and client/src/pages/FieldHome.tsx already uses it
correctly (`continueDraftHref`) for its own equivalent draft-resume
action.

REQUIRED FIX

In Home.tsx, replace the hardcoded `/dpr/${d.id}` with the same resolved
href FieldHome.tsx already uses correctly — branch by DPR type exactly as
FieldHome.tsx does (e.g. structure DPRs go to `/site/edit/${d.id}`-style
routes, road DPRs go through `roadDprDraftHref(d.id)`). Do not invent a
new routing scheme; mirror the already-correct, already-tested logic.

Opening a draft must restore every previously entered section and value
exactly as saved. No new DPR should ever be created by clicking Open, and
no "record not found" error should appear when the draft genuinely
exists.


PART 2 — MANUAL LENGTH OVERRIDE IS SILENTLY DISCARDED (this is the real
bug — the chainage→length FORMULA itself is correct, do not touch it)

GROUND TRUTH

The Length calculation is centralized in one place —
shared/dprGeometry.ts (`calculateLengthFromChainage`,
`getEffectiveLength`) — and is correct: Length(m) = |To(Km) − From(Km)|
× 1000. This is reused consistently across SiteEntry.tsx, SiteEdit.tsx,
and GuidedDpr.tsx, and is independently recomputed and verified
server-side before trusting any client value. Side (LHS/RHS/Both
Sides) does not multiply or otherwise affect this calculation. Do NOT
change this formula and do NOT re-derive it independently anywhere —
it is already correct and already centralized.

The real, separate problem: in SiteEntry.tsx and SiteEdit.tsx, the Length
field can be manually typed (correctly supporting a curved-alignment
stretch where the straight chainage difference is not the true length).
But the onChange handler on EITHER chainage field unconditionally
overwrites `length` with the freshly recalculated chainage-based value
the moment the user touches chainage again — with no check for whether
Length currently holds a legitimate manual value, and no warning. A
manually entered Length is silently discarded on the next chainage edit.

GuidedDpr.tsx does not have this problem — there, Length is read-only and
always chainage-derived by design, so there is nothing to protect there.

REQUIRED FIX

In SiteEntry.tsx and SiteEdit.tsx only: track whether Length was manually
edited by the user for that row (a per-row flag is sufficient — do not
add a schema column unless investigation shows the flag must persist
across save/reload; if a manual value was already saved, treat a Length
that differs from the chainage-derived value on load as manual and
preserve that distinction). When a chainage field changes on a row whose
Length was manually set:
- do NOT silently overwrite it;
- show a small inline prompt such as "Chainage changed — recalculated
  length is X m, current length is Y m. Update to X m?" with an
  explicit action, defaulting to keeping the user's existing manual
  value if they take no action.
When Length has never been manually touched for that row, keep the
current auto-recompute-on-chainage-change behavior exactly as it is.


PART 3 — CUT→FILL LINKAGE (CONFIRMED WORKING — investigate discoverability,
do not rebuild)

GROUND TRUTH

This is a real, quantity-tracked ledger, not a loose cross-reference
banner. shared/schema.ts already has `progressEntries.materialOutcome`
(fully_reusable/partly_reusable/unsuitable) with `reusableQty`, plus two
dedicated ledger tables: `cutFillOpeningBalances` (available quantity per
source excavation) and `cutFillConsumptions` (the actual allocation of a
specific quantity from a specific source into a specific fill row, with a
constraint ensuring exactly one source per consumption row). Server-side,
these are correctly maintained across create/draft-update/submit/edit/
delete. Client-side, client/src/components/CutFillOutcomeControls.tsx
already renders exactly the Required / Available / Allocated / Uncovered
view, with per-source allocation inputs capped at each source's available
quantity — this already matches the desired behavior:
Cut Material Available / Cut Material Used in this entry / Balance
Available.

THE ACTUAL GAP

This rich ledger view only appears for a fill row when the Execution
Arrangement behind it is specifically typed `reused_excavated` with a
`sourceExcavationBoqItemId` set. For any other arrangement type
(vendor-delivered, client-supplied, etc.) no ledger UI shows — which is
correct, since those fills do not draw from project-cut material. The
likely real-world problem is that this prerequisite setup step on the
Execution Arrangement is easy to miss or not obvious to the person
preparing it, not that the feature is unbuilt.

REQUIRED WORK

Do NOT build a new cut-to-fill mechanism. Instead:
1. Confirm with a concrete example (the same embankment-with-excavated-
   earth scenario from the recording) that when the Execution Arrangement
   is correctly set to `reused_excavated` with a source excavation item,
   the existing ledger view appears and behaves as: Required vs Available
   vs Allocated vs Uncovered, exactly as designed.
2. If, in the recording's example, the arrangement was NOT set up this
   way and that is why the linkage looked incomplete, make that
   prerequisite more visible/discoverable at the point where a fill
   activity is being entered (e.g. a clear prompt: "This is Embankment
   with Excavated Earth — link it to an excavation source to track cut
   material usage" when no `reused_excavated` arrangement is linked yet),
   rather than silently letting the fill proceed with no material
   traceability.
3. Report which of these two situations was actually the case.

PART 6 — SUBMISSION VALIDATION SHOWS RAW ERROR CODES INSTEAD OF THE REAL
MESSAGE (CONFIRMED, EXACT ROOT CAUSE — THIS IS A PRECISE, HIGH-VALUE FIX)

GROUND TRUTH — EXACT ROOT CAUSE

server/routes.ts's `validateProgressProgrammeLinks()` already produces a
specific, human-readable message naming the exact activity and reason
(e.g. "Progress entry 'X': the actual execution side (LHS/RHS/Both
Sides/Full Width) is required for chainage-based work", or a specific
programme-bar mismatch reason). The four DPR endpoints that call it
(create, draft-update, submit, version-edit) all respond with:
  res.status(400).json({ message: linkError, error: "PROGRAMME_LINK_INVALID" })
i.e. the real, useful message is put in the `message` field, and the
machine-readable code is put in the `error` field.

client/src/lib/apiError.ts then builds the object the UI actually uses,
and it prioritizes `json.error` over `json.message`:
  message: typeof json.error === "string" ? json.error
          : typeof json.message === "string" ? json.message
          : body
Because the server put the CODE under `error` (not the message), this
picks up the literal string "PROGRAMME_LINK_INVALID" as the "message",
and the real per-activity explanation is discarded before it ever reaches
the screen. `code` in the same object ends up undefined (apiError.ts only
reads `json.code`, which was never set), so
client/src/lib/dprErrors.ts's dedicated `if (code === "PROGRAMME_LINK_INVALID")`
branch never matches either, and it falls through to the generic 400
handler that just prints whatever ended up in `message` — the raw code.

This same field-naming mismatch likely affects other DPR-validation
codes emitted the same way (at minimum check QUANTITY_SOURCE_INVALID and
MATERIAL_OUTCOME_INVALID for the identical pattern — DPR_NOT_READY
happens to still work today only because dprErrors.ts has an extra
string-matching fallback specific to that one code).

REQUIRED FIX

Pick ONE consistent convention and apply it everywhere DPR validation
responds with a machine code, rather than patching this one string:
- Preferred: change the four DPR-validation response sites in
  server/routes.ts to send the machine token under `code` and the human
  message under `message` (i.e. swap the two field names used today),
  matching what apiError.ts already expects for `code`. Confirm this
  does not break any other consumer of these endpoints that might already
  depend on the current field names — search for `.error ===` or similar
  checks against these specific literals before changing the response
  shape.
- Alternative if the above is judged risky: fix apiError.ts to prefer
  `json.message` over `json.error` when both are present as strings, and
  use `json.error` (or `json.code`) only to populate the `code` field.
State which approach was taken and why.

Whichever is chosen, the end result must be: submitting a DPR with an
invalid programme link (or any of the other affected codes) shows the
real, specific, per-activity message on screen — never a bare internal
constant. Also investigate whether any currently-hidden or inapplicable
fields are being incorrectly treated as mandatory by this validation path
(the user reported entering "everything" and still being blocked) —
report what you find rather than assuming the message fix alone resolves
every case.


PART 7 — EXECUTION ARRANGEMENT OUTCOME LINKED TO DPR (CONFIRMED GAP, NEW
CAPABILITY)

GROUND TRUTH

`workProgramBars` (shared/schema.ts) is the planned execution item DPR
already links against via `progressEntries.programmeBarId` (a real FK,
validated server-side by Part 6's function for side/BOQ-item/scheduled
compatibility). It has no field capturing a specific day's execution
outcome — no executed/partially executed/not executed/cancelled/
suspended/rescheduled vocabulary exists anywhere in the schema.
`earthworkArrangements.status` is a different concept entirely — it is
the arrangement's own approval workflow status (draft/submitted/approved/
rejected/cancelled), not a per-day outcome for planned work.

REQUIRED WORK

For each relevant execution arrangement / programme item, let the DPR
(or a dedicated step tied to it) record an outcome:
- Executed
- Partially Executed (record actual executed quantity/resource use)
- Not Executed
- Cancelled
- Suspended
- Early Closed
- Rescheduled (capture the new date)

with a reason selected from a list (Rain, Site not ready, Client
instruction, Equipment breakdown, Vendor unavailable, Material
unavailable, Work completed early, Change in programme, Other) plus free
text for Other.

The original planned arrangement must remain in history — do not delete
or overwrite it; record the outcome as an additional linked record
alongside it. Show Planned vs Actual outcome together wherever the
programme bar or its linked DPR entries are viewed. Reuse the existing
`programmeBarId` link already present on `progressEntries` as the
connection point — do not invent a second, parallel link between DPR and
programme.

INVESTIGATE FIRST: confirm the minimal additive schema needed (most
likely a new small table keyed to workProgramBars.id plus date, holding
outcome/reason/reschedule-date/actual-quantity) and report the proposed
shape before migrating — do not guess at a larger schema than necessary.

PRESERVE HISTORY — DO NOT MODEL THIS AS ONE MUTABLE STATUS

One programme bar may go through multiple outcome events over time — for
example Suspended on 30 Aug, then Rescheduled or Executed on 2 Sep. Do
NOT design this as a single row per bar that gets overwritten each time
its disposition changes. Each outcome event must be its own record (i.e.
the new table is append-only / one row per event, not one row per bar),
so earlier Suspended/Rescheduled actions remain visible and auditable
alongside the current one. The most recent event can be shown prominently
as the bar's current disposition, but the full event history must remain
queryable — this is exactly the "arranged for tomorrow, didn't happen,
moved to another day" case that matters in practice.

REQUIRED WORK

free-text-fallback for now.
