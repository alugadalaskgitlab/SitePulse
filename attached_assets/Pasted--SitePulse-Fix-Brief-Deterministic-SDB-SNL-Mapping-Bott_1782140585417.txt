## Background — what is broken and why

The planning engine (`shared/planningEngine.ts`) already does bottleneck-resource
duration (`calculateAutoDurationFull`) and BOM aggregation (`calculateBomDemand`)
correctly. The Work Programme already calls them. The problem is **upstream**, in two
places:

### Bug 1 — SNL/SDB mapping is fuzzy-text only
`server/snlAutoMapper.ts` maps each BOQ item to an SNL (Standard Norms Library) item by
**scoring the description and short label** (Jaccard keyword overlap). When tender BOQ
wording differs from MoRTH SDB wording, the score stays below the 0.80 confidence
threshold, the item is left `unmapped`/`needs_review`, **no recipe is applied**, and
therefore there is no equipment / labour / material to drive duration or BOM.

**Fix:** add a **deterministic mapping path**. Let the user put the SDB/SNL norm code
(e.g. `5.05`, `4.14`, `3.16`) in a dedicated **"SNL / SDB Code"** column in the BOQ
import. If that code exactly matches an `snl_items.item_code`, map it directly with
confidence `1.0` and apply the recipe — **skip all fuzzy scoring**.

### Bug 2 — Mapped items still show duration = 0
`storage.applySnlMappingToRecipes()` copies SNL equipment into `boq_item_equipment`
**but never sets `planningEquipmentTypeId` or `equipmentMasterId`**. The Work Programme
reads equipment output-per-hour from the linked planning type / equipment master
(`getBoqItemsWithRecipes`). With no link, `outputTheoretical`/`standardOutputs` are
`null`, `getEffectiveOutputPerHr` returns 0, and the bottleneck duration is 0 months.

**Fix:** when applying the recipe, match each SNL equipment to a row in
`planning_equipment_types` by name and store `planningEquipmentTypeId`, so the recipe
equipment carries a real output norm and the slowest one becomes the bottleneck.

### 4. `server/snlAutoMapper.ts` — deterministic code match BEFORE fuzzy scoring

**(a)** In `autoMapBoqItems`, add `snlCode` to the BOQ select. Find the
`.select({ id: boqItems.id, itemCode: boqItems.itemCode, ... })` block and add:

```ts
  const boqRows = await db
    .select({
      id: boqItems.id,
      itemCode: boqItems.itemCode,
      snlCode: boqItems.snlCode,
      description: boqItems.description,
      unit: boqItems.unit,
      workCategory: boqItems.workCategory,
    })
    .from(boqItems)
    .where(inArray(boqItems.id, boqItemIds));
```

**(b)** Inside `for (const boqRow of boqRows) {`, immediately after the opening
`try {`, insert this deterministic block (it runs before the fuzzy scorer and `continue`s
on success):

```ts
      // ── 0. Deterministic SNL-code match (highest priority) ──────────────
      // If the BOQ row carries an explicit SDB/SNL norm code, map straight to
      // the SNL item with that exact item_code. No fuzzy description parsing.
      const explicitCode = (boqRow.snlCode ?? "").trim().toLowerCase();
      if (explicitCode) {
        const directSnl = snlRows.find(
          (s) => s.itemCode.trim().toLowerCase() === explicitCode,
        );
        if (directSnl) {
          await db
            .insert(snlBoqMappings)
            .values({
              boqItemId: boqRow.id,
              snlItemId: directSnl.id,
              projectCategory: "MEDIUM",
              gradingVariant: null,
              mappedBy: "auto",
              isAutoMapped: true,
              confidenceScore: 1,
              notes: `Mapped by SNL code "${directSnl.itemCode}"`,
            })
            .onConflictDoUpdate({
              target: snlBoqMappings.boqItemId,
              set: {
                snlItemId: directSnl.id,
                isAutoMapped: true,
                confidenceScore: 1,
                mappedAt: new Date(),
                notes: `Mapped by SNL code "${directSnl.itemCode}"`,
              },
            });

          let recipesApplied = false;
          try {
            await storage.applySnlMappingToRecipes(boqRow.id, directSnl.id, "MEDIUM", null, "auto");
            recipesApplied = true;
          } catch (recipeErr) {
            console.error(`[autoMapper] code-match recipes failed for boqItemId=${boqRow.id}:`, recipeErr);
          }

          await db
            .update(boqItems)
            .set({ mappingStatus: recipesApplied ? "mapped" : "needs_review" })
            .where(eq(boqItems.id, boqRow.id));
          continue; // done — skip fuzzy scoring for this row
        }
      }
```

> Everything below this block (the existing fuzzy scorer) stays unchanged and is the
> fallback for rows that do not carry an SNL code.

### 5. `server/storage.ts` → `applySnlMappingToRecipes()` — link equipment to planning types (fixes duration = 0)

Find `async applySnlMappingToRecipes(`. **Before** the `await db.transaction(async (tx) => {`
line, add a planning-equipment-type resolver:

```ts
    // Resolve a planning_equipment_type for each SNL equipment so the recipe
    // equipment carries an output-per-hour norm. Without this the Work Programme
    // cannot compute bottleneck (slowest-resource) auto-duration.
    const planTypes = await db
      .select({ id: planningEquipmentTypes.id, name: planningEquipmentTypes.name })
      .from(planningEquipmentTypes)
      .where(eq(planningEquipmentTypes.isActive, true));

    const matchPlanTypeId = (snlEquipType: string): number | null => {
      const t = (snlEquipType ?? "").trim().toLowerCase();
      if (!t) return null;
      // 1) planning name contains the SNL type (e.g. "Hydraulic Excavator" ⊂ "Hydraulic Excavator (0.9 CUM)")
      const contains = planTypes.find((p) => p.name.toLowerCase().includes(t));
      if (contains) return contains.id;
      // 2) token-overlap fallback
      const tw = new Set(t.split(/\s+/).filter((w) => w.length > 2));
      let bestId: number | null = null;
      let bestScore = 0;
      for (const p of planTypes) {
        let s = 0;
        for (const w of p.name.toLowerCase().split(/\s+/)) if (tw.has(w)) s++;
        if (s > bestScore) { bestScore = s; bestId = p.id; }
      }
      return bestScore > 0 ? bestId : null;
    };
```

Then in the `tx.insert(boqItemEquipment).values(...)` mapping, add the
`planningEquipmentTypeId` field:

```ts
        await tx.insert(boqItemEquipment).values(

            equipmentName: e.equipmentType + (e.equipmentSpec ? ` (${e.equipmentSpec})` : ""),

            qtyPerBoqUnit: e.derivedPerUnit ?? 0,
            count: 1,
            notes: e.notes ?? `SNL ${itemFull.itemCode} [${projectCategory}]`,

```

## ADDENDUM — important for an EXISTING BOQ that has NO MoRTH SDB code column

The "Takkadpally-Sirur" BOQ imported from Road Estimator has tender item codes +
descriptions but (typically) **no MoRTH SDB norm code column**. Two things follow:

### A. FIX 2 (duration link) is the universal fix — applies to MANUAL mapping too
The app's manual mapping action `POST /api/snl/mappings/:boqItemId/apply` calls the SAME
`applySnlMappingToRecipes()`. So **today, even when you manually pick the correct SDB
norm for a BOQ item in the app, the duration still comes out 0** because the recipe
equipment isn't linked to a planning type. After applying **FIX 5** above, manual
mappings produce correct bottleneck durations and BOM. **After deploying FIX 5, re-apply
the mappings** (admin → "Remap project" `POST /api/boq/projects/:id/remap`, or re-pick in
the mapping screen) so existing items get the new equipment links.

### B. Optional fallback — match on the existing "Item Code" column (no new SDB column needed)
If you would rather not add an SDB-code column, also let the deterministic matcher try
the BOQ's existing `itemCode` against `snl_items.item_code`. In
`server/snlAutoMapper.ts`, inside the deterministic block from FIX 4(b), broaden the
lookup key:

```ts
      // Try the explicit SNL code first, then fall back to the BOQ item code.
      const explicitCode = (boqRow.snlCode ?? "").trim().toLowerCase()
        || (boqRow.itemCode ?? "").trim().toLowerCase();
```

This only fires when the BOQ item code happens to equal an SDB norm code, so it is safe
(no false positives) and needs no schema/UI change. For reliable results, the cleanest
route is still: add SDB codes per line, **or** map each item once in the app's SNL
mapping screen (which writes the real `snl_id`).

### Recommended order for your existing project
1. Apply **FIX 5** (duration link) + **FIX 4(b)** deterministic block with the 5(B)
   item-code fallback. Run `npm run db:push`, restart.
2. Map your BOQ items to SDB norms — either by the item-code/SDB-code match, or manually
   in the SNL mapping screen.
3. Run **Remap project**, then open Work Programme (AUTO mode) and BOM & Demand to verify
   durations and quantities populate.
