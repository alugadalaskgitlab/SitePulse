BACKGROUND — FIX 0: SITE FILTER DROPDOWN SHOWS DUPLICATE ENTRIES PER DPR REVISION, NOT ONE PER SITE
Confirmed real, separate bug found during live testing. The Site filter dropdown (`ProgressReport.tsx:166`, `{(report?.sites ?? []).map((s) => <SelectItem key={s} value={s}>{s}</SelectItem>)}`) is populated from `report.sites`, built server-side in `assembleProgressReport` (`server/routes.ts:16140`):
```ts
const dprSites = Array.from(new Set(entries.map((e) => e.site).filter((s): s is string => !!s))).sort();
```
This dedupes on the RAW `dprs.site` string. But `dprs.site` gets a provenance suffix appended every time a DPR is edited/copied (per `shared/siteName.ts:1-9`, e.g. `"ALLADURG PWD ROAD TO PAMPAD – Edited by Admin – 2026-09-16 05:43:09"`) — this is intentional DPR revision tracking, not a site name. Because the dedup runs on the raw suffixed string, every distinct edit timestamp for the SAME physical site produces its own dropdown entry, which is exactly what the person saw live (one real site appearing 4+ times, each with a different "Edited by ... [timestamp]" tail).

The fix already has the right tool available: `shared/siteName.ts` already exports `getBaseSiteName()`/`normalizeSiteName()` specifically to strip this suffix, and is already used correctly elsewhere in this codebase (e.g. `server/routes.ts:16091-16106` via `storage.getSites()`/`siteMatchesPermitted`). A real `sites` master table also already exists (`shared/schema.ts:1776`).
