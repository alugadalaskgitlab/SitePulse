BACKGROUND — confirmed by direct code review and a screen recording of the failure

Bug 1 — editing an already-ordered Purchase Indent fails with a 500 and is destructive by design.
`server/routes.ts`'s `PUT /api/purchase-indents/:id` (~line 10315) calls `storage.updatePurchaseIndent(id, validatedData)`. That function (`server/storage.ts` ~line 16948) handles ANY edit to a PI — even just reopening and clicking Update with no real change — the same way regardless of status or how far any item has progressed:
1. It deletes every row in `purchase_indent_item_history` for the indent's current item IDs.
2. It deletes every row in `purchase_indent_items` for the indent (`DELETE FROM purchase_indent_items WHERE indent_id = id`).
3. It re-inserts fresh item rows from the submitted form data — but the re-insert only carries `description/spec/partNo/qty/uom/purpose/priority/materialId/estRate/estAmount/requiredBy`. None of the purchase-tracking fields (vendor, rate actually agreed, orderedQty, totalPurchasedQty, totalAcceptedQty, totalRejectedQty, linkedReceiptId, linkedGrnId, orderNo, orderedByUserId, paymentMode, purchasedBy, etc.) are carried over.

This is unsafe the moment any item has moved past "pending": `shared/schema.ts`'s `purchaseOrders` table (~line 1959) has `purchaseIndentItemId` as a NOT NULL foreign key to `purchaseIndentItems.id` with a unique "one active PO per item" index — so once an item has a PO/vendor assigned (status "Order Placed", exactly the WMM item's state in the reproduction), deleting that item row either (a) throws a foreign-key violation, which is almost certainly the real cause of the generic 500 "Failed to update purchase indent" seen on every retry in the recording, or — if the FK is somehow not enforced in a given deployment — (b) silently deletes a row real other tables still reference, orphaning data. Other tables that also reference an indent item (`pi_item_transactions`, `store_grn_items`, `pending_plant_receipts`, `service_completions` — confirmed via `shared/schema.ts` grep for `indentItemId`) make this worse: even a successful delete-and-reinsert would leave those tables pointing at item IDs that no longer exist, or at a brand-new row that looks unrelated to the history it should be attached to.
Net effect confirmed on video: user reopens PI HLC/PI/2026/0004 (WMM item, status "Order Placed", vendor SARVANA METAL INDUSTRIES already assigned) with no intent to change anything material, clicks "Update Indent", and gets `500: {"message":"Failed to update purchase indent"}` — repeatably, identically, on every retry across roughly 30 seconds of the recording. This is not transient; it is structural, and it currently makes it impossible to make ANY edit (even a harmless one, like fixing a typo in General Remarks) to a PI once any one of its items has an order placed against it.

Bug 2 — the PI-linked delivery trip screen shows "Remaining: MT" with the quantity missing.
`client/src/components/purchase-indent-delivery.tsx`'s `PurchaseIndentDeliveryPanel` builds the "Log Site Delivery →" link (~line where `href` is set for `item.receivingLocation === "site"`) as:
`/site/material-trips?piIndentId=${indentId}&piItemId=${item.id}&material=${...}&uom=${...}&site=${...}`
— it never includes a `qty` (or remaining-quantity) parameter. `client/src/pages/SiteMaterialTrips.tsx` (~line 49-65) parses `piParams` straight from the URL, including `qty: p.get("qty") || ""`, and uses it in two places: the PI-linked banner at ~line 494 (`Remaining: <strong>{piParams.qty} {piParams.uom}</strong>`) and the Quantity field's initial value (~line 97, `quantity: piParams.qty || ""`). Because the link never sends `qty`, both come back blank — the banner literally reads "Remaining: MT" with no number, and the Quantity input doesn't get a sensible starting value either. Confirmed on video at the "Log Material Trip" screen reached via "Log Site Delivery →" from the same WMM item.
Separately, note that `purchase-indent-delivery.tsx` already computes a correct "X of Y delivered" figure via its own `deliveryProgress()` helper (ordered/approved qty vs `item.deliveredQty`) — the remaining quantity for the link is simply `target - delivered` from that same logic and does not need to be invented; REUSE it, do not write a second remaining-quantity calculation.
