APPROVED TO PROCEED WITH BATCH 06F USING THE JSONB + STABLE LINEKEY ROUTE,
WITH THE FOLLOWING CORRECTIONS.

No DB schema change is approved or required.

--------------------------------------------------
1. APPROVE STABLE LINEKEY
--------------------------------------------------

Add a stable client-generated `lineKey` to every NEW requirement line:

- material
- equipment
- labour
- immediate

Generate it ONCE when the Engineer creates the row.

It must survive:

- Save Draft
- submit
- reopen
- row reorder
- row insertion/deletion around it
- allocation updates

Do NOT regenerate lineKey from:
- array index
- row order
- label/material name

Existing historical requirement records without lineKey remain readable
through the existing index fallback.

For NEW records, allocationStatus must key per-line allocation data by
lineKey, with index retained only as compatibility metadata/fallback.

--------------------------------------------------
2. DO NOT CHANGE ENGINEER UX
--------------------------------------------------

Engineer continues raising only the requirement.

Do NOT add:

- Vendor selector
- Execution Arrangement selector
- Responsibility selector
- Fulfilment Type selector

to SiteRequirementNew.

Engineer simply states:

what is required
for what planned work/reach
and how much.

--------------------------------------------------
3. PRESERVE PROGRAMME BAR ID WHEN IT IS ACTUALLY KNOWN
--------------------------------------------------

Current plannedWork does not persist programmeBarId.

If a requirement is created from / against an identified programme bar,
preserve that programmeBarId inside the existing plannedWork JSON.

This is a JSON-shape addition only.

Do NOT add a DB column.

Do NOT attempt to infer an exact programmeBarId later from loose text
matching.

Arrangement-resolution priority becomes:

1. Exact programmeBarId allocation ONLY when programmeBarId is genuinely
   known/persisted.

2. Compatible BOQ item + reach/scope.

3. Compatible BOQ item.

4. No applicable arrangement
   → HLC/Internal context.

Do not call a probabilistic match "exact programme bar".

--------------------------------------------------
4. DAILY FULFILMENT MODEL
--------------------------------------------------

Extend the existing per-line allocationStatus entry with optional:

- lineKey
- fulfilmentType
- arrangementId
- agencyNameSnapshot
- exceptionReason
- updatedBy
- updatedAt

Use:

fulfilmentType:
- "hlc"
- "arrangement"
- "other_agency"

Do NOT create a new state machine.

Existing operational status remains:

Arranged
Available in store
Issued
Direct supply arranged
etc.

Fulfilment fields only answer:

"Who/how is this requirement being fulfilled tomorrow?"

--------------------------------------------------
5. `hlc`
--------------------------------------------------

Use when the requirement is being handled internally by HLC / the main
contractor.

No Execution Arrangement is required.

Example:

Status:
Arranged

Fulfilment:
HLC / Internally Arranged

No "Arrangement required" warning.

--------------------------------------------------
6. `arrangement`
--------------------------------------------------

Use when the allocating authority chooses an applicable existing Execution
Arrangement.

Persist:

- arrangementId
- agencyNameSnapshot

The arrangement ID is authoritative.

The name snapshot is for readable historical context.

Do not modify the standing arrangement.

--------------------------------------------------
7. `other_agency` — DAILY EXCEPTION
--------------------------------------------------

Support the real operational case:

Standing arrangement:
ABC Earthworks

But ABC cannot supply tomorrow.

PM arranges:
XYZ Infra for this day.

If XYZ does NOT have an applicable standing Execution Arrangement, allow:

Fulfilment Type:
Other Agency / Daily Exception

Agency:
XYZ Infra

Reason:
Primary vendor unavailable

Persist:

- fulfilmentType = other_agency
- agencyNameSnapshot
- exceptionReason
- arrangementId = null

This must NOT:

- create a new Execution Arrangement;
- transfer ABC's standing reach;
- alter arrangement allocations;
- alter BOM responsibility;
- expand another vendor's permanent scope.

It is only tomorrow's operational fulfilment record.

--------------------------------------------------
8. WHEN AN ALTERNATE VENDOR HAS AN EXISTING COMPATIBLE ARRANGEMENT
--------------------------------------------------

If XYZ already has a compatible active Execution Arrangement, prefer:

fulfilmentType = arrangement
arrangementId = XYZ arrangement

rather than other_agency.

Show all compatible arrangements to the allocator.

Do not force selection of the arrangement normally assigned to that exact
stretch if PM has deliberately chosen another compatible agency for the
day.

Record an exception reason where the daily allocation differs from the
normal/strongest arrangement suggestion.

--------------------------------------------------

--------------------------------------------------

Do NOT alter calculateBomDemand or the arrangement exclusion engine.

The investigation confirms that BOM is already arrangement-aware for:

- Equipment
