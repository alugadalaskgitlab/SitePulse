INSTRUCTION LABOUR-01: Let each Labour Log row optionally record individual worker names, for both a contractor's crew and one-off individual local labour

READ THIS FIRST — SCOPE DISCIPLINE
This needs a new child table — genuinely new schema, not a reuse of something existing. Part A is a design/mapping plan — STOP after Part A and share it, including the exact proposed schema, before writing any implementation code. Do not touch HOME-01, DIESEL-04/05, NAV-01, VB-27, MAT-03/04, VENDOR-01/02/03, PERM-01/02, the `personnel`/`activityPersonnel` tables, or any DPR-13 through DPR-19 real-screen work beyond what's explicitly described below. Do not publish automatically.

BACKGROUND — confirmed by direct code review
`shared/schema.ts`'s `labourLogs` table (lines ~322-335: `dprId`, `category`, `gender`, `count`, `task`, `contractor`, `boqItemId`, `structureId`) is a pure aggregate headcount — there is no field anywhere for an individual worker's name, and no informal workaround exists in any other field (confirmed — placeholders on `task`/`contractor` are clearly scoped to their own purpose). The real entry screen is `client/src/pages/GuidedDpr.tsx`'s Step 4 "Labour" (~lines 2819-2870, row type `SimpleLabourRow` ~lines 170-175). A separate, older `LabourSection` also exists in `client/src/components/DprForm.tsx` (~lines 708-812) with fewer fields (category/gender/count only, no task/contractor/link) — Part A must confirm whether this older component is still actually reachable/used anywhere live, or dead code, before deciding whether it also needs this feature.

The closest existing precedent in the app is the Plant Shift Log's manpower feature: `plantShiftLogManpower` (schema.ts ~lines 1444-1452) is a simple child table (`shiftLogId`, `name`, `role`, `contractorName`, `category`, `gender`) recording individual names against a parent shift-log record, with optional dedup/relabel infrastructure (`plantShiftLogManpowerRelabelBatches`/`Snapshots`/`DismissedDups`/`CustomAliases`) for when names get typed inconsistently. This is a proven pattern for the same underlying problem — REUSE THE SHAPE of this approach, not the dedup/alias machinery (that's explicitly out of scope for this instruction, see WHAT NOT TO DO).

WHAT THIS SHOULD DO
Each Labour Strength row (Category/Gender/Count/Task/Contractor as they exist today) gets an optional way to list individual worker names under it — free text, typed fresh, not a persistent master roster to maintain ahead of time (matching the Plant Shift Log manpower's free-text approach, minus its dedup tooling for now). This should cover, with the SAME mechanism, both real cases:
- A contractor's crew: one row (Contractor = "Raju Gang", Count = 10), with up to 10 names optionally listed underneath.
- Local/individual labour for the day: a row with Count = 1 (or a small number) and one or more names, exactly as free as any other row — no special "individual mode" needed, it's the same feature used minimally.
Count remains the source of truth for headcount reporting/analytics — names are a supplementary, fully optional detail. Nothing should require names to be entered; a person must still be able to just enter a Count and move on, exactly as today.
