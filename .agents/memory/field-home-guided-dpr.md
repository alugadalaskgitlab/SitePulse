---
name: Field Home + Guided DPR Flow
description: Role-based (not device-based) engineer landing page and guided step-by-step DPR entry, adaptive across mobile/tablet/desktop, layered on top of the existing dashboard/DPR form without touching backend logic.
---

Field roles land on `FieldHome.tsx` (and get guided step-by-step DPR entry in `SiteEntry.tsx`) by ROLE, on every device — mobile, tablet, and desktop. Device only changes layout, never which workspace/flow is shown. Managers/admins always get the classic `Home.tsx` dashboard and classic full-page DPR by default. The guided DPR flow is a presentation-only wrapper around the same Card sections in `SiteEntry.tsx` (conditional `showStep(n)` rendering) — no new form state, validation, autosave, or mutation logic is duplicated.

**Why:** originally this was mobile-gated (`isMobileViewport && !isAdmin && isFieldEngineer`) on the mistaken assumption that "field workflow" meant "phone". The product rule was later corrected: role decides the workspace, device decides layout only — an engineer on a desktop still wants Field Home, not the manager dashboard. The frontend `AuthUser` has an explicit admin-settable `isFieldEngineer` boolean (not derived from `isManager`, which is true for every non-admin user — a known trap, see `is-manager-always-true.md`).

**How to apply:** `Home.tsx` defaults to Field Home via `!isAdmin && isFieldEngineer` (no viewport check); `SiteEntry.tsx` defaults to guided mode the same way. Both use a `useState<boolean|null>` override pattern (`fieldOverride`/`guidedOverride`) so either side can manually toggle between guided/classic views for the session. Use `client/src/hooks/use-device-type.ts` (`useDeviceType()` → `'mobile'|'tablet'|'desktop'`) to vary container width/grid columns in `FieldHome.tsx` and `SiteEntry.tsx`'s guided shell — never to decide whether the field workflow is shown at all. When adding new DPR sections, wrap the Card in the correct `showStep(n)` index per `GUIDED_STEPS` in `SiteEntry.tsx`, and remember it renders unconditionally when not in guided mode.

Also: `drizzle-kit push` can hang on an interactive TUI prompt for *unrelated* pending schema diffs (e.g. a pre-existing unique constraint) even when your own change is a simple additive nullable column. Piped stdin doesn't work with these arrow-key prompts. For a simple additive/nullable column, it's safer to run a direct `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` via `psql "$DATABASE_URL"` instead of fighting the interactive push.
