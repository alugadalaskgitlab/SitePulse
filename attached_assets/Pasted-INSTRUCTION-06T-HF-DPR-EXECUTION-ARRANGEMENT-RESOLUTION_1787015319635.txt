--------------------------------------------------
CONFIRMED ROOT CAUSE
--------------------------------------------------
Real case: TAKKADPALLY-SIRUR, 16/17-Aug-2026. Two earthwork arrangements
were created (Soil/Earth "Reused Excavated" and Earth/Borrow Soil
"HLC Source Outsourced Execution" to Narasimhulu, 10,000 Cum across two
reaches) and have since been APPROVED. The Guided/Detailed DPR still shows
"no supply arrangement" / a PI warning for the matching activities.

Two separate problems, confirmed directly against the code, both must be
fixed together:

1. RESOLUTION: ActivityReceiptStrip.tsx resolves the applicable arrangement
   live, every time, via `resolveApplicableArrangements()` against the
   arrangement's current status + BOQ-item linkage + bar allocations. It
   only ever treats an arrangement as active when its status is exactly
   `approved`, `mobilisation_pending`, or `in_progress` — confirmed
   correct and must stay as-is. What is NOT yet confirmed is why live
   resolution is still failing for these two arrangements now that they
   are approved. Investigate and report, for these exact two arrangements:
   whether each is linked to its BOQ item via a plain `boqItemId` or via
   `boqItemAllocations`, whether `earthwork_arrangement_programme_allocations`
   rows exist for them yet (the auto-allocate-on-approval step may have
   failed silently — check server logs / re-run it and confirm), and
   exactly which check inside `resolveApplicableArrangements` /
   `arrangementCoversItem` is excluding them. Fix whatever is actually
   found — do not guess and patch blind.

2. PERSISTENCE — NOT YET BUILT, CONTRARY TO EARLIER REPORTS: an earlier
   instruction asked for the resolved Execution Arrangement to be saved
   permanently on each DPR progress row (`progress_entries.earthworkArrangementId`
   — the column already exists in schema.ts and is not stripped by
   `insertProgressSchema`). Checked directly: GuidedDpr.tsx, SiteEntry.tsx
   and SiteEdit.tsx have ZERO references to `earthworkArrangementId`, and
   ActivityReceiptStrip.tsx has no prop to accept one — it only ever
   derives `arrangement` fresh, live, every render. This means the strip
   is 100% dependent on live resolution succeeding every single time,
   with no stable fallback — which is exactly the class of failure hit
   here, and will keep recurring for other activities/days until this is
   built. This hotfix must build it now, not defer it again.

--------------------------------------------------
1. PERSIST THE RESOLVED ARRANGEMENT ON THE DPR ROW
--------------------------------------------------
- Add `earthworkArrangementId: number | null` to the progress-row state in
  GuidedDpr.tsx and SiteEntry.tsx (Detailed DPR create). At the point an
  activity's applicable arrangement is resolved (live, via the existing
  resolver), persist its id onto the row — only when the row does not
  already have one set. Include it in the DPR create/draft/submit payload.
  No new endpoint needed; the existing insert mapping already passes the
  field through once the client sends it.
- SiteEdit.tsx (Detailed DPR edit): load and keep a row's existing stored
  `earthworkArrangementId` exactly as saved — never silently recompute or
  overwrite it against current live state, even if the arrangement's
  status, allocation, or the bar context has since changed. Only resolve
  a value for a row that does not yet have one (a brand-new row added
  during that edit session, or an older row saved before this fix
  existed). If the Engineer deliberately changes a row's BOQ item /
  programme-bar context during an edit, re-resolve for the new context —
  that is a genuine change of what is being recorded, not an overwrite of
  history.
- Preserve `earthworkArrangementId` through the DPR clone/version/revision
  path (`cloneDpr` in storage.ts) the same way it already preserves
  `layerNo`.

--------------------------------------------------
2. ActivityReceiptStrip: USE THE STORED ID FIRST, LIVE RESOLUTION AS FALLBACK ONLY
--------------------------------------------------
- Add an optional prop, e.g. `storedArrangementId?: number | null`, to
  ActivityReceiptStripProps. When SiteEdit (and Guided/Detailed once a row
  has been saved once) has a stored value, pass it in.
- When `storedArrangementId` is present: look up that specific arrangement
  directly (by id) for display — do not run the live
  `resolveApplicableArrangements()` matching logic for arrangement
  selection at all in this case. This is what makes an already-submitted
  report stable even if live resolution later breaks again for any
  reason.
- When no stored id is present (new row, or a row saved before this fix):
  fall back to the existing live resolution exactly as today, and persist
  the result per §1 once resolved.
- This does not change how PI/procurement matching (06S) or receipt
  matching (§4 below) work — those remain live/day-specific by design;
  only the EXECUTION ARRANGEMENT identity itself becomes a stable,
  saved fact once set.

--------------------------------------------------
3. COMPACT OPERATIONAL DISPLAY — NOT THE FULL ARRANGEMENT RECORD
--------------------------------------------------
Replace the current confusing pair of messages with one compact,
context-appropriate line. Use the arrangement data already available
(`allocatedQty`, agency/vendor name, and the existing received-trip
aggregation) — no new data model needed.

Reused excavated / cut-fill (relevance "none"):

No applicable arrangement resolves at all (nothing set up for this

  (neutral — never suggest re-approving something that is not the actual
  problem)

4. REMOVE MISLEADING "AWAITING APPROVAL" TEXT
--------------------------------------------------
- If the resolved (or stored) arrangement's status is already
  `approved`/`mobilisation_pending`/`in_progress`, never show any
  "awaiting approval" wording — show §3's compact tag instead.
- Only show "awaiting approval" when the actual arrangement backing this
  activity is genuinely still `draft`/`submitted` — and in that case, name
  it plainly, e.g. "An arrangement exists for this stretch but is awaiting
  approval," not a generic "no arrangement" message.
- If nothing resolves at all, use §3's neutral "not linked" message —
  never tell the user to approve something when no arrangement was found
  in the first place.
