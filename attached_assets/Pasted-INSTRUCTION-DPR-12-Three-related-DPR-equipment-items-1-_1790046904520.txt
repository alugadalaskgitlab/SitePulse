BACKGROUND — FIX 2: OPENING READING DOES NOT CARRY FORWARD FROM THE TRUE LAST LOGGED DATE
1. client/src/components/DprEquipmentCompact.tsx (~line 137-148) already has a working continuity fetch for diesel tank balance: on adding an equipment row, it calls `GET /api/equipment/:id/latest-confirmed-diesel-tank?beforeDate=...&site=...` and auto-fills `openingDiesel` from the machine's last CONFIRMED tank balance before the current date — correctly regardless of how many days have passed since that machine was last logged (not just literally "yesterday").
2. The "Opening Reading" (Opening Odometer/Opening Meter) field (~line 186) has NO equivalent continuity fetch at all — it is a bare, always-blank input (`placeholder="Not recorded"`) with no auto-fill logic whatsoever. This is confirmed as the root cause of the reported gap: after a machine goes unlogged for several days (no work on site), its next entry's Opening Reading comes up empty instead of pulling the machine's actual last recorded closing reading.

FIX 2
a. Add an equivalent continuity fetch for Opening Reading, following the exact same pattern as the diesel tank continuity fetch (~line 137-148): on adding/opening an equipment row with no `openingReading` already set, call a "latest confirmed closing reading before this date" lookup for that equipment (add a new endpoint mirroring `/api/equipment/:id/latest-confirmed-diesel-tank`, e.g. `/api/equipment/:id/latest-confirmed-reading`, or extend the existing endpoint to also return the last closing reading if that's simpler — your judgment on the cleanest implementation) and auto-fill `openingReading` from it.
b. This must search backward to the true last logged entry for that equipment, not just the literal previous calendar day — mirroring the diesel version's correct "beforeDate" behavior exactly.
c. Like the diesel version, this must only auto-fill when `openingReading` is not already set (never overwrite a value the person has already entered or that came from a linked source), and must respect `site` scoping the same way the diesel fetch does.
d. This applies to both hour-meter and odometer machines — the label already correctly adapts ("Opening Odometer" vs "Opening Meter"); only the auto-fill behavior is being added.

BACKGROUND — FIX 3 (NEW FEATURE): EXPLICIT DAILY EQUIPMENT STATUS (WORKING / IDLE / BREAKDOWN) + A FLEET STATUS VIEW
1. Today, the only way to signal a hired or owned machine was idle on a given day is an informal workaround: entering the same value for Opening and Closing reading. This is ambiguous — it looks identical to someone simply forgetting to update the reading, and it captures no reason (no work available, operator unavailable, breakdown).
2. The person wants: an explicit status per equipment per day, and a place to see, across all machines (hired and owned, especially monthly-hire), how much of the time each one has actually been operating vs idle, and why.
3. Explicitly OUT OF SCOPE for this fix: do not modify the existing breakdown/maintenance recording system (downtime hours, breakdown deduction logic already used in vendor bill hire calculations) — that integration is a deliberate, separate future decision. For this batch, "Breakdown" is simply one selectable status value with a reason field; it does not need to create or link to a maintenance record yet.

FIX 3
a. Add a `usageStatus` field to the equipment daily log entry (server/storage.ts / shared/schema.ts's `equipmentLogs` table, and the equivalent plant-usage entry table if it captures the same per-day concept — check both), nullable, with values: `"working"`, `"idle_no_work"`, `"idle_no_operator"`, `"breakdown"`. Null/unset means "not specified" — treat exactly as today (inferred from readings) for full backward compatibility with existing rows.
b. Add a `usageStatusReason` free-text field alongside it, required in the UI whenever `usageStatus` is anything other than `"working"`.
c. In client/src/components/DprEquipmentCompact.tsx, add this status selector to the equipment row — place it near the top of the card (by Machine/Operator/Entry-Type details), before the Opening/Closing reading fields, since it should inform how the person fills the rest of the row (e.g., an explicit Idle day may still have identical opening/closing readings, but now that's clearly intentional and explained, not ambiguous).
d. When `usageStatus` is set to `"idle_no_work"` or `"idle_no_operator"` (i.e. the machine did not run at all that day), AUTO-FILL Closing Reading to match Opening Reading, and diesel-related fields (Diesel Issued/Added, and for Plant Stock rows the Closing/Physical Dip) to match their opening equivalents — so the person can select the status and move straight on to the next equipment or DPR section without manually typing matching numbers. This must remain EDITABLE, not locked: keep it a helpful default, not a hard rule, since the person can still change any of these fields if needed.
e. When `usageStatus` is `"breakdown"`, do NOT auto-fill the same way by default — a machine can genuinely work part of the day before breaking down, so Closing Reading and diesel fields must stay exactly as the person enters them (or blank) for a breakdown day, with no assumption of zero movement. Do not remove any "did you forget to update this" warning that exists for a genuine data-entry slip — only suppress it for the two idle statuses in point (d), where matching values are now an expected, intentional outcome of the auto-fill, not a slip.
e. Do NOT remove or repurpose the existing entry-type/basis fields (daily/hourly/trip_based/monthly/time_meter) — `usageStatus` is a new, additional concept layered on top of the existing per-day entry, not a replacement for anything.
