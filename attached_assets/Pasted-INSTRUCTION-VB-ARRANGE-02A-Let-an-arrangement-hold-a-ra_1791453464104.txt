INSTRUCTION VB-ARRANGE-02A: Let an arrangement hold a rate per trip size. Storage and entry only — no billing change.

READ THIS FIRST
This batch adds ONE thing: the ability to record, on an Execution Arrangement, a rate per trip size — e.g. 600 CFT / 800 CFT / 1000 CFT, each with its own flat per-trip amount.
It does NOT change any bill, any rate card, any pricing, or how any trip is billed. The billing side is VB-ARRANGE-02B. Do not start it.
Do NOT publish. Show the Publish preview and STOP.
Do NOT change, backfill, infer or correct any existing trip or arrangement row.
Do NOT touch the vendor rate card system (`vendor_rate_cards`, `applyTransportCard`, `shared/vendorBillTransport.ts`). This is a separate, arrangement-level rate and must not be mixed into it.
PARKED — do not investigate or touch: LDO, startup data repair jobs, stock balances, user permissions, trips list, filters.
Commit and push all work to GitHub before reporting.

WHY
The owner engages a vendor to extract soil from a borrow area HLC itself identified, haul it, and dump it at the work stretch. The vendor is paid a FLAT AMOUNT PER TRIP, and that amount differs by trip size: one rate for a 600 CFT trip, another for 800 CFT, another for 1000 CFT.

That rate is ALL-INCLUSIVE — extraction, loading, haulage and dumping are all covered by the single per-trip figure. There is no separate transport payment for these trips. (VB-ARRANGE-02B will enforce that on the bill; this batch only stores the rates.)

Today there is nowhere to put this. `earthworkArrangements.agreedRate` (shared/schema.ts ~4548) is a single `real`, documented "per UOM (e.g. per CUM)". It cannot hold three rates, and it is not per trip.

The vendor transport rate card cannot express it either: `calcCandidateAmount` prices transport as `leadDistance × 2 × ratePerKm × trips`, a per-kilometre round-trip model. Forcing a flat per-trip figure through it would require a fabricated lead distance and could not vary by trip size. Do not attempt that.

PART A — THE STORED RATES
=====================================================================
A1. Add a per-trip rate table to `earthworkArrangements`. A JSONB array is appropriate, each entry holding:
      - trip quantity (number, e.g. 600)
      - trip UOM (text, e.g. "CFT")
      - rate per trip (number, the flat all-in amount in ₹)
    Name it clearly, e.g. `tripRates`.
A2. Nullable, defaulting to null. Every existing arrangement row stays exactly as it is and keeps behaving as it does today.
A3. `agreedRate` is NOT touched, NOT migrated, NOT deprecated and NOT read by this batch. It keeps its current meaning (per UOM). The two coexist; 02B will decide which applies to what.
A4. Validate on write: quantity > 0, UOM non-empty, rate >= 0, and no two entries sharing the same quantity+UOM pair (a duplicate makes the rate ambiguous and must be rejected with a clear message, not silently resolved).
A5. Additive migration only. No existing column changes meaning. No existing row is written.

=====================================================================
PART B — ENTERING THEM
=====================================================================

      800              CFT      ₹ ____
      1000             CFT      ₹ ____          [+ Add row]  [remove]

B2. Label it so a non-accountant reads it correctly — this is a flat all-in amount per trip, covering extraction, haulage and dumping. Put that in plain words near the table, in one line.
B3. Rows can be added and removed. Saving with no rows stores null, exactly as today.
B4. Reject a duplicate trip size + UOM on screen with a plain message before saving.
B5. Do not change any other field, validation or behaviour on this screen. Do not change the approval workflow.
