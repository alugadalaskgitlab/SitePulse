Instruction 06Z-HF2 — Cut/Fill Source Selector Misclassifies Embankment as Roadway Excavation

OBJECTIVE

Fix the confirmed 06Z Cut/Fill source-selection bug before doing any other
work.

CURRENT PRODUCTION FAILURE

In Execution Arrangement:

Arrangement Type:
Reuse of Excavated Material

the field:

Source roadway excavation BOQ item

shows/preselects the BOQ item:

"Forming embankment with excavated earth obtained from roadway excavation..."

That is the DESTINATION EMBANKMENT BOQ item, not the source excavation BOQ
item.

The user has already submitted this arrangement with that incorrect
self-source selected.

ROOT CAUSE — INDEPENDENTLY CONFIRMED BY READING THE ACTUAL REGEX

shared/workTypeRecipes.ts classifyWorkType(), in order:
1. A "roadway_excavation" rule (~line 436) matching /roadway\s*excavat|.../
   against CUM-unit items.
2. AFTER that, an "earthwork" rule (~line 442) matching
   /embankment|earth\s*work|earthwork|.../ against CUM-unit items.

Because rule 1 runs first and only checks for the substring "roadway
excavat", any embankment item whose description mentions its material
source as "...obtained from roadway excavation" matches rule 1 and returns
"roadway_excavation" before rule 2 (which would correctly classify it as
"earthwork") ever runs — even though the description's own opening words
("Forming embankment with...") make the item's real nature unambiguous.

NOTE FOR THE FIX: the structure-excavation rule immediately above rule 1
(~line 424-429, "excavation_structure") already handles exactly this shape
of problem — it excludes any description containing "embankment" via
`&& !/\bembankment\b/i.test(d)`. Apply the same style of guard to the
roadway_excavation rule rather than introducing a new mechanism: exclude
descriptions containing "embankment" (or otherwise built around forming/
constructing embankment) from matching roadway_excavation, so they fall
through to the earthwork rule instead. Prefer this precedented, minimal,
narrowly-scoped change over reordering the rule blocks — reordering risks
changing classification for other descriptions that legitimately match
both patterns.

This is contextual misclassification. The classifier must distinguish:
A. the BOQ item is itself Roadway Excavation / Cutting
versus
B. an Embankment BOQ description merely REFERENCES roadway excavation as
   the SOURCE of the material.

Do not fix this only inside the dropdown with a hardcoded item exclusion.
Fix the canonical classifier/context rule so all consumers get the correct
classification — both the source dropdown (EarthworkArrangementDialog) and
the Cut/Fill opening-balance screen (EarthworkControl) already call the
same classifyWorkType() to build their item lists, so a correct classifier
fix should resolve both without touching either UI file. Confirm this in
your report rather than assume separate UI fixes are needed.
