BACKGROUND (confirmed by direct code review — do not re-derive)
Six separate, confirmed issues found from a live-use recording of the Daily Diesel Requirement → Material Receipt flow:

1. When a Daily Diesel Requirement is marked "Purchased," its Purchase Summary already captures a Bill No. (`dieselRequirements.billNo`, shared/schema.ts ~line 2020, entered via client/src/pages/DieselRequirements.tsx's `purchaseBillNo` field). When a Material Receipt is then recorded against that same requirement (via the "Daily Diesel Requirement" dropdown), the receipt's own "Invoice No. (optional)" field (client/src/pages/PlantMaterialReceipts.tsx, `invoiceNo` state, ~line 175) stays blank — there is an existing effect (~lines 397-429) that auto-fills the Invoice Date from the linked requirement, but it never reads `requirement.billNo` or sets `invoiceNo`.
2. "Challan / DN No." is required only by client-side logic (`handleSubmit` guard ~line 603, Save button disabled condition ~line 1435, red-asterisk styling ~line 1207) — the database column is nullable and the server does not require it. "Invoice No." has no such requirement anywhere. This mismatch is backwards for real usage: the owner usually has the invoice/bill number (now available from the linked requirement per Part 1) but often does not have a physical challan/delivery note.
3. A Diesel Requirement's "Received/Pending" status does not update promptly after a linked receipt is created and Final Submitted. Root cause is NOT a missing recompute — `computeDieselReceiptState()` (shared/dieselReceiptStatus.ts) already computes status live from actual receipts each time it's queried. The real cause is stale client-side caching: the material-receipt create/update/final-submit mutations in PlantMaterialReceipts.tsx invalidate several query caches (material-receipts, stock-balances, stock-ledger, attachments, purchase-indents) but never invalidate `/api/diesel-requirements`, `/api/diesel-requirements/receipt-status`, or `/api/diesel-requirements/summary` — so the Diesel Requirement screens keep showing pre-receipt data for up to 5 minutes (the default `staleTime`) or until a manual reload. Separately, the "Daily Diesel Requirement" dropdown's own filter (`purchasedDieselRequirements`, ~line 364: `status === "purchased" && qtyPurchased > 0`) checks nothing about REMAINING quantity, so an already-fully-received requirement stays selectable forever, contradicting its own helper text ("must use a purchased requirement with quantity remaining").
4. Navigating between major sections sometimes blanks the ENTIRE screen (including the sidebar) to a plain centered "Loading page…" message. Cause: client/src/App.tsx wraps the whole top-level `<Switch>` (including `AuthedShell`/`HubShell`, which renders the sidebar) in one single `<Suspense>` boundary (~line 206), so any lazy-loaded page chunk triggers the fallback for the whole tree, sidebar included, instead of just the content area.
5. "Site Operations" navigates to `client/src/pages/SiteHome.tsx` (registered at App.tsx ~line 271, path `/site`), which is a legacy standalone page that never adopted the shared `HubShell` sidebar shell used by the rest of the app (Dashboard, Material Receipts, etc.) — it renders its own full-page layout with a dark "SiteLog" branded header and no persistent sidebar, making it look like a different app.
6. A saved Material Receipt shows its linked Diesel Requirement only as plain static text — `Purchase document linked ✓ from Daily Diesel Requirement #{linkedDieselRequirementId}` (PlantMaterialReceipts.tsx ~line 1837) — not a link. There is no way to click through from a receipt back to its requirement's detail page; the user has to manually search the Diesel Requirements list.
