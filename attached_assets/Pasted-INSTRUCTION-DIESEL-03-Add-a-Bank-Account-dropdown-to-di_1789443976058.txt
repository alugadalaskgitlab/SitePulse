FIX 1 — ADD A BANK/ACCOUNT DROPDOWN TO DIESEL'S MARK-AS-PAID FLOW
a. In MarkAsPaidDialog, add a "BANK / ACCOUNT" Select, shown only when payer === "company" (mirroring Vendor Bills' paidByKind === "company" gating), populated from the same source Vendor Bills uses — reuse GET /api/vendor-bills/company-accounts directly (it's a general company-accounts list, not vendor-bill-specific data) rather than duplicating the endpoint. If you judge the endpoint path itself should be renamed/generalized since it's now used by two different areas, that is acceptable — just keep it working for Vendor Bills exactly as before.
b. Add a new column to store this selection on the diesel requirement's payment record (e.g. paymentAccountKey, matching Vendor Bills' naming) — this IS a schema change, so add the column via a proper migration, default null, and show the exact migration before/while applying it.
c. Include the selected account in the existing PATCH /api/diesel-requirements/:id/payment-status call alongside paymentStatus, paymentMode, and paidBy.
d. Required-ness: make it required when payer is company (matching Vendor Bills' expectation that a company payment needs a named account), optional/hidden when payer is personal — same pattern Vendor Bills already uses.

FIX 2 — SHOW PAID STATUS WITH TIMESTAMP ON THE LIST, WITHOUT ENLARGING THE ROW
a. In the list view's per-row badge stack (~line 1140-1143, the `<div className="flex flex-col items-end gap-1">` holding getStatusBadge and receiptStatusBadge), add a third, compact indicator: when paymentStatus === "paid", show a small badge/line reading something like "PAID · {formatted paidAt date/time}" — keep it small (matching the existing badges' text size/padding, not a larger element) so the row's footprint stays essentially the same as today, not a new multi-line section.
b. When paymentStatus is not "paid" (pending or absent), show nothing extra — do not add an empty placeholder that reserves space.
c. This must work correctly for EVERY existing requirement record already in the database, not just newly-created ones going forward — paymentStatus and paidAt already exist as fields (per Background #3) on both historical and new records, so simply reading and displaying them is sufficient; no backfill/migration should be needed for this specific piece (only Fix 1's new paymentAccountKey column is a schema change — a requirement paid before this batch simply won't have an account on file, and that's fine, it just won't be shown for that historical row).
