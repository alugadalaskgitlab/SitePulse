CONFIRMED AREAS THAT MUST BE EXPLICITLY VERIFIED
--------------------------------------------------

The following possible gaps have already been identified and must be checked directly in the current code.

1. RMC GRANULAR PERMISSIONS

The UI exposes separate permission rows for:
- RMC Batch Records
- RMC Mix Designs
- RMC Cube Tests
- RMC Raw Materials
- RMC Delivery Challans
- RMC Daily Report

Verify whether each underlying route/API actually enforces its own specific RMC permission.

There is concern that the server may instead be using one broader plant-production permission for multiple/all RMC functions.

Report for every RMC feature:
- UI permission key
- frontend guard
- server/API guard
- actual permission currently enforced
- whether the displayed checkbox is genuinely authoritative

If the UI presents fine-grained permissions that are not actually enforced, classify this as a HIGH-PRIORITY permission trust gap.

Do not fix it in this audit batch.

2. TOMORROW'S PROGRAM / SITE REQUIREMENTS

Audit the complete Tomorrow's Program / Site Requirements flow.

Check:
- list/view
- create/raise
- edit
- review
- status/outcome actions
- labour allocation
- any related endpoints

Verify both:
- frontend visibility
- server/API authorization

There is concern that current access may only be hidden in the UI while server endpoints lack an equivalent permission check.

If authenticated users can directly call the endpoint without the intended permission, classify it as a HIGH-PRIORITY server authorization gap.

Also recommend the minimum sensible permission model for this module.

Do not implement it in this audit batch.

3. DIESEL REQUIREMENT PERMISSION CONSISTENCY

Trace the entire Diesel Requirement workflow:

- view
- raise
- edit
- submit
- approve/reject
- any related list/detail endpoints

Compare use of:
- legacy site_diesel
- diesel_req_view
- diesel_req_raise
- diesel_req_approve

There is concern that raise/edit may still depend on the old broad permission while approval uses the newer granular permission.

Report the exact current behavior and recommend one consistent model.

Do not change it in this audit batch.

4. GRANT ALL / REVOKE ALL / NOTIFY BEHAVIOR

Inspect all of these separately:

- Section "All"
- Group "Grant all"
- Global "Grant all"
- Global "Revoke all"

For each, report whether Notify:
- remains unchanged
- becomes enabled
- becomes disabled

The intended principle is that Notify is a separate explicit opt-in and bulk access changes should not silently alter notification choices unless deliberately designed that way.

There is concern that global Grant All may currently rebuild the permission matrix with Notify=false and therefore silently remove existing Notify selections.

Confirm from code and report the exact behavior.

Do not fix it in this audit batch.
