**Instruction 029C — Work Programme Data Round-Trip, Stage/Front Usability and Category-Aware Side Quantity Allocation**

**BUSINESS PURPOSE**

SitePulse is not road-design or quantity-surveying software. It connects BOQ/SDB/SNL → Work Programme → planned material/equipment/labour/fuel demand → Procurement/Stores → DPR actuals → balance/gaps → draft RA support. All programme quantities, DPR progress and balance remain in the BOQ item's own UOM. SDB/SNL and mix templates — untouched by this batch — convert that BOQ-UOM quantity into materials, plant, labour and fuel. This batch corrects how the BOQ-UOM planned quantity is computed and displayed; it does not add procurement-UOM or stock-UOM logic to Auto Sequence.

**PART C — CATEGORY-AWARE SIDE QUANTITY ALLOCATION (the core fix)**

Do not introduce a single user-selected allocation basis on a stretch that governs every BOQ item generated from it. A reach commonly mixes earthwork (CUM), GSB/WMM (CUM), Prime/Tack (SQM), DBM/BC (MT), and possibly pipe/structure items — one basis is wrong for all of them. Instead, apply automatic category rules based on the item's existing `layerConfig.layerType` classification (and existing structure/location linkage), with no new per-item selector UI in this batch:

9. **Linear pavement/granular/spray items** (`layerType` = bituminous, granular, spray_coat): side-aware reach-length allocation. `full_width`/`both_sides`/`median` stretches get the full length-proportional share (`stretchLen / totalRoadLen`, or `manualQtyFraction` when the stretch has one). `lhs`/`rhs`/shoulder/service-road stretches get half that share by default (see #11 for the width-matched exception).
10. **Earthwork/embankment/subgrade** (`layerType` = earthwork): use the *same* side-aware reach-length math as #9 — do not treat earthwork specially in the formula. Every bar and preview row generated for an earthwork item must carry a visible label: "Planning Estimate — based on BOQ quantity and reach length." No blocking confirmation is required merely to generate this estimate. Do not add cross-section, cut/fill, or survey-grade calculation.
11. **Width-matched split** (applies within #9/#10, automatic, no UI selector): when an LHS stretch and an RHS stretch for the same item have *identical* `chainageFrom`/`chainageTo` and both have `plannedWidthM` set, split that chainage's full share as `widthLHS / (widthLHS + widthRHS)` and the complement, instead of the flat 0.5/0.5. If the boundaries differ at all — even partial overlap — do not attempt a width fraction; use the flat 0.5 side-share and show a non-blocking note: "Width-based split needs matching LHS/RHS reach boundaries; using standard side allocation." Segmented/partial-overlap width calculation is explicitly out of scope, deferred to 029D.
12. **MT-UOM bituminous items** (DBM/BC/SDBC/BM in MT): apportion the BOQ-UOM MT total using the same side-aware reach-length math as #9. Do not derive or adjust quantity from area × thickness × density — no density or geometry conversion is invented at this stage.
13. **Discrete/location items** (pipes, structures, or any item already tied to a `structureId`/location-based planning path): exclude entirely from this automatic road-stretch side-length distribution. They keep using their existing structure/location generation logic, untouched.
14. **`manualQtyFraction`** on a stretch: remains an explicit override — when set, it is used directly as the full share for that stretch's items, bypassing all automatic side-fraction math above. Label it in the UI as "Manual allocation — fraction of BOQ item quantity" for clarity.
15. Add `plannedWidthM?: number | null` to `RoadStretchInput` in `shared/programmeSequencer.ts` if not already present, needed for #11. Do not add an `allocationBasis` field or any per-stretch/per-item basis selector — that belongs to 029D's full matrix.
16. Confirmation/blocking is required only in three cases, none of which apply merely because an item is earthwork or because a stretch has a side: (a) total planned quantity for an item exceeds its BOQ quantity beyond tolerance (Part D); (b) a `both_sides`/`full_width` stretch conflicts in chainage with an `lhs`/`rhs` stretch for the same item — already blocked by the existing 029B validator, enforce via test, not new prompts; (c) a manual or location-based quantity already recorded for that item/stretch would be silently overwritten by the automatic calculation — surface this instead of overwriting it.
