BACKGROUND (confirmed by direct code review of the REC-01 build — do not re-derive)
REC-01 correctly made Invoice Date the operative stock date for creating and editing a Material Receipt (`createMaterialReceipt`, `updateMaterialReceipt` in server/storage.ts, via the shared `materialReceiptTransactionDate()` helper), and correctly calls `recomputeBalanceAfterForMaterial` after a create so the ledger's running balance trail re-sorts into correct chronological order.

Two gaps remain in the paths REC-01 did not touch:
1. `_cancelMaterialReceiptWithinTx` (server/storage.ts, `cancelMaterialReceipt`) inserts its compensating reversal ledger row with `date: new Date().toISOString().slice(0, 10)` — i.e. today's actual date — instead of the original receipt's resolved Invoice Date. Cancelling a backdated receipt will therefore park the reversal on today's date instead of next to the original transaction, distorting the historical trail for any date range between the original Invoice Date and today.
2. Neither the cancel path nor `_deleteMaterialReceiptWithinTx` (`deleteMaterialReceipt`) calls `recomputeBalanceAfterForMaterial` after reversing/removing stock — unlike create and edit, which already do. This can leave other, unrelated ledger rows for that material showing a stale `balance_after` figure after a cancel or delete.

We are asking for this now because the very next real action is entering several backdated diesel receipts and then cancelling or deleting one accidental duplicate (approx. 165 L) — this must produce a clean, correctly-ordered ledger the first time.

PART 1 — FIX THE TWO CONFIRMED DEFECTS
1. In `_cancelMaterialReceiptWithinTx`, date the compensating reversal ledger row using `materialReceiptTransactionDate(originalReceipt)` (resolved Invoice Date, with the existing historical-date fallback), not today's date. This avoids any ambiguity for an old receipt whose `invoiceDate` is null and relies on the fallback historical date. The reversal must sit chronologically next to the entry it reverses.
2. After a successful cancel (`cancelMaterialReceipt`) and after a successful delete (`deleteMaterialReceipt`/`_deleteMaterialReceiptWithinTx`), call `recomputeBalanceAfterForMaterial` for the affected material — the same call `createMaterialReceipt` already makes — so the running balance trail is correct immediately, not just after some later edit.
3. Do not change the stock-sufficiency guard behavior on cancel/delete (the block that refuses to reverse when the quantity has already been consumed) — leave that exactly as is.
