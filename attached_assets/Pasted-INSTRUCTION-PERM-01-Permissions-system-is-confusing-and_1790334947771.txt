INSTRUCTION PERM-01: Permissions system is confusing and partly mis-wired — some "granular" permission toggles the person sees in the UI don't actually control anything (the old "legacy" key silently does the real work instead), and every section shows all 8 action columns (View/Create/Edit/Delete/Reports/Export/Approve/Notify) even when most of them don't apply to that section (e.g. a Hub entry-page row, which has nothing to create/edit/delete). Fix both: make the granular keys the real, functioning gate (keeping legacy keys working too, for safety), and make the Permissions screen only show checkboxes that actually do something for each section.

READ THIS FIRST — SCOPE DISCIPLINE
This touches the authorization system — treat it as security-sensitive. The prime directive: after this fix, NO EXISTING USER should lose any access they currently have. Every change here must be ADDITIVE (OR logic alongside what already exists), never a replacement that could narrow anyone's current permissions. Four parts, increasing in scope — STOP after each Part and report back before starting the next. Do not touch VENDOR-01, VENDOR-02, VENDOR-03, or any other prior instruction. Do not publish automatically.

BACKGROUND (confirmed by direct code review — do not re-derive)
1. `shared/permissions.ts` defines two overlapping generations of permission keys for the same real features: older "legacy/broad" keys (e.g. `site_procurement`, `site_diesel`, `vendor_bills`, `admin_settings`) and newer "granular" keys meant to replace them (e.g. `purchase_indents_view`, `purchase_indents_raise`, `purchase_indents_approve`, `diesel_req_raise`, `vendor_bills_raise`). The Permissions UI (`client/src/pages/UserManagement.tsx`, `PermMatrix` component) shows both generations as separate rows, and a "Legacy / Broad Keys (backward compat)" group at the bottom.
2. CONFIRMED: for Purchase Indents and Diesel Requirements, the migration to granular keys was never actually finished in the server/client CHECK logic — the granular "Raise" keys (`purchase_indents_raise`, `diesel_req_raise`) are only used to decide whether a shortcut TILE is shown on a dashboard; the actual create/edit routes and buttons still check ONLY the old legacy key (`site_procurement`/`site_diesel`). This means a person could have "Purchase Indents — Raise" checked and still be unable to actually raise one, because only the legacy "Purchase Indents (legacy)" key is truly gating that action — a very confusing trap.
3. CONFIRMED: for Vendor Bills, most routes were correctly migrated to check `vendor_bills_raise` OR the legacy `vendor_bills` key (a safe, additive pattern — see `assertCreateEither`, `server/auth-routes.ts`), but three routes were missed and still check ONLY the legacy key: duplicate-checking, editing a draft bill, and the equipment-hire-discovery endpoint (`server/routes.ts` ~lines 11250, 11488, 12067).
4. CONFIRMED: "Admin Settings (legacy)" is the ONLY gate for a wide bundle of unrelated admin actions that have no granular equivalent key at all today: site create/edit, plant create/edit, admin notifications, vendor aliases, vendor rate cards, and concrete estimates (`server/routes.ts` ~lines 1058, 1072, 1096, 1649, 3565, 3612, 11201, 12025, 12441, 12515). This is the most confusing one for an admin trying to reason about what a person can/can't do, since it's one broad switch covering many distinct real capabilities.
5. CONFIRMED: six of the ten legacy keys shown in the "Legacy / Broad Keys" group are fully INERT — checked nowhere in the current codebase: RMC Operations (legacy), HMP Operations (legacy), Reports & Analysis (legacy), Estimates Manager (legacy), App Management (legacy), and Reports (legacy) is checked but always OR'd with other keys already, never standalone-load-bearing.
6. CONFIRMED: the Permissions matrix UI (`PermMatrix` in `UserManagement.tsx`) renders the SAME fixed 8 action columns for every single section, with no per-section filtering of which actions are actually meaningful. For "Hub (entry page)" rows specifically, ALL of View/Create/Edit/Delete/Reports/Export/Approve independently do the exact same single thing (make the hub visible in the sidebar — `sectionVisible()`'s OR logic in `client/src/lib/auth-context.tsx` ~lines 156-161), and "Notify" does nothing at all for any hub row.
7. Permission checks throughout this app use simple OR logic when multiple keys are involved (`assertCreateEither`, `gatedEither`, etc.) — there is NO AND logic anywhere requiring two permissions simultaneously, and NO pattern where a legacy key can override/cancel a granular grant. This means Fix Part A/B below (adding a granular OR-check alongside the existing legacy check) is safe and cannot narrow anyone's current access — it can only ever add a new way to gain the SAME access, or leave it unchanged for people who don't have the new granular key checked.
