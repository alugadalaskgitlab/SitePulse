BATCH 04 — DPR DATA INTEGRITY, UOM CONSISTENCY & SUBMIT READINESS

This is a focused DPR integrity hotfix.

Do NOT start Progress Report, Tomorrow's Programme workflow changes, or further Geometry work in this batch.

There are THREE related real-data issues to resolve:

1. DPR physical quantity / BOQ-UoM inconsistency
2. Summary vs Detailed DPR dimension inconsistency
3. DPR fields — especially Guided DPR equipment details — may not be saved exactly as entered, and an incomplete DPR can presently reach submission without sufficiently warning the Engineer.

IMPORTANT RISK NOTE

Sections dealing with measurement/UoM/save fidelity are corrective bug fixes.

The Final Submit readiness gate is different: it introduces new blocking behaviour into a LIVE field workflow used by Engineers/Foremen every day.

Therefore:

- false-positive blocking is a higher operational risk;
- Draft Save must remain available at all times;
- mandatory checks must be conservative and clearly justified;
- ambiguous/incomplete cases without a valid resolution path should default to WARNING rather than hard block;
- submit-readiness tests must be reviewed especially carefully before this batch is accepted.

Also investigate Guided DPR equipment persistence: the current code path appears capable of collecting equipment information but may serialize only part of it and replace entered fields with blank/null values.

OBJECTIVE

Make DPR data trustworthy end-to-end:

A. what the Engineer enters is what is saved;
B. Summary and Detailed DPR represent the same stored measurement consistently;
C. physical measurement is converted correctly to the BOQ item's UoM;
D. an Engineer is clearly notified before Final Submit if selected/entered DPR sections are incomplete;
E. Draft remains lenient so the Engineer can save unfinished work and return later.

2. EXPLICITLY DISTINGUISH CONVERSION-FACTOR ROOT CAUSE

Determine which is true for Clearing & Grubbing:

CASE A — CODE BUG

The BOQ item's dprConversionFactor is correctly populated, e.g. 0.0001, but the auto-calculated L×W DPR path never applies it.

OR

CASE B — CONFIGURATION/DATA GAP

The physical quantity calculation is correctly 225 Sqm, but dprConversionFactor is blank/default 1 even though the BOQ is in Ha.

OR

CASE C — BOTH

There is both missing configuration and a code path that ignores the factor.

Report the actual case.

If this specific item's correct deterministic factor is obvious from its standard units, report what should be configured and whether automatic standard conversion is safer than relying on manual configuration.

5. HARD DPR → BOQ UOM RULE

Physical measurement and BOQ progress are distinct when units differ.

Example:

Physical:
225 Sqm

BOQ:
Ha

BOQ progress:
0.0225 Ha

The final quantity used against BOQ progress/balance must be in the actual BOQ item's UoM.

Do NOT merely calculate 225 Sqm and label it "Ha."

Preserve the physical measurement for transparency.

A compact display may be:

Measured: 225 Sqm
BOQ Progress: 0.0225 Ha

or:

150 m × 1.5 m = 225 Sqm → 0.0225 Ha

6. DPR CONVERSION PRECEDENCE

Reuse the existing canonical DPR/UoM and dprConversionFactor mechanisms.

Do not create a parallel conversion system.

Explicitly define and test the precedence between:

1. physical geometry quantity
2. canonical standard-unit conversion
3. BOQ item's dprConversionFactor
4. final BOQ progress quantity

The existing BOQ `dprConversionFactor` field is specifically intended for DPR-unit → BOQ-unit conversion and must be investigated rather than bypassed.

Prevent double conversion.

State whether the auto-calculated L×W/L×W×T path currently reads dprConversionFactor.

9. FINAL SUBMIT READINESS — NOTIFY THE ENGINEER

Before Final Submit, run one consistent completeness check.

This should identify incomplete selected/entered records and show a clear checklist to the Engineer.

Do not silently submit an incomplete DPR.

MANDATORY checks must be conservative.

Where SitePulse cannot currently distinguish a legitimate "not used / no work happened" case from an incomplete row, treat it as ADVISORY until the proper outcome workflow exists.

At minimum check:

A. PROGRESS / ACTIVITIES

For every activity row actually selected/added:

- BOQ/activity selected
- applicable From/To chainage completed where required
- side selected where required
- required dimensions or manual quantity completed
- quantity > 0 where work was done
- quantity source completed if manual
- required override/reason completed where applicable

Do not force every BOQ item in the project to be selected.

However, if an activity has been deliberately added/selected and left incomplete, flag it.

If the existing programme/Tomorrow's Plan provides a reliable list of activities expected today, investigate whether missing outcomes can be surfaced as a WARNING only:

"Planned activity X has no DPR outcome."

Do not build Tomorrow's Programme outcome workflow in this batch.

B. EQUIPMENT

For every equipment row with a machine selected:

Require a meaningful closure before Final Submit ONLY where the row clearly represents equipment that was actually used.

Depending on entry type, validate the appropriate fields.

For normal time/meter equipment:

- machine
- task
- operator where the current business rule expects it
- opening reading and closing reading if meter method is being used
OR
- start time and end time if time method is being used

If openingReading exists but closingReading is blank:
flag:
"Closing meter reading required."

If startTime exists but endTime is blank:
flag:
"End time required."

If machine exists AND some usage data has been entered but the row cannot be completed:
this may be a mandatory issue.

IMPORTANT — MACHINE SELECTED BUT NOT USED

If a machine is selected but NO actual usage details were entered:

- no opening/closing meter;
- no start/end time;
- no trips;
- no other evidence of actual use;

and SitePulse does NOT yet have a proper explicit "Not used" outcome:

DO NOT hard-block Final Submit solely for this case.

Show an ADVISORY warning such as:

"JCB is selected but no usage was recorded. Confirm whether it was not used."

This remains advisory until a proper Not Used / Released / Cancelled outcome is introduced in the planned Tomorrow's Programme / Equipment workflow batch.

Do not invent zero hours.

If a lightweight existing "not used" concept already exists and can be reused without schema/business-rule expansion, use it.

Otherwise report the gap and keep this specific case non-blocking.

Trip-based equipment:
validate trips/distance according to the existing entry type.

C. LABOUR

For an entered labour row:

- category
- positive count
- task where expected

Rows with zero count/blank category should not masquerade as completed labour records.

If a blank placeholder labour row can exist naturally in the UI without meaning labour was actually used, avoid false-positive blocking.

- quantity
- UoM
- other currently required fields depending on type
