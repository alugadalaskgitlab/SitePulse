## Why this batch exists

VB-EDIT-01 made the Edit control appear on an approved equipment-hire bill. The save
is then refused, because `server/storage.ts` holds two rules that contradict each
other once such a bill leaves draft:

```
if (linkedStatements.length > 0 && data.hireGroups === undefined)
  → "Edits to a bill with linked hire statements must include its hire groups"
if (data.hireGroups !== undefined && existing.status !== "draft")
  → "Hire groups on verified, approved, or paid bills are frozen"
```

Both paths refuse, so **no** edit to an approved hire bill can succeed — not even one
that changes only the bill date. **Both rules are correct and must stay.** A frozen
hire bill should stay frozen. What is wrong is offering a control that cannot work,
and having no way at all to correct an accounting date.

## Part B — A bill date can be corrected on its own

**The need.** `HLC/VB/2026/0055` carries bill date 09-Oct-2026 for the August period,
which puts it out of order against `HLC/VB/2026/0054` and hides it from the
previous-bill block. The date must be correctable. Nothing else about the bill is
being changed.

**Required.**

1. A new action, `PATCH /api/vendor-bills/:id/bill-date`, that changes **only**
   `billDate`.
2. **The bill's status does not change.** An approved bill stays approved. It does
   not leave Payable now, is not reset to draft, and needs no re-approval — no
   amount has moved.
3. Permission: the same as the existing edit path — an administrator for a verified,
   approved or paid bill; the ordinary edit permission for a draft. A voided bill is
   refused.
4. It writes one audit entry through the existing `recordChange` helper: module
   `vendor_bills`, the bill id, action `bill_date_changed`, the old and new date, the
   actor. A reason is accepted and stored if the user types one; it is not required.
5. On screen: a small control beside the bill date on Bill Detail — not inside the
   edit form — opening a single date field with the current date shown, and one line
   of plain text: *"Changes the accounting date only. Amounts, line items and status
   are unchanged. This is the date Tally orders the vendor's ledger by."*
6. Add `bill_date_changed` to the action label map in
   `client/src/components/HistoryDialog.tsx`.

**Constraints — this action must not touch:**

- `status`, `verifiedBy`, `verifiedAt`, `approvedBy`, `approvedAt`, `paidAt`,
  `paymentRecordedBy`, `paidBy`, `amountPaid`;
- any line item, any hire group, any hire statement, any exception;
- `calculationSnapshot` or any frozen evidence;
- `periodFrom` or `periodTo` — the billed period is **not** part of this action;
- the bill number, the vendor, the site, or any amount.

Validate that the new date is a real date in `YYYY-MM-DD`. Reject a blank or
malformed date. Do not silently accept a value the field cannot parse.

## Part C — Every status names its person, with the date and the time

**The fault.** The status strip shows an actor for some states and not others, and
the timestamps are inconsistent — some carry a time, some only a date, because
`verifiedAt`, `approvedAt` and `paidAt` are stored as text while `createdAt` is a
real timestamp.

**Required.** Each of the four states — draft, verified, approved, paid — shows, in
the same shape:

- **who** did it, and
- **the date and the time** it happened.

Where a name was never recorded, say so plainly ("not recorded") as VB-EDIT-01 does
for the draft author — do not leave a bare timestamp and do not infer a name. Where a
stored value carries a date but no time, show the date and say the time was not
recorded rather than inventing midnight.

**Constraints.** Display only. Do not write to, backfill or reformat any stored
timestamp or actor field. Do not add a column.
