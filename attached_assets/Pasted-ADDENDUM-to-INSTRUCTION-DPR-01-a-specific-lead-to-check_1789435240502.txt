Please check specifically: for the real DPR referenced in DPR-01 (TAKKADPALLY-SIRUR, the JCB with roadway excavation + embankment-excavated earth), is `activitySegments` actually empty and `activityAllocations` populated instead (i.e. is this DPR hitting the legacy conversion path)? Report what you find — this is a lead to confirm or rule out, not an assumption to build on blindly.

SECOND ISSUE — SEPARATE BUG, FOLD INTO THIS SAME BATCH: A NEW DPR CANNOT BE FINAL-SUBMITTED WHEN NO LABOUR WAS LOGGED

READ THIS FIRST — SCOPE DISCIPLINE
This is unrelated to the Work Assignment display bug above — a different, real, blocking bug confirmed by direct use of the app. Fix only this specific validation; do not touch the rest of the DPR submission flow, equipment log, activity progress, or diesel handling.

BACKGROUND (confirmed by direct use, not yet traced to an exact line — this build's zip was checked and the literal message text could not be located, so it may be a dynamically-built validation message or may not exist yet in the zip reviewed; find and confirm the actual source before fixing)
When creating a new DPR where activity/no-activity and equipment are logged normally, but the Labour Log section is left empty because no labour was used that day, the app refuses to finalize/submit the report — it only allows saving as a draft — and shows an error along the lines of "labour count cannot be negative." This is wrong: having zero labour rows is a completely valid, common day-to-day scenario (not every DPR involves labour), and it should not block submission at all.

FIX
a. Find wherever DPR submission/finalization is validated (client-side form validation and/or server-side submit endpoint) and locate the rule that is producing this "count cannot be negative" (or similarly worded) error when the Labour Log has zero entries.
b. The likely cause is a validation step that runs over labour rows and, when there are none, ends up computing or checking a count value incorrectly (e.g. defaulting to -1, or checking a total against a minimum incorrectly) rather than correctly treating "no labour rows" as valid and simply skipping labour validation entirely.
c. Fix it so that: zero labour rows is always valid and never blocks final submission. If a labour row DOES exist, its count should still be required to be a non-negative number (that part of the validation, if it exists for populated rows, is correct and should stay — only the zero-rows case is broken).
d. Do not change any other section's validation or submission behavior — equipment log, activity progress, diesel, materials, everything else must continue to work exactly as it does today.

TESTS
A. Create a new DPR: log an activity, log equipment usage, add zero labour rows (leave Labour Log completely empty). Confirm the report can be fully submitted/finalized, not just saved as draft.
B. Create a DPR with at least one labour row filled in correctly. Confirm submission still works normally, no regression.
C. Try entering an actually negative count in a labour row that does exist (if that's possible to enter) — confirm that specific case is still correctly rejected with a validation message, so real bad input is still caught.

REPORT BACK (fold into DPR-01's report)
1. State the exact file/line and cause of the false "labour count cannot be negative" block on zero labour rows.
2. Confirm Fix with Test A/B/C evidence.
3. Confirm no other section's validation was touched.
