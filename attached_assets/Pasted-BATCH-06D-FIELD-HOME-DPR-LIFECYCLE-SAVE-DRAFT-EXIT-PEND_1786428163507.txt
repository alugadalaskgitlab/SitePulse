BATCH 06D — FIELD HOME DPR LIFECYCLE
+ SAVE DRAFT EXIT
+ PENDING-SUBMISSION GUIDANCE

This is a focused DPR lifecycle / Field Home usability batch.

It must NOT change the current working Guided DPR wizard, DPR quantity logic,
programme logic, weather, equipment entry, photos, or reporting.

CURRENT VERIFIED STATE

1. Guided Save Draft currently saves successfully and only shows a toast.
   It does NOT navigate away from the Guided wizard.

2. Field Home currently uses:
   - not-started
   - draft-own
   - submitted-own
   - submitted-other

3. Field Home already derives section completeness and per-row pending
   messages through `deriveDprChecklist`, which itself uses the common
   Batch 04 submit-readiness validator.

4. Field Home currently fetches DPRs only for today:
   dateFrom=today
   dateTo=today

   Therefore an older unsubmitted DPR is currently invisible there.

5. Existing own road drafts already reopen through the SAME draft route /
   draft ID.

Expected schema change: NONE.

--------------------------------------------------
1. IMPORTANT LIFECYCLE RULE
--------------------------------------------------

Do NOT introduce a new `continue-own` vs `complete-own` phase based on
`doneCount`.

Keep the existing single:

`draft-own`

phase.

Reason:

`doneCount` is section-based.

A Labour or Materials section may become "done" early in the day and would
therefore incorrectly flip the CTA from Continue to Complete even though
the Engineer is still recording normal site operations.

For this batch use the simpler lifecycle:

NO DPR:
"Start Today's DPR"

OWN DRAFT EXISTS:
"Complete Today's DPR"

OWN DPR SUBMITTED:
"View Today's Site Report"

OTHER USER'S DPR SUBMITTED:
"View Today's Site Report"

The secondary status beneath "Complete Today's DPR" may say:

"Draft in progress"

and show actual outstanding items.

Do not infer morning/evening from:
- clock time;
- checklist doneCount;
- percentage complete.

--------------------------------------------------
2. SAVE DRAFT — SAVE WHATEVER IS FILLED
--------------------------------------------------

The explicit Save Draft action must continue to save the current DPR
exactly as entered.

Draft saving remains intentionally lenient.

It may contain, for example:

ACTIVITY
- From Chainage entered
- To Chainage missing

EQUIPMENT
- Opening Reading entered
- Closing Reading missing
- Start Time entered
- End Time missing

LABOUR
- partial/current information

Do NOT run Final Submit readiness as a blocker for Save Draft.

Preserve the existing draft payload and same-draft update semantics.

--------------------------------------------------
3. GUIDED SAVE DRAFT — RETURN TO FIELD HOME
--------------------------------------------------

Current Guided behavior:

Save Draft
→ toast
→ stays on current wizard page.

Change only the explicit Save Draft action:

Save Draft
→ successful server save
→ show confirmation
→ return to Field Home.

Suggested confirmation:

"Draft saved. You can complete today's DPR later from Field Home."

Do not navigate away before the server confirms success.

If save fails:
- stay on the current wizard step;
- preserve the entered data;
- show the existing error feedback.

--------------------------------------------------
4. NEXT / BACK MUST NOT EXIT
--------------------------------------------------

Only the explicit:

Save Draft

action should exit to Field Home.

Wizard:

Back
Next

must continue navigating within the current DPR.

Do not treat step navigation as Save Draft + exit.

Local/autosave behavior may continue as currently implemented.

--------------------------------------------------
5. DETAILED SAVE DRAFT — CONSISTENT EXIT
--------------------------------------------------

Investigate the current Detailed/SiteEntry Save Draft behavior.

For an explicit Save Draft action in Detailed DPR, use the same user
expectation:

successful Save Draft
→ return to the appropriate Field Home / originating Field Home context.

Do NOT alter ordinary autosave behavior.

Do NOT make every background save navigate away.

If Detailed was opened from another legitimate management/report context,
preserve its existing returnTo semantics rather than hard-coding `/`.

Report the final routing rule.

--------------------------------------------------
6. FIELD HOME — START BECOMES COMPLETE AFTER DPR START
--------------------------------------------------

Before today's DPR exists:

Primary CTA:
"Start Today's DPR"

After the current Engineer has created/saved today's draft:

Primary CTA:
"Complete Today's DPR"

The Start action must disappear for that Engineer/site/date.

"Complete Today's DPR" must reopen:

THE SAME server draft.

Never create a second DPR.

Do not use checklist doneCount to choose the CTA wording.

--------------------------------------------------
7. FIELD HOME — DRAFT STATUS
--------------------------------------------------

For `draft-own`, show a useful secondary status such as:

"Draft in progress"

plus:

X items need completion

where meaningful.

Do not merely show:

"Draft open · X/Y items done"

if a more actionable pending message is available.

The Engineer should understand:

- the DPR is safely saved;
- it has not been submitted;
- some closure information may remain.

--------------------------------------------------
8. ITEMIZED PENDING-SUBMISSION DETAILS
--------------------------------------------------

Reuse the EXISTING `deriveDprChecklist()` output.

Do NOT create another readiness/completeness model.

Display its actual per-row details where appropriate.

Example:

Today's DPR is pending submission

2 items need completion:

• WMM — chainage is incomplete — enter both From and To
• Roller TS09... — closing meter reading required
• Roller TS09... — end time required

Use the existing `details` strings.

If one row has multiple missing fields, it is acceptable to show multiple
specific lines, or group them cleanly under that row.

Do not fabricate generic messages when the shared validator has a specific
one.

--------------------------------------------------
9. FIELD HOME PENDING PANEL
--------------------------------------------------

For an own draft with pending mandatory closure items, make the existing
Pending Before Submit area more immediately useful.

It should show:

- section
- affected Activity / Equipment
- actual missing information

Examples:

ACTIVITY
WMM
Closing/To chainage missing

EQUIPMENT
Tandem Roller
Closing meter reading required
End time required

The CTA from this panel should be:

Complete Today's DPR

and reopen the same draft.

--------------------------------------------------
10. REOPEN AT FIRST RELEVANT INCOMPLETE STEP
--------------------------------------------------

When the Engineer taps:

Complete Today's DPR

do not automatically dump him on Review if known mandatory closure items
exist.

Use the existing checklist/readiness output to select the earliest relevant
Guided wizard step.

Current separate Guided steps include:

Activities / Details
Labour
Equipment
Photos / other applicable steps
Review

Map readiness sections to the actual CURRENT Guided step IDs after
investigation.

Conceptually:

activities
→ Activity Details

labour
→ Labour

equipment
→ Equipment

materials
→ the actual step that manages/materially presents Materials, if any

If no mandatory incomplete section remains:
→ Review.

Do NOT create new readiness rules just for navigation.

--------------------------------------------------
11. DO NOT USE CHECKLIST ITEM IDs BLINDLY
--------------------------------------------------

Claude's draft proposed mapping:

c1 equipment
c2 labour
c3 materials
c4 activities

That reflects today's checklist ordering.

Do not hard-code UI navigation around fragile labels/order if a safer shared
section mapping is possible.

Prefer mapping by semantic readiness section:

activities
equipment
labour
materials

to the corresponding GuidedStepId.

If using c1/c2/c3/c4 is unavoidable, centralize that mapping in one helper
and test it.

--------------------------------------------------
12. AUTOSAVE STEP VS FIRST-INCOMPLETE STEP
--------------------------------------------------

Current Guided autosave stores the wizard `step`.

On normal accidental refresh/restore:
preserve the existing stored-step behavior.

But when the user intentionally enters through:

Complete Today's DPR

Field Home should be allowed to request:

first incomplete step

based on the server draft's actual readiness.

Do not destroy the normal autosave restore mechanism.

A clean implementation may use a route/query intent such as:

complete=true

or an existing safe equivalent.

Do NOT add schema just to persist this navigation intention.

--------------------------------------------------
13. YESTERDAY / OLDER PENDING DPR
--------------------------------------------------

Field Home currently requests only today's DPRs.

Add a separate, bounded check for the current Engineer's own unsubmitted
DPR(s) before today.

Investigate the safest query first.

Do NOT replace today's efficient bounded query with an unbounded fetch of
all DPR history.

Preferred approaches, in order:

A. use existing `/api/dprs/with-details` dateFrom/dateTo with a small recent
   lookback window;

or

B. add a lightweight read endpoint only if the existing query cannot do
   this safely/efficiently.

Do not create a new endpoint merely by default.

--------------------------------------------------
14. HOW FAR BACK TO CHECK
--------------------------------------------------

Do not search unlimited DPR history on every Field Home load.

Use a bounded recent lookback suitable for field operations.

At minimum detect:

yesterday.

A short recent window, for example the previous 7 days, is acceptable if
the existing endpoint remains efficient and Replit can justify it.

If more than one older own draft is pending:

show the most recent prominently and indicate that additional pending DPRs
exist.

Do not silently hide multiple pending drafts.

Report the chosen lookback behavior.

--------------------------------------------------
15. OLDER DPR BANNER
--------------------------------------------------

If yesterday's DPR remains unsubmitted, show a visually stronger banner
separate from today's normal DPR card.

Example:

"Yesterday's DPR pending submission — 10 Aug"

"3 items need completion"

Then specific details where space permits:

• WMM — closing chainage missing
• Roller — closing reading required

Primary action:

Complete Pending DPR

Tap:
→ reopen THAT draft
→ first relevant incomplete step.

Never create a new DPR.

--------------------------------------------------
16. TODAY MAY STILL START — WARN, DO NOT BLOCK
--------------------------------------------------

An older pending DPR must NOT hard-block today's site work in this batch.

The Engineer may still:

Start Today's DPR.

Reason:

there are legitimate site cases where yesterday cannot immediately be
closed but today's work must proceed.

Show a strong warning, but no blocking rule.

Whether an overdue DPR should later require escalation/Manager action is a
separate future lifecycle decision.

SUCCESS CRITERION
--------------------------------------------------

1. Save Draft safely saves incomplete work and exits to Field Home.

2. Once today's DPR has started, Start Today's DPR becomes Complete Today's
   DPR.

3. Field Home tells the Engineer specifically what remains to be closed.

4. Complete Today's DPR always reopens the SAME server draft.

5. It opens at the first meaningful incomplete step when possible.

6. Yesterday's unsubmitted DPR is clearly visible and actionable.

7. Yesterday's pending DPR does not block today's legitimate work.

8. Final Submit remains governed by the existing shared readiness validator.

9. No artificial doneCount/time-of-day lifecycle state is introduced.

10. No schema, Programme, weather, quantity, reporting, or wizard-structure
    change is introduced.
