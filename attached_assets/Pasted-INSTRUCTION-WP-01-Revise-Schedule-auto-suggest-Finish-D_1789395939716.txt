BACKGROUND (confirmed by direct code review — do not re-derive)
In ScheduleRevisionActions (~line 118), `startDate` and `endDate` are two completely independent pieces of React state (~lines 135-136), both initialized from the bar's current values when the dialog opens (beginRevision(), ~line 154). There is no link between them today: changing Start Date does nothing to End Date, and the person must set both manually. This caused a real mistake in live use — a person intending a 2-day shift to an activity's finish date accidentally left the finish date 10 days out, because nothing suggested the correct finish once they changed the start.

The activity's duration is already implicitly known — it's just (current endDate − current startDate) at the moment the dialog opens, the exact same duration the app already calculated for that activity from its resource/equipment norms. `inclusiveDays()` (~line 240) already computes exactly this kind of day-count elsewhere in this same component for the read-only "revised duration" preview line.

FIX 1 — SUGGEST FINISH DATE FROM START DATE, KEEPING THE ORIGINAL DURATION
a. When beginRevision() opens the dialog (~line 154), capture the activity's ORIGINAL duration in calendar days: `originalDurationDays = inclusiveDays(bar.startDate, bar.endDate)` (use the same inclusiveDays function already in this file, or the equivalent day-count math already used for revisedDays). Store this in a ref or state that persists for the lifetime of this dialog session (reset each time beginRevision() runs, so it always reflects the CURRENT activity being revised, not a stale one).
b. Add an onChange handler to the Start Date input (only relevant when state === "not_started", since started bars lock their effective start): when the user changes Start Date, automatically set End Date to `newStartDate + (originalDurationDays - 1)` calendar days (inclusive counting — matching inclusiveDays' own convention, so a 1-day activity's start+end land on the same date).
c. End Date remains a normal, independently editable field — the auto-suggestion only PRE-FILLS it the moment Start Date changes; the person can still type or pick a different End Date afterward if they genuinely want a different duration for this revision. Do not lock or disable the End Date field.
d. If the person edits End Date directly (without having just changed Start Date), do not touch Start Date — this fix is one-directional (Start suggests Finish), not bidirectional. Do not build a reverse suggestion (Finish changing Start) — out of scope.
e. This applies to calendar days exactly as the app already counts them today — no change to how working days, Sundays, or holidays factor into duration; if the app doesn't currently treat non-working days specially in this calculation, don't add that here.
