Part D — Transport billing verification

Development only. Part C was published before these edits; its schema diff was empty. No duplicate analysis or cleanup was performed. No production database writes were made.

Implemented

  • Newly pulled transport lines opt into a saved rate/km, one-way lead and payload setup. Exact item matches win; otherwise only a single unambiguous configured transport card in the vendor-scoped response is used.
  • Trip rows default to per-trip pricing; actual carried MT is informational. Weight-based receipts default to actual MT × derived per-MT rate. No density/weight is guessed from volume or descriptive text.
  • Each row has a per-trip/per-MT toggle. Unknown weight disables per-MT. Row lead takes precedence and a difference from the card is shown in amber.
  • A nullable JSON pricing snapshot persists the selected basis, original card lead, payload and physical quantities. The existing calculator handles the new branch; NULL snapshot retains legacy math.
  • Snapshots are not reloaded from today's rate card on saved bills. Opted-in rows never participate in bill-to-standing-rate write-back or bulk flat-rate replacement.
  • Export projection adds pricing basis, working and lead difference. GST, deductions, TDS, totals and payables-preview calculations were not changed.
