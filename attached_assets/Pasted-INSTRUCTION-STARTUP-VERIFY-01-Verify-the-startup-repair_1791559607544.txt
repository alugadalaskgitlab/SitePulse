PART C — COULD REMOVING IT CAUSE DUPLICATE KEYS? ANSWER FROM THE CODE.
=====================================================================
C1. A sequence only falls behind `MAX(id)` when a row is inserted with an EXPLICIT
    id, bypassing the sequence. Search the entire server and migration code for any
    insert that supplies an id, any `OVERRIDING SYSTEM VALUE`, any raw
    `INSERT INTO ... (id, ...)`, and any seed or import path that does so. Report
    every one you find, or state plainly that there are none.
C2. If there are none, then ordinary application inserts cannot drift, and
    `resetAllSequences` was not protecting them. Say so, with the evidence.
C3. CONSIDER THE OPPOSITE RISK, which this instruction regards as the more serious
    one. `setval(seq, MAX(id))` moves a sequence DOWN as well as up. If rows with
    the highest ids were deleted or purged — and this application does delete and
    purge rows — the next start would pull the sequence BACK, and subsequent inserts
    would REUSE ids that previously belonged to other records.
    Determine, from the code and from the data:
      - whether any of the 42 tables has rows deleted or purged in ordinary
        operation (hard deletes, `purgeOrphanedDeletionReversals`, cleanup jobs);
      - whether any id in those tables is referenced from elsewhere WITHOUT a
        foreign key — for example `equipment_logs.plant_usage_id`,
        `equipment_usage.source_usage_id`, or the `auto:<type>:<id>` identity string
        stored in `vendor_bill_items.source`;
      - whether a reused id could therefore attach a new record to an old reference.
    Report your conclusion and the evidence. This may explain existing dangling
    references; do not fix anything.
C4. Relate this to the recorded symptom in
    `.agents/memory/startup-ledger-backfill-race.md`: transient primary-key
    collisions during rapid restarts. State whether `resetAllSequences` running
    asynchronously alongside concurrent startup inserts was a plausible CAUSE of
    those collisions rather than a cure.
