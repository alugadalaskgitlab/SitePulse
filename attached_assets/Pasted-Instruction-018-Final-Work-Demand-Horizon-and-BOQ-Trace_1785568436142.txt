1. Preserve BOQ identity on every material-demand contribution

In calculateBomDemand, every material breakdown contribution must carry the actual contributing BOQ item ID.

Add boqItemId: item.id when each material contribution is created.

Update the BomMaterialRow.breakdown type accordingly.

Do not rely on:

- material label;
- category name;
- description matching;
- a later reverse lookup

to determine which BOQ item generated the material quantity.

Where one material is generated by several BOQ items or stretches, retain each contribution separately in breakdown with its own:

- boqItemId
- quantity
- programme/month allocation
- source description where already available

Then aggregate only for the material-level display.

Do not make unrelated equipment/labour changes unless their existing types require the same field for compilation. The acceptance target in this batch is material procurement.

2. Derive real programming status from contributing BOQ items

Replace the current unreliable boolean with a genuine three-state result for each material:

- fully_programmed:
  every contributing BOQ item has valid Work Programme bars covering its relevant quantity;

- partly_programmed:
  at least one contributing BOQ item is programmed and at least one is not;

- not_programmed:
  none of the contributing BOQ items has valid programme bars.

Use the real boqItemIds carried by the material breakdown.

Do not determine programming status from the generic material label.

Return enough detail for the UI to show:

- fully programmed;
- partly programmed;
- not programmed.

For partly programmed materials, retain separately:

- programmed contribution quantity;
- unprogrammed contribution quantity.

3. Restore BOQ traceability into Material Requirements

When a Work Demand material row creates a Material Requirement:

- populate sourceBoqItemId when there is exactly one contributing BOQ item;
- where several BOQ items contribute, do not arbitrarily select the first and pretend it is the only source.

For a multi-source material:

- preserve the complete contributing BOQ item IDs in the shortage result;
- use the existing appropriate source-link mechanism if one exists;
- otherwise keep sourceBoqItemId nullable and include the contributing IDs in structured metadata or the smallest safe additive representation already supported by the code.

Do not lose traceability again through name-only aggregation.

At minimum, the requirement must retain enough source context to identify the Work Demand row and its contributing BOQ items.

4. Correct server-authoritative horizon resolution

The server remains the authority for resolving the procurement horizon.

Explicitly correct the clamp logic so distinct horizon modes do not collapse to the same programme ceiling incorrectly.

Required behaviour:

Date before programme start:
- demandUpToSelectedDate = 0;
- resolved programme index represents no elapsed programme month;
- do not floor it to programme month 1.

Date within the programme:
- include cumulative demand only through the corresponding programme date/month;
- do not automatically clamp it to the last programmed month.

Date after programme completion:
- include full programmed demand.

current_month:
- resolve relative to project/work-programme start, not calendar month alone.

next_programme_month:
- resolve to the next project programme period.

next_30_days:
- resolve using today + 30 actual days, then calculate cumulative demand through that cutoff.

custom_date:
- use the selected date exactly.

entire_programme:
- deliberately return full programme demand.

A maximum programme index may be used only to prevent reading beyond the programme after the requested cutoff genuinely exceeds programme completion. It must not force an earlier valid cutoff to the programme maximum.

Return:

- selectedHorizonMode
- resolvedHorizonDate
- resolvedProgrammeMonthIndex
- whether the horizon is before programme start, within programme, or after programme completion where useful

For each material contribution:

For partly programmed materials:

- horizon demand includes only the programmed contribution due by the cutoff;
- unprogrammed contribution is shown separately;
- do not treat the unprogrammed full BOQ contribution as immediate selected-horizon demand.

For Entire Programme:

- show programmed full demand plus the existing unprogrammed planning fallback;
- show a clear warning.

6. Correct selected-horizon and programme totals

For each material return:

- totalProgrammeDemand
- programmedTotalDemand
- unprogrammedDemand
- demandUpToSelectedDate
- futureProgrammedRequirement
- programmingStatus

Definitions:

totalProgrammeDemand:
- full planning demand, including the approved unprogrammed fallback where applicable.

programmedTotalDemand:
- demand attributable to programmed BOQ contributions.

unprogrammedDemand:
- demand attributable to BOQ contributions without programme bars.

demandUpToSelectedDate:
- cumulative programmed demand due through the resolved cutoff;
- under Entire Programme, include the full planning demand with the warning.

futureProgrammedRequirement:
- max(0, programmedTotalDemand - demandUpToSelectedDate).

Do not show the same full BOQ fallback as Demand to Horizon for every horizon.

10. Fix split-suggestion arithmetic

Correct any double subtraction in the internal/procurement split.

Use:

remainingAfterConfirmed =
max(
  0,
  demandUpToSelectedDate
  - confirmedIncomingPurchase
  - confirmedInternalIncoming
)

suggestedInternalQty =
min(
  remainingAfterConfirmed,
  hlcRecordedStock
)

suggestedProcurementQty =
max(
  0,
  remainingAfterConfirmed
  - suggestedInternalQty
)

Do not subtract HLC stock once in actionableShortfall and then subtract it again.

Ensure the split-dialog validation ceiling uses the same quantity basis.

The dialog must not allow:

- internalQty + procurementQty > remainingAfterConfirmed;
- a procurement suggestion larger than the true remaining quantity;
- Other Parties stock to enter the internal suggestion.
