BACKGROUND (confirmed by direct code review — do not re-derive)
Reported symptom: editing a Material Receipt (client/src/pages/PlantMaterialReceipts.tsx, "Update Receipt") and clicking save appears to do nothing — the dialog doesn't show an error, but the receipt is not updated either.

Two separate, compounding bugs, both confirmed in the code:

1. `updateMutation` (~line 490) has no `onError` handler at all. `createMutation`... actually specifically `deleteMutation` (~line 504) and `finalSubmitMutation` (~line 520) both have an `onError` that shows a toast with the server's message; `updateMutation` has none. So whenever the PUT request to `/api/plant-module/material-receipts/:id` fails for any reason, the user sees nothing — no toast, the dialog stays open, and it looks exactly like a silent no-op. This is the reason no error message appears, regardless of why the underlying save failed.

2. A specific, real case that WILL fail every time today: correcting a receipt that has already been Final Submitted (documentStatus = "submitted", shown with a lock icon). The server (`server/routes.ts` ~line 3645-3670, `PUT /api/plant-module/material-receipts/:id`) requires, for a submitted receipt:
   - A "direct editor" (Owner/Admin/anyone with the `plant_materials` edit permission) must send `editPermissionRequestId: 0` exactly.
   - Anyone else must send a real, currently-active, approved edit-permission request id (obtained via the `EditPermissionButton` component's request/approval flow).
   But the client only ever shows the `EditPermissionButton` (~line 1684-1691) for a submitted receipt's row — regardless of whether the logged-in user is a direct editor or not — and that button's flow always produces a real granted request id via `onEditGranted`, never `0`. So even an Owner/Admin going through the only edit path the UI offers for a submitted receipt ends up sending a real (non-zero) id, which the server's direct-editor branch rejects, because it specifically requires exactly `0`. Combined with bug #1, this failure is currently invisible — the correction attempt just silently fails.

PART 1 — SHOW WHY A RECEIPT UPDATE FAILS
Add an `onError` handler to `updateMutation` (~line 490), matching the existing pattern already used on `deleteMutation`/`finalSubmitMutation` in this same file: parse the server's error message (including the `NNN: {json}` prefix pattern already handled in `finalSubmitMutation`'s `onError`) and show it in a destructive toast. Do not change `onSuccess` or the mutation function itself.

PART 2 — LET A DIRECT EDITOR ACTUALLY CORRECT A FINAL SUBMITTED RECEIPT
1. For a submitted receipt's row, a direct editor (Owner/Admin, or anyone with the `plant_materials` edit permission — the same check already used elsewhere in this file, e.g. `isOwnerOrAdmin`/`canEdit`) must get a control that opens the edit form and, on save, sends `editPermissionRequestId: 0` — bypassing the request/approval flow entirely, consistent with what the server already expects from a direct editor. This can be a small, clearly-labelled addition next to or instead of the existing `EditPermissionButton` for that role, e.g. calling `handleEditClick(receipt, 0)` directly. Keep it visually distinct from the ordinary (non-submitted) Edit button so it's clear this is a "correct a locked receipt" action.
2. A non-direct-editor (no `plant_materials` edit permission) must keep using the existing `EditPermissionButton` request/approval flow exactly as today — do not change anything about that path.
3. Confirm the payload-building logic (~line 646-648, the `editPermissionRequestId` conditional in the update-submit handler) correctly sends `0` (not omitted, not `null`) when a direct editor uses the new control from 2.1, and still sends the real granted id when a non-direct-editor uses the existing approval flow.
