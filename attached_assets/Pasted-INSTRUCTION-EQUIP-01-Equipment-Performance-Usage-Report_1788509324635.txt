BACKGROUND (confirmed by direct code review — do not re-derive)
SitePulse already has the right foundation for this — we are not asking you to invent a new usage-tracking model, only to report off the one that exists:
- `equipment_usage` (plant-module) and `equipment_logs` (DPR-linked) are the two usage sources. When a DPR with an `equipmentId`-linked `equipment_logs` row is closed, the app already automatically creates the matching canonical `equipment_usage` row and records the link via `plantUsageId` on the log.
- `shared/equipmentContinuity.ts` (`pickLatestClosing`) is the app's own existing cross-source identity resolver — it already treats a `dpr_log` row and the `plant_usage` row it closed (matched via `plantUsageId`) as ONE physical event, not two. This report must follow that same principle for counting usage, not invent a separate heuristic (matching by same machine/date/hours) to detect duplicates.
- `shared/equipmentUsage.ts` (`computeEquipmentUsage()`) is the app's existing shared runtime/fuel calculation logic (hours or km/trips depending on meter type, expected diesel from the equipment's consumption norm, variance). Reuse this directly for the report's numbers — do not re-derive the math separately.
- `equipment_master` is the canonical fleet table (name, registration number, ownership owned/hired, hire start/end dates, consumption norm, plant name, active flag, output figures, meter type hour_meter/odometer). Both `equipment_logs.equipmentId` and `equipment_usage.equipmentId` reference this same table.
- `boq_projects.status` is `draft | active | closed` — this is the field to use for the active-project scope boundary below.
- There is no existing "equipment is scheduled/expected to work on date X" table. Only a hired machine's `hireStartDate`–`hireEndDate` window gives a real expected-activity period; owned equipment has nothing equivalent.
- No true fuzzy/similarity-matching library exists in this codebase; existing free-text matching elsewhere (e.g. `matchPlanTypeId`) uses normalize (lowercase/trim/collapse whitespace) + exact-or-substring matching. Reuse that same pattern for Part 1 below — do not add a new matching library.

PART 2 — STRICT, LINK-BASED DEDUPLICATION (not heuristic)
1. Counting rule: if an `equipment_logs` row has a valid `plantUsageId` pointing to a real `equipment_usage` row, count that usage ONCE via the `equipment_usage` row — the `equipment_logs` row is its source/reference only, never a second event. Only `equipment_logs` rows with no `plantUsageId` (unlinked legacy rows, whether Unclassified or Confirmed-legacy-matched) are counted as their own separate events.
2. Do not deduplicate by matching same-machine/same-date/same-hours or any other heuristic — the existing `plantUsageId` link (and `equipmentContinuity.ts`'s existing same-event logic) is the sole, authoritative source of truth for "is this the same event."
3. Report back a concrete before/after count for at least one real equipment example proving no double-counting.

PART 3 — THE REPORT: FLEET SUMMARY + MACHINE DRILL-DOWN
Build one permanent Equipment Performance & Usage screen with two levels:

A. Fleet summary (default view)
Filters: date range, site/project, plant-usage vs site-usage, ownership (owned/hired), equipment type, specific machine.
Per-equipment row: total working hours or km/trips (per its meter type), number of active days, diesel issued/consumed, expected diesel (via `computeEquipmentUsage`), diesel variance, efficiency %, last-used date, current location/status where available, and its data-confidence state (Part 1.4).
- Hired equipment: also show hire-period utilization — usage vs its `hireStartDate`–`hireEndDate` window, with gap days flagged only inside that window.
- Owned equipment: show "days since last use" — do NOT call it idle; there is no expected-activity schedule to justify that claim for owned equipment.

B. Machine drill-down (opening one equipment)
Chronological usage history table: date, site/plant, task, opening/closing meter, hours/km/trips, diesel actual, expected, variance, operator, linked DPR/usage source, breakdown notes if any. Table is the primary view; add an hours-and-diesel-efficiency trend chart above/alongside it as a secondary, visual aid — not a replacement for the table.

Diesel efficiency and utilization are two separate concepts — do not conflate them in the UI:
- Efficiency = actual vs expected diesel, from the equipment's consumption norm and usage basis (via `computeEquipmentUsage`) — computable for most equipment now.
- Utilization = working time vs an expected/available period — only reliable for hired equipment within its hire window; not shown as a hard number for owned equipment (Part 3.A).
