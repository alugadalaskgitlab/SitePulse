FROZEN BUSINESS RULE

No Execution Arrangement record means:

HLC / Contractor self-execution by default.

Absence of an arrangement is NOT:
- an error;
- a missing setup;
- an “Arrangement Required” condition.

Execution Arrangements are created only deliberately where all or part of a BOQ item is:
- outsourced/sublet;
- externally supplied;
- client supplied;
- split by responsibility;
- otherwise different from normal HLC self-execution.

PART A — REMOVE “ARRANGEMENT REQUIRED” DEFAULT STATE

1. In shared/executionState.ts:

Current zero-arrangement behaviour returns:
arrangement_required

Change this.

When there are no active arrangement records for the BOQ item/bar:
- treat execution as default HLC/self-execution;
- return a neutral/default self-execution state;
- do not render an amber warning;
- do not require user action.

Do not disturb states for arrangements that actually exist:
- draft
- submitted
- approved
- mobilisation_pending
- in_progress
- on_hold
- returned
- rejected
- cancelled
- completed

2. In shared/planningEngine.ts / deriveEarthworkSourcingBadge:

Zero active arrangements must not produce an “Execution Arrangement Required” message.

It should mean:
Default HLC execution / no outsourcing arrangement.

This may be represented as:
- no badge at all; or
- a neutral “HLC / Self-execution” status where a status is useful.

Prefer no warning badge in Gantt.

3. Gantt:

Do not display:
Execution Arrangement Required

merely because no arrangement exists.

Only show arrangement information when a deliberate arrangement exists.

Examples:
- Outsourced — Approved
- Partly Outsourced — Submitted
- Client Supplied
- HLC + Agency Split

No arrangement:
show no outsourcing warning.

PART B — PROCUREMENT / BOM MUST BE READ-ONLY ABOUT ARRANGEMENTS

The Procurement tab is for:
- material demand;
- stock;
- incoming quantity;
- shortfall;
- procurement action.

It is NOT an Execution Arrangement setup, management or navigation screen.

1. Remove clickable:
“Manage in Execution Arrangements →”

from Procurement / BOM rows.

2. Remove narratives such as:
“X CUM not covered by an arrangement yet”

when absence of an arrangement simply means HLC/self-execution.

3. Do not route the user from Procurement to arrangement creation, editing or management.

4. Procurement may show a read-only arrangement-status badge only when useful.

Examples:

No arrangement:
- blank; or
- HLC / Self-execution

Existing arrangement:
- Draft
- Submitted
- Approved
- Partly Outsourced
- Fully Outsourced
- Client Supplied

No action button.

5. Remove the separate bituminous arrangement navigation action as well.

WorkDemand.tsx currently has BituminousArrangementSummaryLine which, when a bituminous arrangement exists, renders a:
“View in Work Programme →”
link.

Remove that navigation action.

When a bituminous arrangement exists, Procurement/BOM must show only the read-only arrangement status text/badge.

Do not provide any arrangement-management OR arrangement-navigation link from Procurement for:
- earthwork;
- bituminous;
- future categories.

Execution Arrangements must be opened from its own dedicated project-level section.

6. Keep procurement actions independent.

Examples:
- Covered by stock
- Purchase required
- PI raised
- Confirmed incoming
- Partially covered
- Internal stock available

These remain procurement statuses.

Arrangement status must not replace procurement status.

PART C — PRESERVE EXISTING DEMAND-REDUCTION ENGINE

Do not change:

buildArrangementEffects
hlcRetainedFraction
DEMAND_AFFECTING_ARRANGEMENT_STATUSES

Existing correct behaviour must remain:

No arrangement:
100% HLC demand.

Draft/submitted/returned/rejected/cancelled:
do not reduce HLC demand.

Approved/mobilisation_pending/in_progress/on_hold:
reduce HLC demand only for the approved outsourced/client/not-applicable components and applicable quantity.

Partly outsourced:
reduce only the outsourced share/components.

Do not simplify this to a binary outsourced/not-outsourced model.
