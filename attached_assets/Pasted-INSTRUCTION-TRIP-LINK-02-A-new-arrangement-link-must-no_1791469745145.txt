THE GAP
`bulkLinkTripArrangement` (`server/tripArrangementLink.ts` ~line 29) resolves the
chosen arrangement by id and site only:

    .where(and(eq(earthworkArrangements.id, input.earthworkArrangementId), siteMatch(input.site)))

There is no status condition. The same is true of the options the selector offers,
and the manual correction mode deliberately bypasses the normal applicable-arrangement
resolution. So a trip can today be NEWLY attached to an arrangement that is draft,
rejected, cancelled or superseded — and VB-ARRANGE-02B would then bill against it.

The codebase already has the right tools and they must be used rather than
duplicated:
- `shared/arrangementStatusHistory.ts`: `arrangementStatusAsOf(arrangement, asOf)`
  resolves the status ON A GIVEN DATE from `revisionHistory`, and
  `isArrangementOperationalAsOf(arrangement, asOf, operationalStatuses)` tests it.
- `shared/arrangementAutoAllocation.ts`: `AUTO_SYNC_STATUSES`
  (`approved`, `mobilisation_pending`, `in_progress`, `on_hold`).
- `shared/materialReceiptSummary.ts` ~line 177 shows an existing caller choosing its
  own operational set.

=====================================================================
PART A — DECIDE THE RULE FROM WHAT EXISTS
=====================================================================
A1. Inspect the existing status helpers and their current callers, and determine
    which statuses are commercially valid for a NEW billing link. Do not invent a
    new set, and do not silently reuse one whose purpose is different. State in the
    report which set you chose, which existing caller you took it from, and why it is
    the right one for commercial linkage.
A2. The test is AS OF THE TRIP'S DATE, not today. `arrangementStatusAsOf` exists for
    exactly this reason: an arrangement approved in June and cancelled in September
    is valid for a July trip and invalid for an October one. Use the trip's own date.
A3. If you conclude the correct behaviour differs from what this instruction assumes,
    say so plainly with the evidence rather than following it.

=====================================================================
PART B — APPLY IT TO NEW LINKS ONLY
=====================================================================
B1. The bulk link operation rejects a trip whose date falls outside the chosen
    arrangement's commercially valid period, with a clear message naming how many
    trips were excluded and why. It does not silently drop them from the count.
B2. The arrangement options offered in the selector show the status, and either
    exclude the ones that are never valid or mark them plainly. The owner must not be
    able to pick one by accident.
B3. The same rule applies to a link set one-at-a-time from the Set-roles dialog and
    from the Materials Received edit form. One rule, one implementation, all entry
    points — do not write it three times.
B4. EXISTING LINKS ARE UNTOUCHED. A trip already pointing at an arrangement keeps
    that link and keeps displaying it, even if that arrangement is now cancelled or
    was never approved. Correcting history is the owner's decision, not this batch's.
