INSTRUCTION 06T — GUIDED DPR INTEGRITY & CONTEXT FIX
(supersedes the standalone 06R — the Execution Arrangement persistence work
in 06R is folded into §3 below; do not implement 06R separately)

STOP ADDING FEATURES TO DPR UNTIL THIS BATCH IS DONE. This batch fixes
correctness and internal consistency of the Guided/Detailed DPR activity
card. Priority order for this batch is:

  Chainage → Length → Programme Reach → Execution Arrangement → Material Trips

must become ONE consistent chain, each step silently derived from the one
before it, never a set of independent widgets that can disagree with each
other on screen.

This batch is triggered by a real production report (16-Aug-2026,
TAKKADPALLY-SIRUR site) showing, simultaneously, on the same DPR: Length
stuck at 0 despite chainage present, a highlighted reach that does not
match the entered chainage, a false "no Purchase Indent" warning on a
cut/fill excavated-earth activity, a borrow-earth activity showing both
"no execution arrangement" and "no approved indent" at once, and 24 real,
already-recorded soil delivery trips for that date/site not appearing
against the activities they should be linked to. None of the underlying
data was lost — this is a context-resolution and display problem, not a
data-loss problem (except §6, which is a separate, serious complaint that
must be independently proven, not assumed fixed).

--------------------------------------------------
1. CHAINAGE IS THE SOURCE OF TRUTH — LENGTH MUST ALWAYS BE DERIVED, NEVER STALE
--------------------------------------------------
Confirmed root cause: SiteEntry.tsx (Detailed DPR create) correctly imports
and uses ONE shared `calculateLengthFromChainage` (from the shared
dprCalculations module) and recomputes Length live as chainage is typed.
SiteEdit.tsx instead defines its OWN local, duplicate copy of
`calculateLengthFromChainage` (lines ~127-148) and — critically — its
Length input just displays whatever `entry.length` value was loaded from
the database (`value={entry.length ?? ""}`) without ever recomputing it
from the chainage already present when the screen opens. Length only
updates if the Engineer manually retypes the From/To boxes. This is why a
perfectly valid saved report opens up showing Length 0.

Fix:
- Delete SiteEdit.tsx's local duplicate `calculateLengthFromChainage`/
  `parseChainageToMeters` functions. Import and use the same shared
  dprCalculations module SiteEntry.tsx already uses — one calculation,
  one implementation, everywhere.
- On initial load of an existing DPR for edit, and any time chainage
  changes thereafter, Length must be recalculated from the current
  chainageFrom/chainageTo and reconciled against the stored value — never
  silently displayed stale. If a manually-overridden Length was
  deliberately saved different from the geometric calculation, follow the
  same "computed vs overridden" pattern already used elsewhere in this
  codebase for quantity override warnings (visible note, not silent
  overwrite) — do not guess a new rule here.
- Apply the same audit to Guided DPR and Detailed DPR create: confirm
  Length is always freshly derived from chainage on every render path,
  not just on keystroke.

--------------------------------------------------
2. PROGRAMME REACH MUST BE SILENT, BACKGROUND, AND ALWAYS RECONCILED — NOT A COMPETING CONTROL
--------------------------------------------------
Confirmed root cause: ProgrammeBarPicker.tsx auto-links a programme bar
once (`autoLinkedRef`, only "while nothing is linked" — `value != null`
skips re-attempting). Once a bar is linked, the highlighted/checked chip
stays fixed to that bar id and is never re-validated against the
chainage actually showing on the card. Separately, the "Outside planned
reach — review required" warning IS correctly triggered when there's a
mismatch — but the stale chip stays checked anyway, so the Engineer sees
a checkmark and a contradiction warning at the same time, about the same
thing.

Design principle (per Krishna): the Engineer's actual From/To chainage IS
the execution fact. Programme Reach is background bookkeeping — needed
for planned-vs-actual tracking, programme progress, RA/report drill-down,
and Execution Arrangement resolution — but it must be RESOLVED FROM the
chainage, not held as an independent, manually-clickable choice that can
silently drift out of sync with it.

Fix:
- Re-run bar matching (the existing `autoMatchBar` logic) every time
  chainage or side changes on an entry that already has a linked bar, not
  only while nothing is linked. If the newly-entered chainage no longer
  matches the currently-linked bar:
  - If exactly one other bar now matches, re-link automatically and show
    a brief, clear "Reach updated to match your entry" notice — no silent
    surprise, but no separate manual step either.
  - If no bar matches, or more than one matches, clear the stale link
    (do not leave an old checkmark showing) and surface ONE single,
    clear message — reuse "Outside planned reach — review required" —
    not a checked chip plus a contradiction.
- Remove the four large Reach chip buttons from their current prominent
  position on the main activity card. Collapse them into a secondary
  "Programme context" disclosure (e.g. a small expandable row or a "Change
  planned reach" link) that stays reachable for genuine manual override /
  out-of-sequence work, but does not visually compete with the Engineer's
  own chainage/length/qty fields as if it were an equally-weighted, separate
  decision.
- This must not change any balance/remaining-quantity arithmetic, BOQ
  credit, or RA/report calculation — only when/how the bar link is
  resolved and how prominently it is displayed.

3. EXECUTION ARRANGEMENT MUST RESOLVE FIRST AND RELIABLY — PERSIST IT ON THE DPR ROW (absorbs 06R)
--------------------------------------------------
Confirmed: the classification logic is already correct — `reused_excavated`
is already listed in `AGENCY_SUPPLIED_ARRANGEMENT_TYPES` and
`receiptRelevanceForType` already returns "none" for it (shared/
materialReceiptSummary.ts). `isHlcProcurementResponsible()` already
correctly returns false for agency-supplied/reused-excavated types WHEN
an arrangement is actually resolved. The bug is upstream: for these two
real activities, `arrangement` is coming back null/undefined at the point
ActivityReceiptStrip runs — and the code's documented fallback for "no
arrangement resolved" is to assume HLC is procurement-responsible and run
a Purchase Indent lookup, which is correct behaviour ONLY when nothing has
ever been configured, and wrong/misleading when it happens because the
resolution itself is failing to find real data.

Investigate and report which of these is actually happening for the two
sample activities (Excavated Earth and Borrow Earth, same stretch,
TAKKADPALLY-SIRUR, 16-Aug-2026), before proposing the fix, since the
correct remedy differs:
  (a) No Execution Arrangement was ever created/allocated for this
      programme bar in Work Programme — a setup gap, not a code bug.
  (b) An arrangement exists and is allocated, but the live lookup chain
      (GET /api/dpr/programme-bars → bar.arrangement, matched by
      boqProjectId/boqItemId/programmeBarId) is failing to find or attach
      it to this specific activity row — a real resolution bug.

Whichever is found, also implement the permanent fix (this is 06R's
scope, now done here instead of separately):
- Add `earthworkArrangementId` to the progress-row state in Guided DPR,
  Detailed DPR create, and Detailed DPR edit. At the point the bar/
  arrangement is resolved (§2's reconciled resolution, not a one-time
  guess), persist `earthworkArrangementId` onto the row — the schema
  column (`progress_entries.earthworkArrangementId`) already exists and
  is currently never set by any DPR screen.
- Once persisted, a saved row's arrangement is a historical fact: never
  silently recomputed or overwritten on a later edit unless the Engineer
  deliberately changes the row's BOQ item/programme-bar context (a real
  work-context change, not just reopening the form). Preserve it through
  `cloneDpr`'s version/clone path the same way `layerNo` (06P) already is.
- Show the resolved arrangement plainly on the card for ALL types, not
  only "part" mode (today only "part" mode surfaces anything, and even
  then nothing is shown, only the existing `executedBy` requirement is
  enforced — keep that requirement exactly as-is).
- For `relevance: "none"` types (reused_excavated and any other type
  `receiptRelevanceForType` marks "none"): show ONLY the execution line.
  No Purchase Indent block, no "Received today" block, nothing about
  material receipts at all — this activity type has none, by design.
- For types that DO need a receipt (borrow earth, GSB, WMM, aggregates,
  etc.): show the arrangement badge FIRST and correctly. Only if the
  resolved arrangement/override genuinely makes HLC procurement-
  responsible should the Purchase Indent lookup run. If arrangement truly
  is unset for a bar that needs one, show ONE single clear message — e.g.
  "No supply arrangement set up for this stretch — configure it in Work
  Programme" — never a "no execution arrangement" badge and a separate
  "no approved/ordered indent" warning shown together as if they were two
  unrelated problems.
- `material_logs` scope note: do not add schema to `material_logs` in
  this batch — that remains a separate, deliberately-deferred investigate-
  first item. Nothing in this section requires touching it.

4. MATERIAL TRIP MATCHING MUST FIND REAL, RELEVANT DELIVERIES RELIABLY
--------------------------------------------------
Confirmed: the 24 soil trips for TAKKADPALLY-SIRUR on 16-Aug-2026 are real,
correctly recorded (10,500 CFT, all tagged "linked to work context" on the
Materials Received screen) — they are not lost. The DPR activity card's
"Received today" match requires same site + same date AND (matching
`earthworkArrangementId`, OR matching `boqItemId` AND matching/null
`programmeBarId`). Since `earthworkArrangementId` has never been set on
any DPR row until this batch (§3), matching has been relying on
boqItemId+programmeBarId alone — and given §2's stale/mismatched reach
linking, a DPR row can easily be carrying the wrong or a blank
programmeBarId, causing a real, relevant delivery to not match.

Investigate and report, for this real case specifically: what
boqItemId/programmeBarId/earthworkArrangementId values are actually
stored on the 24 trip records, versus what the Excavated Earth and Borrow
Earth activity rows in that DPR are carrying, and explain the exact
mismatch found. Then fix the matching so genuinely-relevant deliveries
(same site, date, material, and correctly-resolved reach/arrangement per
§2/§3) are reliably found and counted — without loosening the match to
the point of pulling in deliveries that are not actually relevant to that
activity. Do not change anything about how a trip is created or how site
material stock/reconciliation is computed — matching/display only.

second time. No new ledger, no schema change, no change to `material_logs`
itself — a display composition change only, pulling in the real trip
records that already exist.
