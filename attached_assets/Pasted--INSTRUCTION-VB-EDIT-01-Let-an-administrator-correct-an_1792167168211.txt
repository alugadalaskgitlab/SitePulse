## Part A — One Edit rule for every bill type

**The fault.** In `client/src/pages/VendorBills.tsx` the Edit control is rendered
when:

```
canEdit && (!bill.hireStatements?.length
  || (bill.status === "draft" && bill.hireStatements.every(s => s.status === "draft")))
```

So a bill **with** hire statements can only be edited while it is a draft, while a
bill **without** them — material, transport, labour — can be edited at any status
including paid. An approved equipment-hire bill therefore cannot be corrected at all
from the screen, even though `PUT /api/vendor-bills/:id` would allow it. The user
needs to correct a bill date on an approved hire bill and has no way to ask.

**Required.**

1. One rule for every bill type: where the user may edit at all, the Edit control
   appears **regardless of status and regardless of whether the bill carries hire
   statements**. A voided bill stays uneditable, as AUDIT-01 established.
2. **Do not change the server's permission check.** `PUT /api/vendor-bills/:id`
   already requires an administrator for a verified, approved or paid bill, and the
   ordinary edit permission otherwise. Leave both exactly as they are.
3. Do not relax the hire-statement rules themselves. If a hire statement cannot
   accept a change, the save refuses as it does today — the button appearing is not
   a promise that every field is editable.

## Part B — Say what the edit costs, before it happens

**The fault.** `PUT /api/vendor-bills/:id` sets the status back to `draft` when an
administrator edits a verified, approved or paid bill. Nothing warns the user. A
bill the user had approved silently leaves the approved list and drops out of
Payable now, and they discover it later.

**Required.**

1. Before an edit to a bill that is verified, approved or paid is submitted, show a
   confirmation naming, in plain words:
   - that the bill will return to **draft**;
   - that it will need verifying and approving again;
   - that it will leave **Payable now** until it is approved again;
   - the bill number and its current status.
2. The edit proceeds only on an explicit confirmation. Cancelling changes nothing.
3. A draft bill shows no confirmation — nothing is lost by editing a draft.

**Constraints.** Do not change the reset itself. It is the correct behaviour: a
corrected bill should be looked at again.

---

## Part C — Record the reset as its own entry

AUDIT-01 records an edit through `recordChange`. The **status reset that the edit
causes** must be legible on its own, not buried inside the before-and-after of a
whole bill.

**Required.** When an edit resets the status, write one further audit entry through
the existing `recordChange` helper: module `vendor_bills`, the bill id, action
`status_reset`, the old status and the new status, and the actor. No reason is
required — the edit entry beside it carries the detail.

Add `status_reset` to the action label map in
`client/src/components/HistoryDialog.tsx` so it renders as words rather than a raw
string.

---

## Part D — VOID belongs to the Owner

**The fault.** AUDIT-01 gated the void action on `assertAdmin` on the server and
`isAdmin || isOwner` in the client. Voiding removes money from the company's
liability, and every administrator can currently do it.

**Required.**

1. `POST /api/vendor-bills/:id/void` requires **`isOwner`**, matching the delete
   route. An administrator who is not the Owner is refused.
2. The VOID control is shown only to the Owner.
3. Everything else about voiding stays exactly as AUDIT-01 built it — the reason,
   the audit entry, the bill's own figures untouched, the VOID marking, the
   exclusion from totals.

**Constraints.** Do not remove the void action or its endpoint. Do not change who
may delete. Do not add any new permission key.

---

## Part E — A draft bill does not say who raised it

**The fault.** On Bill Detail, the verified, approved and paid states each name the
person who did it — the bills table stores `verifiedBy`, `approvedBy` and
`paymentRecordedBy` as text. The draft state shows only `createdAt` — a date and
time with no name — because no name was ever stored for it. The table does hold
`authorUserId`, so the person is known; it is simply not resolved for display.

**Required.**

1. Show **who raised the bill** beside the created date, in the same shape as the
   other three states, resolved from `authorUserId` against the users table.
2. Where `authorUserId` is empty — older bills saved before it was recorded — say so
   plainly ("author not recorded") rather than leaving a bare timestamp or inventing
   a name.
3. Where a bill is **back in draft because it was edited**, the draft line must not
   read as though the original author did that. Name the original author as the one
   who raised it, and leave the edit itself to the history, where Part C records it.

**Constraints.**

- **Display only.** No migration, no new column, no backfill, and
  `authorUserId` is never written or changed by this batch.
- Do not alter `verifiedBy`, `approvedBy`, `paymentRecordedBy` or any timestamp.
- Do not resolve the name on every row of the bills list — this is the Bill Detail
  page only, so the list does not gain a query per row.
