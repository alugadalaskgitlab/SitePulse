GEOMETRY BATCH 01A — CORRECT EXISTING ROAD GEOMETRY FOUNDATION

Geometry Batch 01 is implemented and working as a preview foundation.

This batch is a narrow correction pass on that existing implementation.

Do NOT generalize Geometry to arbitrary BOQ item calculation types yet.
Do NOT start Earthwork geometry yet.
Do NOT feed Geometry into Auto Sequence, No-Scope, Execution Arrangement, BOM, DPR or RA bills.

OBJECTIVE

Correct the current project geometry foundation in four areas:

1. use existing BOQ Layer Config when identifying WMM/DBM/BC/etc.;
2. add explicit Formation Width as a project design input;
3. improve the independent suggested width handling for pavement layers;
4. investigate the reported decimal-width issue and fix it only if reproducible.

No broad redesign.

Confirm current behaviour before changing it.

2. FIX WMM / LAYER IDENTIFICATION USING EXISTING LAYER CONFIG

Current issue:

A BOQ item already configured as WMM through the existing BOQ Layer Config can still appear in Geometry as:

"Needs attention"

because Geometry currently relies on generic description/category classification and does not consume the explicit saved layer config.

The BOQ already has:

item.layerConfig?.mixType

which may contain explicit resolved values such as:
- WMM
- GSB
- DBM
- BC
- etc.

For Geometry classification, use the following priority:

1. explicit existing `layerConfig.mixType`
2. other existing persisted reliable item/layer mapping if available
3. short name / deterministic existing classification
4. generic description/category heuristic fallback
5. needs-mapping if still uncertain

Normalize `layerConfig.mixType` safely for comparison:
- trim surrounding whitespace;
- compare case-insensitively;
- preserve the original stored value.

Do not require exact casing such as "WMM" if saved data contains values such as:
- "wmm"
- " WMM "
- "Dbm"

Unknown or unsupported mixType values must fall back safely to the next classification source rather than being guessed.

Do NOT require the user to configure the same BOQ item again in Geometry if SitePulse already knows its layer type.

For the current WMM example, an item whose saved layerConfig.mixType confirms WMM must resolve as WMM and no longer show "Needs attention."

Do not modify the Layer Config workflow itself.

3. ADD EXPLICIT FORMATION WIDTH

Add a project-level geometry input:

Formation Width (m)

This is a DESIGN INPUT.

Do not treat formation width as being derived from side slope.

For initial convenience, when geometry is first configured and no Formation Width has been entered, SitePulse may SUGGEST:

carriageway
+ paved shoulder LHS/RHS
+ soft shoulder LHS/RHS

But Formation Width must then exist as its own editable value.

Do not silently keep recalculating/overwriting a user-confirmed Formation Width whenever shoulder values change.

The distinction is:

- finished/paved widths describe the road crust/surface;
- Formation Width describes the prepared formation/subgrade platform;
- future earthwork geometry will use Formation Width together with cut/fill depth and side slopes.

Store Formation Width in the existing road geometry profile structure.

A small additive schema field is acceptable.

Use the app's existing idempotent schema-evolution pattern.

4. LAYER WIDTHS — INDEPENDENT SUGGESTIONS, NOT ONE PAVED-WIDTH RULE

Current behaviour is too simplistic:

- Subgrade derives from carriageway + paved + soft shoulders
- GSB/WMM derive from paved width
- DBM/BC derive from paved width

Keep the existing per-layer override concept, but improve the meaning.

Each layer must have its own independently resolved:

Suggested Width
and
Override Width (optional)

For this correction batch:

- Subgrade suggested width → Formation Width
- DBM suggested width → paved width
- BC suggested width → paved width
- Prime/Tack suggested width → paved width where applicable

For GSB and WMM:

Do NOT hard-code them permanently to paved width as an engineering truth.

Use a simple initial suggestion, but clearly treat it as a suggestion requiring confirmation/override.

Preferred safe behaviour:

- if a user has entered a layer width override, use it;
- otherwise show a suggested width;
- make the suggested width plainly editable through the existing Advanced / Adjust layer widths control.

If a sensible project-level design width for GSB/WMM cannot be derived reliably from current inputs, it is acceptable for the suggested width to start from the current paved width, PROVIDED the UI/report makes clear that this is only a suggested default and not a design assumption guaranteed to be correct.

Do not create a complex cross-section designer in this batch.

5. UI WORDING

Where the table currently says:

"Default width"

change it to:

"Suggested width"

or similarly clear wording.

Reason:

the value is a convenience/default derived from the simple road section, not necessarily the project's final design width.

Keep:

Override width

as the explicit user-confirmed per-layer adjustment.

6. DECIMAL WIDTHS — INVESTIGATE BEFORE FIXING

User reports that decimal widths are not being accepted.

Do NOT assume the cause.

First reproduce using examples such as:

- carriageway = 7.25
- paved shoulder = 1.50
- Formation Width = 9.375
- GSB override = 8.75

Check separately:

A. Can "." be typed in the field?

B. Does the field temporarily accept an incomplete decimal such as "7." while editing?

C. Does blur/save round or truncate the value?

D. Does API validation reject it?

E. Is precision lost on persistence/reload?

F. Is this browser/input behaviour rather than backend validation?

If decimals already work correctly in the current build:
- do not change production code merely to create a diff;
- report the reproduction result.

If a real issue is found:
- fix the narrow cause;
- support reasonable road-design precision;
- retain finite-number validation.

Store enough numeric precision for values such as:
9.375 m.

Do not unnecessarily force integer widths.
